The fastest way to diagnose a failed request is the status code plus the
error body. Here are the stumbles you're most likely to hit first.

## `401 Unauthorized` on `/v1` requests

Your relay key is missing, malformed, or wrong.

- Confirm the header is exactly `Authorization: Bearer <relay-key>`.
- Use the **plaintext** returned when the key was created, not the id or
  prefix. If you lost it, mint a new one — plaintext is never retrievable.
- A disabled relay key also returns 401; check it's enabled in the dashboard.
- `token_revoked` means an inference token was revoked — either by id
  (`DELETE /api/auth/token/{jti}`) or in bulk (`POST
  /api/auth/token/revoke-all`, which invalidates every token the caller
  holds). Mint a fresh one; see [Inference tokens](/concepts/auth#inference-tokens).

## `403 Forbidden` — model not granted

The relay key authenticated, but its **policy** doesn't grant the requested
model.

- In the dashboard, open the policy attached to your relay key and confirm
  the model is in its allowed set.
- The model name in your request must match a catalog model the policy grants.

## `404` — unknown model or no binding

- The `model` value doesn't resolve to any catalog model, **or**
- the model has no **enabled host binding**. A model needs a binding to a
  host (with an adapter and an upstream name) to be routable.

List what your key can actually reach:

```bash
curl http://localhost:8080/v1/models \
  -H "Authorization: Bearer <relay-key>"
```

## `502` / `503` — "no healthy keys in pool"

Every host key for the route has tripped its **circuit breaker** — usually
because the upstream credential is wrong, revoked, or rate-limited. Each key
has a per-key breaker keyed on auth / quota / rate-limit / server-error
classification.

To recover:

1. Fix the underlying cause — correct the upstream key value, or wait out a
   rate limit.
2. Clear the breaker state so the fixed key can be tried again. In dev with
   the bundled stack:

   ```bash
   make breakers-reset
   ```

   This clears the pooled host keys' circuit-breaker state. In production,
   breakers heal automatically once the cooldown passes.

<Info>
A rotated key gets a fresh breaker automatically — the breaker is keyed by
value-hash, so a new value starts clean and the old hash's record expires.
</Info>

## Adapter mismatch

If a request to a model returns a wire-format error from the upstream, the
host binding's `adapter` (`openai` or `anthropic`) likely doesn't match the
upstream's actual wire protocol.

- A single host (e.g. AWS Bedrock) can serve models on different protocols —
  the adapter is set **per binding**, not per host.
- Confirm the binding's adapter matches how that specific model speaks
  (Claude on Bedrock → `anthropic`; Llama on Bedrock → `openai`).

## The container starts but the dashboard won't log in

- On the **standalone** image the admin password is auto-generated and
  **printed to the container logs** on first boot — check `docker logs` for
  the `admin` / password line. It's persisted on the data volume across
  restarts.
- The admin UI is served on `RELAY_CONTROL_PORT` (`:8081` by default; standalone
  maps it there). Set it to `off` only if you want the control plane disabled.
- For local HTTP (no TLS), `RELAY_COOKIE_SECURE` must be `false` — otherwise
  the session cookie is marked `Secure` and the browser drops it. The
  standalone image already defaults it to `false`; set it on the lean image.
- On the **lean** image you supply credentials yourself: set
  `RELAY_ADMIN_TOKEN` for bearer access, or mount a `kind: User` YAML into
  `RELAY_CONFIG_DIR` for dashboard username/password login.

## Credentials (and catalog) regenerate on every run

You're starting a **new** container each time without a volume, so the
standalone image boots against an empty data dir and regenerates the master
key, admin credentials, and catalog. Mount a named volume to persist them:

```bash
docker run -p 8080:8080 -p 8081:8081 \
  -v relay-data:/var/lib/postgresql/data \
  wyolet/relay:standalone
```

Everything — Postgres data, master key, admin login — lives under that one
directory. See [Persisting data](/configuration#persisting-data-across-runs)
and [Retrieving or pinning the master key](/configuration#retrieving-or-pinning-the-master-key).

`docker stop` + `docker start <container>` already preserves state; only a
fresh `docker run` without a volume starts clean.

## Stored host key won't decrypt after a restart

`RELAY_MASTER_KEY` changed between runs. It must be **stable** — it unwraps the data keys stored secrets are encrypted under. `relay secret status` lists those data keys as `locked`, and lists the ids of the values the process cannot decrypt in `undecryptableRows`. Restore the original master key, or keep the new one and add the original as `RELAY_MASTER_KEY_EXTRA`, then follow [Changing the master key](/concepts/secret-keys#changing-the-master-key) to move onto the new one.

The standalone image keeps the key stable automatically **as long as you mount a volume** (see above).

### The original master key is lost

The values encrypted under it are lost too. To store values again under the new key:

1. Run `relay secret status` with only the new key configured and note `undecryptableRows`. A value's id is the id of the host key it belongs to.
2. While any value in the format from before data keys cannot be decrypted, `relay secret rewrap` is refused, so delete the values in `undecryptableRows` by hand:

   ```sql
   BEGIN;
   SELECT id, name FROM secrets WHERE id IN ('<id>', '<id>');  -- the host keys to re-enter
   DELETE FROM secret_values WHERE id IN ('<id>', '<id>');
   COMMIT;
   ```

   An id that starts with `payload-logging:` holds payload-logging credentials: write them again in the `payload-logging` settings section. Any other id with no host key is the inference-token signing key: clear `signingKey` in the `auth:tokens` settings section so the next boot generates a new one (tokens signed by the old key stop verifying).
3. Run `relay secret rewrap --to <new kek id>`, where the new KEK id is the one in `heldKeks`. It lists every data key under the lost key as skipped, and new data keys are wrapped under the new key from then on.
4. Run `relay secret rotate --all`, so every scope gets a primary data key the new key opens.
5. Re-enter the values of the host keys from step 2 and of any other host key that loads unresolved, and re-authorize OAuth host keys.

## Wrong master key at the upgrade to data keys

When `RELAY_MASTER_KEY` held a different key than the one the stored values were encrypted under before the upgrade, those values stay in the old format: `legacyRows` stays above 0, `undecryptableRows` lists them, pods log `cannot rewrite stored secret`, and the host keys load unresolved. Values written since then (a host key value entered again, a refreshed OAuth token) were stored under data keys wrapped by the wrong key, and the first of them made it the target (`targetKek`).

1. Set `RELAY_MASTER_KEY` to the correct key and `RELAY_MASTER_KEY_EXTRA` to the wrong one, and roll every pod. The pods convert the old-format values within seconds; wait until `legacyRows` is 0. New data keys are still wrapped under the wrong key until the next step.
2. Run `relay secret rewrap --to <kek id of the correct key>` (the first entry in `heldKeks`). Every data key is wrapped under the correct key and it becomes the target. Skip this step if `targetKek` is empty or already the correct key.
3. When `relay secret status` shows every data key under the correct KEK, remove `RELAY_MASTER_KEY_EXTRA` and roll every pod.
4. If the wrong key may be known elsewhere (it belongs to another deployment, or came from an example), whoever has it and a copy of the database from that period can unwrap the data keys it wrapped. Rotate every scope (`relay secret rotate --all`), wait until the old data keys show 0 `rows`, and destroy them, as in [If the master key leaks](/concepts/secret-keys#if-the-master-key-leaks).

## Health checks

```bash
# Inference readiness: Postgres ping + catalog loaded (public)
curl http://localhost:8080/healthz

# Control plane build version (public)
curl http://localhost:8081/api/version
```

<Note>
Still stuck? Send the request, the full error body, and the output of
`/healthz` and `/api/version` — that's enough to diagnose almost anything.
</Note>
