title: "Catalog server"
description: "The HTTP layout catalog releases are served from, and how to run catalog-server"
---

Relay and the Go SDK resolve [catalog](/concepts/catalog) releases over plain HTTP: one YAML read for the channel index, then a GET for the release file and its `.sha256`. No git, GitHub API or credentials are involved, so any host that serves this layout works. `catalog-server` serves it from a git mirror of [`wyolet/relay-catalog`](https://github.com/wyolet/relay-catalog).

Relay defaults to the public server at `https://catalog.wyolet.com`. The examples use `https://catalog.example.com` for a server you host yourself.

## Paths

| Path | Response | Caching |
| --- | --- | --- |
| `/index.yaml` | The channel index (below). | `public, max-age=60`; `ETag` is the quoted sha256 of the body, `If-None-Match` gets `304`. |
| `/releases/<tag>/catalog.json.gz` | The SDK catalog of release `<tag>`. | `public, max-age=31536000, immutable`; `ETag: "<sha256>"`, `If-None-Match` gets `304`. |
| `/releases/<tag>/relay-catalog-data-<tag>.tar.gz` | The release's `data/` tree, which Relay seeds from. | As above. |
| `/releases/<tag>/<file>.sha256` | The sum file published with the release on GitHub, byte for byte. | As above. |
| `/channels/<channel>/latest/<file>` | `302` to `/releases/<tag>/<file>` for the channel's latest tag. `<file>` is `catalog.json.gz` or `relay-catalog-data.tar.gz`, optionally with `.sha256`. For curl and people; clients read the index. | `public, max-age=60` |
| `/livez`, `/readyz`, `/metrics` | Health and Prometheus metrics; see [Running catalog-server](#running-catalog-server). | none |
| `POST /v1/webhooks`, `POST /hooks/github` | Release webhook registration and the repository push hook; see [Release webhooks](#release-webhooks). | none |

Release files are served as `Content-Type: application/gzip` with no `Content-Encoding`: the body is the stored `.gz` file, and clients check the sha256 of exactly those bytes. A proxy in front of the server must not compress or decompress `/releases/*`, or every checksum fails.

## Verifying a download

```bash
curl -fsSLO https://catalog.example.com/releases/v0.1.18/catalog.json.gz
curl -fsSLO https://catalog.example.com/releases/v0.1.18/catalog.json.gz.sha256
sha256sum -c catalog.json.gz.sha256
```

The sum files are `sha256sum` output: `<hex digest>  <file name>`.

`catalog-server` rebuilds each file from the tag's tree and serves the rebuild only when its sha256 equals the published sum. When it differs (a newer builder composes the catalog differently) or the build fails, the server downloads the published file, checks it against the same sum, and serves that. A tag's bytes therefore never change, whichever server version serves them. The check runs on the same origin as the download, so it catches corruption and builder drift, not a compromised host.

## Schema channels

```yaml
channels:
    v1alpha2:
        latest: v0.1.18
```

A tag's channel is the last segment of the `apiVersion` every document in its data tree shares: `relay.wyolet.dev/v1alpha2` is channel `v1alpha2`. A client reads only the channel of the schema it was built for. A release with a new schema is published under a new channel, so a client that can't parse it never picks it up; using it takes a client upgrade.

`latest` is the highest release tag of the channel whose two sum files are published and whose two files verified. Release tags are `vX.Y.Z` with no pre-release or build suffix. The index never names a tag that can't be downloaded, whatever order the release's files were uploaded in. A tag whose documents disagree on `apiVersion` is never indexed.

## Status codes

- **404**: an unknown tag, a tag that isn't a release tag, a file name other than the two above, or a file the release didn't publish. v0.1.0 to v0.1.9 publish no files, and v0.1.10 to v0.1.14 only `catalog.json.gz`. A 404 for a release tag's file is sent with `Cache-Control: no-store`, since the file may be published later.
- **503**: `/index.yaml` before the first sync has finished; or a release file that is published but couldn't be verified, because the published file failed its own sum or couldn't be fetched. A release file's `503` is sent with `Retry-After: 60`.

Replicas sync on their own, so one may index a tag another hasn't fetched yet. A request for a tag the server doesn't hold, or whose sums it is still waiting for, waits for an early sync (at most one every 10 seconds, up to 20 seconds) before it is answered, so a file the index names never answers 404 from a replica that is behind.

## Release webhooks

A relay that can receive HTTPS requests can register to hear about new releases instead of waiting for its next poll. The nudge carries no data a relay acts on: it only prompts the relay to re-read the index and verify the files itself.

```bash
curl -X POST https://catalog.example.com/v1/webhooks \
  -H 'Content-Type: application/json' \
  -d '{"url": "https://relay.example.com/catalog/hooks/release", "channel": "v1alpha3"}'
```

| Answer | Meaning |
| --- | --- |
| `202 {"expiresAt": "<RFC 3339>"}` | Registered for 24 hours. Registering the same `url` and `channel` again renews it. |
| `400` | The body isn't JSON, the URL isn't an absolute `https` URL without credentials, its host doesn't resolve, or the index has no such channel. |
| `403` | The host resolves to a loopback, private, link-local, CGNAT, unique-local, multicast or reserved address, or the challenge failed. |
| `429` | More than 10 registrations from one client address in a minute. |
| `503` | The replica holds its limit of 10,000 subscriptions. |

Before it answers, the server resolves the host once and sends the challenge to that address; every later request to the receiver dials the same address, with the URL's host for TLS and the `Host` header, and never follows a redirect. The challenge is `POST <url>` with `{"type": "challenge", "challenge": "<32 hex chars>"}`; the receiver must answer `200` with `{"challenge": "<same value>"}` within 5 seconds.

When a channel's latest tag moves to a newer tag whose files all serve, each live receiver of that channel gets `POST <url>` with `{"type": "release", "channel": "v1alpha3", "tag": "v0.2.3"}`. Any `2xx` counts as delivered. A failure or a 5-second timeout is retried 10 seconds, 1 minute and 5 minutes after that receiver's own failed attempt, then given up for that tag; a receiver that misses 3 tags in a row is removed. Once a newer tag of the channel is sent, pending retries for the older tag stop. At most 32 nudge requests are in flight at once. Requests carry `User-Agent: wyolet-catalog-server/<version>` and `Content-Type: application/json`. A server that restarts sends nothing for the tags it finds at startup.

Subscriptions live in the memory of the replica that took the registration, which is also the one that sends to it. A restarted replica forgets them until relays renew, so a relay that registers should also poll.

`POST /hooks/github` asks for an early sync and answers `202`; point the catalog repository's push webhook at it to pick up a new tag in seconds rather than at the next poll. Its payload is never read and it needs no secret: a forged call costs one fetch. Calls are coalesced to at most one sync every 10 seconds, and a call inside that window is synced at its end, not dropped.

## Stability

This layout never changes in place. Files under `/releases/<tag>/` never change once served. A breaking change to the layout ships beside this one, under new paths, and this one keeps serving.

## Pointing clients at a server

### Relay

```bash
RELAY_CATALOG_VERSION=latest
RELAY_CATALOG_INDEX_URL=https://catalog.example.com/index.yaml
RELAY_CATALOG_URL=https://catalog.example.com/releases/{version}/relay-catalog-data-{version}.tar.gz
```

`RELAY_CATALOG_INDEX_URL` is read only when `RELAY_CATALOG_VERSION` is `latest`; a pinned tag goes straight to `RELAY_CATALOG_URL`, with `{version}` replaced by the tag. Relay fetches `<url>.sha256` first and extracts the tarball only when its sha256 matches; a missing or mismatching sum fails the download. Tags before v0.1.15 have no data tarball, so a relay pinned to one can't download it: seed it from a checkout of the tag with `RELAY_CATALOG_DIR` instead.

### Go SDK

```go
src := catalogsource.Release("", cacheDir,
	catalogsource.WithIndexURL("https://catalog.example.com/index.yaml"),
	catalogsource.WithDownloadURL("https://catalog.example.com/releases"),
)
```

Tag `""` resolves the SDK's channel through the index; a concrete tag skips the index. Files are fetched from `<download URL>/<tag>/catalog.json.gz` and checked against `catalog.json.gz.sha256` before they are used or cached.

`catalogsource.Latest` follows the channel's latest tag, which is what `client.Models` and `client.Catalog` read outside proxy mode:

```go
src := catalogsource.Latest(catalogsource.WithBaseURL("https://catalog.example.com"))
```

`WithBaseURL` reads `<base>/index.yaml` and `<base>/releases`. Without it, `WR_CATALOG_URL` sets the base (default `https://catalog.wyolet.com`), and `WR_CATALOG_URL=off` uses the catalog embedded in the SDK with no request. The index is revalidated with `If-None-Match` at most once every 10 minutes (`WithRefreshInterval`). When the server can't be read, the last good catalog is served, and with `WithCacheDir` or `WR_CATALOG_CACHE_DIR` it survives a restart.

## Running catalog-server

```bash
GOEXPERIMENT=jsonv2 go build -o catalog-server ./cmd/catalog-server
catalog-server serve
```

Or run the image, published with each relay release as `ghcr.io/wyolet/catalog-server:<relay version>`. It holds `catalog-server`, `catalog-validate` and git, runs as uid 65532, and defaults to `catalog-server serve`:

```bash
docker run -p 8080:8080 ghcr.io/wyolet/catalog-server:<version>
```

On Kubernetes, set `catalogServer.enabled: true` in relay's [Helm chart](https://github.com/wyolet/relay/tree/main/chart#catalog-server).

It needs the `git` binary on `PATH`: the data tarball is `git archive` output, and Go's gzip writer produces different bytes, so a pure-Go build could never match the published sums. It needs outbound HTTPS to the repository (git fetch) and to its release downloads; for GitHub that is `github.com` plus the host release downloads redirect to. It holds no credentials and no state beyond the mirror directory and memory, so replicas run independently.

| Variable | Default | Description |
| --- | --- | --- |
| `RELAY_CATALOG_SERVER_ADDR` | `:8080` | Listen address. |
| `RELAY_CATALOG_SERVER_REPO` | `https://github.com/wyolet/relay-catalog.git` | Repository to mirror. Only its tags and `main` are fetched. |
| `RELAY_CATALOG_SERVER_RELEASES_URL` | `https://github.com/wyolet/relay-catalog/releases/download` | Where each tag's published files and sums live, as `<url>/<tag>/<file>`. |
| `RELAY_CATALOG_SERVER_SYNC_INTERVAL` | `60s` | How often the mirror is fetched, as a Go duration. Matches the index's `max-age`. |
| `RELAY_CATALOG_SERVER_CACHE_BYTES` | `64Mi` | Memory budget for release files, in bytes or with a `Ki`, `Mi` or `Gi` suffix. |
| `RELAY_CATALOG_SERVER_MIRROR_DIR` | `<temp dir>/relay-catalog-mirror` | The bare clone. |
| `RELAY_CATALOG_SERVER_WEBHOOKS` | `on` | `off` turns off `POST /v1/webhooks`, release nudges and `POST /hooks/github`. |
| `RELAY_CATALOG_SERVER_WEBHOOK_ALLOW_LOOPBACK` | `off` | `on` also accepts `http://` receivers on loopback addresses. For local development only; private and other refused ranges stay refused. |
| `RELAY_TRUSTED_PROXIES` | empty | Comma-separated IPs or CIDRs of the proxies in front of the server. Their `X-Forwarded-For` names the client the registration limit counts; when empty, the limit counts the connecting peer, so behind a proxy every client shares one limit. |
| `RELAY_LOG_LEVEL` | `info` | `debug` \| `info` \| `warn` \| `error`. Logs are JSON on stdout. |

The mirror defaults to the temp directory because it is a disposable cache: a few MB that clone again in about a second, and the temp directory is writable for any user. Point it at a volume to skip the clone after a container restart.

At every sync the server fetches the mirror, reads each new release tag's channel, fetches the sums it doesn't have yet, and builds and verifies the latest tag of each channel. Missing sums are retried every sync while the tag is less than a day old, hourly after that. Other tags are built on first request. Each channel's latest files stay in memory; other files are kept in a least-recently-used cache within `RELAY_CATALOG_SERVER_CACHE_BYTES` and rebuilt when evicted. At most two builds run at once, and concurrent requests for the same file share one build. When the repository or the release host is unreachable, the server keeps serving what it holds and the index doesn't move.

`/livez` answers `200` while the process runs. `/readyz` answers `200` once the first sync has finished and the index names at least one tag, which means every channel's latest files are verified.

`catalog-server` exits `2` on a usage or configuration error and `1` when the listener or the sync loop fails.

| Metric | Type | Labels | What it answers |
| --- | --- | --- | --- |
| `catalog_server_last_fetch_success_timestamp_seconds` | gauge | | When the mirror last fetched successfully. |
| `catalog_server_fetch_failures_total` | counter | | Failed git fetches. |
| `catalog_server_tags_known` | gauge | | Release tags in the mirror. |
| `catalog_server_tags_ready` | gauge | | Release tags whose two files are verified so far. |
| `catalog_server_builds_total` | counter | `asset` | Files rebuilt from the mirror. `asset` is `catalog` or `data`. |
| `catalog_server_build_failures_total` | counter | `asset` | Rebuilds that failed, such as a schema this server can't compose. |
| `catalog_server_rebuild_mismatch_total` | counter | `asset` | Rebuilds whose sha256 differs from the published sum; the published file is served. |
| `catalog_server_release_fetch_failures_total` | counter | `asset` | Published sums or files that couldn't be fetched or failed their sum. |
| `catalog_server_cache_bytes` | gauge | | Bytes of release files in memory. |
| `catalog_server_webhook_subscriptions` | gauge | `channel` | Live receivers this replica holds. |
| `catalog_server_webhook_registrations_total` | counter | `result` | Registrations: `created`, `renewed`, `invalid`, `refused`, `challenge_failed`, `rate_limited`, `full`. |
| `catalog_server_webhook_nudges_total` | counter | `result` | Nudge requests `delivered` or `failed`, `gave_up` once a receiver's retries for a tag ran out, and `superseded` when a newer tag replaced a pending retry. |
| `catalog_server_github_hooks_total` | counter | | Calls to `POST /hooks/github`. |

### Building a release's files

```bash
catalog-server build --repo ./relay-catalog --ref <commit> --version <tag> --out out
```

From a relay-catalog checkout, with the image (`--user` lets it write `out` into a checkout the container user doesn't own):

```bash
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/src" -w /src ghcr.io/wyolet/catalog-server:<version> \
  catalog-server build --repo . --ref "$(git rev-parse <tag>^{commit})" --version <tag> --out out
```

This writes `relay-catalog-data-<tag>.tar.gz`, `catalog.json.gz` and their `.sha256` files. The data tarball is `git archive` of `data/` without `data/drafts` at the commit. The catalog is composed from that tarball, with the commit's committer time as its `generatedAt`. Both are reproducible from the tag, so comparing the output with a release's published sum files shows whether this build reproduces it. `--repo` defaults to the current directory and may be a bare clone or a checkout; `--ref`, `--version` and `--out` are required.
