The control plane is the admin API behind the dashboard. It listens on
`RELAY_CONTROL_PORT` (separate from the inference port) and serves the admin
UI, CRUD for every catalog entity, auth, and operational endpoints.

<Info>
All control-API routes are mounted under the **`/api`** prefix (e.g.
`GET /api/providers`). The prefix keeps the API from shadowing the embedded
admin UI's client-side routes (`/models`, `/policies`, …), which are served
on the same origin — a hard reload of `/models` must return the UI, not JSON.
Only `/config.json` and `/metrics` stay at the listener root.
</Info>

## Authentication

Two ways to authenticate:

| Caller | Mechanism |
| --- | --- |
| Browser / dashboard | `relay_session` cookie, set by `POST /api/auth/login` |
| Operator / CI | `Authorization: Bearer ${RELAY_ADMIN_TOKEN}` (break-glass) |

```bash
# Break-glass bearer (CI, scripts)
curl -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  http://localhost:8081/api/providers
```

## CRUD surface

Every kind shares one uniform shape:

```
GET    /api/{plural}                 list
GET    /api/{plural}/{ref}           read by slug or id (UUID form prefers id)
POST   /api/{plural}                 create (server stamps id + slug)
PUT    /api/{plural}/by-id/{id}      update
DELETE /api/{plural}/by-id/{id}      delete
```

Plurals: `providers`, `hosts`, `models`, `host-keys`, `rate-limits`,
`policies`, `pricings`, `host-bindings`, `keys`, `teams`, `projects`,
`service-accounts`, `groups`, `roles`, `role-bindings`, `policy-bindings`.

Roles, role bindings, and policy bindings are stored, validated, and
served like every other kind. With `RELAY_AUTHZ=rbac` they are what
decides access: every read is filtered and every write authorized against
the bindings naming the caller, at the scope of the row being touched.
Authoring a role of your own is a licensed feature; the built-in roles
ship with every deployment and are reserved by name.

<Info>
Every write triggers a Postgres `NOTIFY`; the change propagates to every
pod's in-memory snapshot within ~1 second. No manual reload needed for
CRUD operations.
</Info>

## Host keys

A **host key** is your upstream provider credential (e.g. your OpenAI key).
Two value modes:

<CodeGroup>

```json Env-ref (no secret in DB)
{
  "metadata": { "displayName": "My OpenAI key" },
  "spec": {
    "hostId": "<host-id>",
    "policyId": "<host-tier-policy-id>",
    "valueFrom": { "kind": "env", "env": "OPENAI_API_KEY" }
  }
}
```

```json Stored (AES-GCM encrypted in Postgres)
{
  "metadata": { "displayName": "My OpenAI key" },
  "spec": {
    "hostId": "<host-id>",
    "policyId": "<host-tier-policy-id>",
    "valueFrom": { "kind": "stored" },
    "value": "sk-..."
  }
}
```

</CodeGroup>

Stored-mode values are encrypted with `RELAY_MASTER_KEY` and only the
ciphertext is persisted.

## Relay keys

A **key** is the inbound bearer your callers use. It is a credential of a
principal — a service account or a user — so rotating it leaves everything
bound to that principal alone. The server generates the plaintext via
`crypto/rand`, stores only `sha256(plaintext)` + a short display prefix, and
returns the plaintext **once** on create.

`spec.principal` is required; `spec.expiresAt` (RFC3339) is optional and
stops the key authenticating once passed.

```bash
curl -X POST http://localhost:8081/api/keys \
  -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "metadata": { "displayName": "prod key" },
    "spec": {
      "principal": { "kind": "serviceaccount", "id": "<service-account-id>" },
      "policyId": "<policy-id>",
      "expiresAt": "2027-01-01T00:00:00Z"
    }
  }'
```

Response:

```json
{
  "plaintext": "rk_live_...",   // save this now — never retrievable again
  "key": { "metadata": { "id": "..." }, "spec": { "prefix": "rk_live" } }
}
```

<Warning>
The `plaintext` field is returned exactly once. Persist it on receipt — it
cannot be retrieved later, only rotated.
</Warning>

## Tokens

A **token** is a relay-signed, short-lived credential for `/v1/*`, scoped
to one project and minted for the session holder — see
[Authentication](/concepts/auth#inference-tokens).

```
POST   /api/auth/token               mint a token for a project (session auth only)
DELETE /api/auth/token/{jti}         revoke one token by id
POST   /api/auth/token/revoke        revoke the presented token (self-service)
POST   /api/auth/token/revoke-all    bump the caller's token_version, revoking every token they hold
POST   /api/auth/token/keys/rotate   rotate the signing key
POST   /api/users/by-id/{id}/revoke-tokens   bump another user's token_version
```

Revoking by `jti` needs `tokens.revoke` at the scope of the project the token
was minted for, and the user who minted a token may always revoke it. Only the
fallback path — passing `team_id` and `exp` because the mint is no longer in
the audit log — requires an admin caller, since nothing then proves who minted
it. Bumping another user's `token_version` needs `users.update` at the global
scope.

A revoked token fails on the inference plane with `401` and the code
`token_revoked`, whether it was the token's `jti` that landed on the denylist
(revoke by jti or by value) or the user's `token_version` that moved.

```bash
curl -X POST http://localhost:8081/api/auth/token \
  -H "Cookie: relay_session=<session from POST /api/auth/login>" \
  -H "Content-Type: application/json" \
  -d '{"project": "my-project", "ttl": "1h"}'
```

## Users and audit

```
GET  /api/users            list users (id, username, email, roles, disabled — never a password hash)
PUT  /api/users/by-id/{id} edit `disabled` and `roles`; disabling also bumps token_version
GET  /api/audit            the admin audit log; filter by actor_id, actor_name, action,
                            resource_kind, resource_id, scope, status, from, to
```

Both user endpoints authorize at the global scope: an account belongs to the
deployment, so a binding inside one team or project grants neither the list nor
an edit. Disabling an account refuses its next login and invalidates every
inference token it holds (the `token_version` bump), so re-enabling it does not
bring those tokens back. A session already open is not destroyed — log the user
out, or wait for the session to expire.

See [Audit Log](/concepts/audit) for the audit event shape and retention.

## Operational endpoints

```
POST   /api/auth/login           username + password → session cookie
POST   /api/auth/logout          destroy session
GET    /api/auth/whoami          return the authenticated caller
POST   /api/master-key/generate  mint a candidate RELAY_MASTER_KEY
POST   /api/reload               force full snapshot rebuild from Postgres
GET    /api/version              build version (public)
GET    /api/openapi.json         generated typed spec
```

`/reload` is a manual fallback; normal CRUD writes propagate automatically
via `NOTIFY`.
