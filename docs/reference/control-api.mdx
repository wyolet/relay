The control plane listens on `RELAY_CONTROL_PORT` (default `8081`), separate from the inference port. It serves the control API under `/api` and the admin UI on the same origin.

<Info>
API routes are mounted under `/api` (for example `GET /api/providers`) so they do not shadow the admin UI's own routes (`/models`, `/policies`, …): a hard reload of `/models` returns the UI, not JSON. Any path not claimed by the API falls through to the UI, except under `/api`, where an unknown path answers a JSON `404`. Set `RELAY_UI_DISABLE=1` to serve the API without the UI.
</Info>

A few paths sit at the listener root instead:

| Path | Purpose |
| --- | --- |
| `/config.json` | Runtime configuration the admin UI reads before it knows the `/api` prefix. |
| `/metrics` | Prometheus metrics, unauthenticated. See [Metrics](/reference/metrics). |
| `/auth/callback` | OIDC redirect URI. See [SSO](/concepts/sso). |
| `/scim/v2` | SCIM 2.0 endpoint for identity providers. See [SCIM](/concepts/scim). |

The generated OpenAPI document at `GET /api/openapi.json` is the complete, typed list of operations, with request and response schemas; `GET /api/docs` renders it. This page groups the routes and links the page that explains each area.

## Authentication

| Caller | Mechanism |
| --- | --- |
| Browser (admin UI) | `relay_session` cookie, set by `POST /api/auth/login` or the OIDC sign-in |
| Operator, CI, scripts | `Authorization: Bearer $RELAY_ADMIN_TOKEN` |

```bash
curl -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" http://localhost:8081/api/providers
```

Public, with no credentials: `GET /api/version`, `GET /api/healthz`, `GET /api/livez`, `POST /api/auth/login`, the OIDC sign-in routes, `GET /api/schemas/*` and `/config.json`. Every other route requires a session or the admin token and is authorized per action; under `RELAY_AUTHZ=rbac` the caller's role bindings decide. See [Authentication](/concepts/auth).

Control-plane actions are recorded in the [audit log](/concepts/audit), which describes what is recorded.

## Resource CRUD

Every kind shares one shape:

```
GET    /api/{plural}                 list
GET    /api/{plural}/{ref}           read by slug or id (a UUID is tried as an id first)
POST   /api/{plural}                 create; the server assigns id and slug
PUT    /api/{plural}/by-id/{id}      replace
DELETE /api/{plural}/by-id/{id}      delete
```

| Plural | Kind | Concept |
| --- | --- | --- |
| `providers`, `hosts`, `models`, `host-bindings`, `pricings` | Catalog | [Catalog](/concepts/catalog) |
| `host-keys` | Upstream credentials | [Authentication](/concepts/auth), [Key pooling](/concepts/key-pooling) |
| `accounts` | What requests run in and are charged to: team, project, personal, member, service and provider accounts | [Accounts and lanes](/concepts/accounts), [Key pooling](/concepts/key-pooling#accounts) |
| `pools` | Ordered sets of one host's keys | [Key pooling](/concepts/key-pooling) |
| `policies`, `policy-bindings` | Model grants and links to pools, rate limits and budgets; the accounts they govern | [Policies](/concepts/policies) |
| `rate-limits` | Rule sets | [Rate limits](/concepts/rate-limits) |
| `budgets` | Spend caps | [Budgets](/concepts/budgets) |
| `keys` | Relay keys (create through [`POST /api/keys`](#relay-keys)) | [Authentication](/concepts/auth) |
| `teams`, `projects`, `service-accounts`, `groups` | Tenancy | [Authentication](/concepts/auth) |
| `roles`, `role-bindings` | Access control | [Authentication](/concepts/auth) |

List endpoints accept `q` (free text), `sort`, `limit`, `offset`, `label=key=value` (repeatable), and per-kind field filters; an unknown filter answers `400`. The OpenAPI document lists each kind's filters.

Policies, pools, rate limits, budgets, accounts, host keys, relay keys, service accounts and policy bindings also filter by `owner` (the owner's kind) and `owner_id` (repeatable; a row matches any of them). `GET /api/policies?owner_id=<team-id>` lists the policies that team owns; `usable_by` below differs in also listing rows the scope may link but does not own.

A create that leaves out `metadata.owner` makes the row the caller's own: owned by the signed-in user, or by the system for the admin token. Teams and groups are always owned by the system and a role without an owner is too; a project by its `spec.teamId`, a service account by its `spec.projectId`, a role binding by its `spec.scope`, and a relay key by its principal. To create a row in a team or project, set `metadata.owner` to it.

A signed-in user who creates a team or a project gets a role binding of the scope's built-in admin role there (`team-admin`, `project-admin`), and with it a member account. The admin token gets none, and [`apply`](/concepts/gitops) creates only the bindings a bundle declares.

#### Listing what a scope may use

`usable_by` narrows the lists of pools, policies, rate limits, budgets, accounts and host keys to the rows a row owned by one scope may link, by the same rule a save of that row applies. The value is `system`, `organization`, `user:<id>`, `team:<id>` or `project:<id>`; `organization` applies only where the linking row is a policy or a pool, else `400`. It composes with the other filters, and a malformed value answers `400`. The caller must be allowed to create or update the linking row (a policy, a pool or a policy binding) in that scope, else `403`; a team or project that does not exist answers `400`, one the caller may not see `404`.

| List | What `usable_by=<scope>` keeps |
| --- | --- |
| `pools`, `budgets`, `rate-limits` | What a policy owned by the scope may link |
| `host-keys` | What a pool owned by the scope may hold; add `host_id` for the pool's host |
| `policies` | What a policy binding owned by the scope may use, including the pools and host keys the policy links |
| `accounts` | With `usable_for=binding` (the default), what a policy binding owned by the scope may bind. With `usable_for=pool`, what a pool owned by the scope may list: the provider accounts it may draw on and the shares made with that scope; add `host_id` for the pool's host. A host key joins only an account of its own owner: filter with `owner` and `owner_id` |

`usable_for` is accepted on the accounts list only, and only together with `usable_by`.

```bash
curl -H "Cookie: relay_session=<session>" \
  "http://localhost:8081/api/pools?usable_by=project:<project-id>&host_id=<host-id>"
```

`GET /api/me/contexts` lists the scopes the caller may create rows in: their personal scope first, then each team, then each project. Each row is `{kind, id, name, displayName, teamId?, admin}`, with `kind` one of `personal`, `team`, `project`, and `teamId` on projects. A team or project is listed when the caller may create at least one policy, pool, account, host key, budget, rate limit, policy binding, key, service account or role binding there, through any binding: direct, a group's, or one on the project's team. `admin` is true where the caller holds every permission of the scope's built-in admin role. The admin token gets every team and project with `admin: true` and no personal scope.

Every read returns `metadata.resourceVersion`, an opaque string that changes on every write to the row. Send it back unchanged in the PUT body to make the update conditional: if the row changed since you read it, the PUT fails with `409` and the code `stale_resource_version`, and nothing is written. A PUT without `resourceVersion` replaces the row unconditionally.

Every write is applied to each pod's in-memory catalog within about a second; no reload is needed. Edits and deletes of catalog-owned rows are governed by the `governance:*` settings; see [Settings](/reference/settings).

A `DELETE` answers `204`, or `200` with `{"detached": [...]}` when it took links from rows that stay: policies that lose a rate limit or budget, or that keep a deleted pool's id and narrow, and pools that lose a deleted host key. Each entry groups the rows by `kind` and `field`, with `count`, `hidden` (rows you may not see) and `items`. A row still referenced where the link cannot be dropped answers `409` with the code `resource_in_use` and the same groups as `blockers`.

### References and detach

```
GET  /api/{plural}/by-id/{id}/references   rows that reference this one, before a delete
POST /api/{plural}/by-id/{id}/detach       clear every reference to this row the caller may edit; returns what still references it
```

Available for `providers`, `hosts`, `models`, `pricings`, `policies`, `host-keys`, `rate-limits`, `teams`, `projects`, `service-accounts`, `groups`, `roles`, `accounts`, `pools` and `budgets`. For a pool, budget, rate limit or host key, `references` also lists the links a delete would take. Detach deletes nothing.

### Host keys

```
POST /api/host-keys/by-id/{id}/rotate   {"value": "<new value>"}: replace a stored or oauth value
GET  /api/host-keys/by-id/{id}/health   the key's circuit-breaker state
POST /api/host-keys/by-id/{id}/detect-account   ask the key's host which organization the key belongs to
```

Reads carry `status.lastUsedAt`, when Relay last tried an upstream call with the key, to the minute; see [When a key was last used](/concepts/auth#when-a-key-was-last-used).

A PUT cannot change a host key's value; rotation is explicit. An env-referenced key is rotated by changing the variable, and the rotate call answers `400`. See [Key pooling](/concepts/key-pooling) for breaker states and [Stored secrets](/concepts/secret-keys) for how stored values are sealed.

`detect-account` needs the same permission as updating the key and answers `{"orgId", "orgName"?, "currentAccountId", "matchingAccountId"?}`. It does not move the key; see [Detect a key's account](/concepts/key-pooling#detect-a-keys-account). It answers `422` when the host's responses name no organization or the key's value cannot be resolved, and `502` when the host refuses the call (the host's status is in the error details).

### Relay keys

```
POST /api/keys                         create; the plaintext is returned once
POST /api/keys/by-id/{id}/rotate       new plaintext; optional {"graceSeconds": N} keeps the old one valid that long
```

```bash
curl -X POST http://localhost:8081/api/keys \
  -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "metadata": { "displayName": "prod key" },
    "spec": {
      "principal": { "kind": "serviceaccount", "id": "<service-account-id>" },
      "expiresAt": "2027-01-01T00:00:00Z"
    }
  }'
```

```json
{
  "plaintext": "sk-wr-…",
  "key": { "metadata": { "id": "…" }, "spec": { "prefix": "sk-wr-…", "...": "..." } }
}
```

`spec.principal` left out makes the key the signed-in user's; the admin token must name one, or the create answers `400`. Optional fields: `metadata.labels`, `accountId`, `expiresAt`, `enabled`, `passthroughAllowed` ([proxy mode](/concepts/proxy-mode)) and `payloadLoggingEnabled`. `accountId` is the key's default [lane](/concepts/accounts#a-keys-default-lane): left out, the service account's account or the user's personal account; an account the principal may not run keys in answers `403 account_not_held`, and a closed one `400`. A key holds no policy: bind one to its account instead. Relay stores only a hash of the plaintext; save it on receipt, it cannot be read again. A PUT never changes the key's value, hash or principal; it may move the key to another account under the same rules.

Create and rotate answer once the pod that handled them authenticates the new value, waiting up to 5 seconds, so the plaintext can be used at once. `GET /api/keys?account_id=<id>` lists the keys whose default lane is an account. Reads carry `status.lastUsedAt`, when the key last served a request, to the minute; see [When a key was last used](/concepts/auth#when-a-key-was-last-used).

### Policies and policy bindings

A policy's links are ids in the API and names in manifests:

```json
{
  "metadata": { "displayName": "ML team", "owner": { "kind": "team", "id": "<team-id>" } },
  "spec": {
    "models": ["openai"],
    "poolIds": ["<pool-id>"],
    "rateLimits": [{ "rateLimitId": "<rate-limit-id>" }, { "rateLimitId": "<per-person-id>", "shared": false }],
    "budgets": [{ "budgetId": "<budget-id>" }]
  }
}
```

A `rateLimits` entry may add `"models": [...]` to apply only to those models. `shared` on a rate-limit or budget link defaults to `true` (one count for the bound account) and is always returned; `false` counts once per lane under it. `models` is always returned, `[]` when the policy allows every model its pools serve.

A policy binding is owned by the system, a team, a project or a user (`metadata.owner`) and names accounts:

```json
{
  "metadata": { "displayName": "ML team", "owner": { "kind": "team", "id": "<team-id>" } },
  "spec": {
    "policyId": "<policy-id>",
    "accountIds": ["<account id of team-ml>"]
  }
}
```

Find a team's, project's or service account's account with `GET /api/accounts?kind=team&owner_id=<team-id>`, `kind=project&owner_id=<project-id>` or `kind=service&holder_id=<service-account-id>`. List bindings with the `account_id`, `owner` and `owner_id` filters. On save:

| Answer | When |
| --- | --- |
| `400` | A linked row does not exist or lives in a scope the policy may not use; an account does not exist or lies outside the binding owner's scope; the binding uses a policy, or a pool, its owner may not use; a host-owned policy links pools; a policy model names a host. |
| `404` | A linked row exists but you may not see it. |
| `403` `policy_in_use` | An update of a policy, or of a rate limit or budget a policy links, while the policy is applied through an enabled binding to an account whose policy you may not set; `blockedBy` is `{accounts: [{id, name, displayName, kind}], hidden}`. Never for an admin. |
| `409` `duplicate_binding` | An account is already held by another binding. |
| `422` | The body does not match the schema, including a field of an earlier version (`subjects`, `projectId` on a binding; `includeDeprecated`, `credentialIds`, `budgetIds`, `payloadLoggingEnabled` on a policy). |

The rules behind each answer are on [Policies](/concepts/policies#policy-bindings). A scope refusal names the rows by display name and their owners in words, and says what to change, for example:

```
policy "General Policy" uses your personal pool "anthropic"; a policy binding of project "Web" can use pools of the project, its team or the system. Create the pool in the project or its team, or move this one there.
```

```
POST /api/policies/{ref}/duplicate   copy a policy: {"displayName"?, "owner"?}; answers 201 with the copy
```

The copy keeps the spec and links the same pools, rate limits and budgets. It gets a new id, a slug derived from `displayName` (left out, the source's display name followed by ` copy`), the owner you name or else your own user (the system for the admin token), and no bindings or labels. It needs read access to the source and is checked and authorized as `POST /api/policies` of the same row. `GET /api/policies/{ref}` adds `editable` and, while accounts block an update, `editBlockedBy` in the shape of `blockedBy`; the list leaves both out. See [Editing a policy in use](/concepts/policies#editing-a-policy-in-use).

### Accounts and pools

```
GET  /api/pools/{ref}/keys       the pool's host keys in pool order, without values
GET  /api/accounts/{ref}/keys    the host keys that name the account, without values; a shared account's are its real account's, readOnly
POST /api/accounts/{ref}/shares  share a provider account: {"receiver": {"kind": "user|team|project|serviceaccount", "id"}}
GET  /api/accounts/{ref}/shares  its shares, each {sharedAccount: {id, name}, receiver: {kind, id, name}, usage: {requests, costNanos, unpriced}}; since= sets the usage window (default 30d)
PUT  /api/accounts/{ref}/policy  set the account's policy: {"policyId": "<id>"} or {"policyId": null}; answers {binding, previousBindingId?, previousBindingDeleted?}
```

`PUT …/policy` runs in one transaction: it takes the account out of the binding that holds it, deleting that binding if it held no other account, and for a `policyId` creates a binding of its own, owned by the account's owner. It never adds the account to another binding. A holding binding that is enabled and already uses the policy is left as it is. It needs update (or delete) on the old binding and create in the account's scope, and refuses with the answers of a policy-binding save above; a concurrent change answers `409` `conflict` and writes nothing.

A pool's keys and accounts must be at the pool's host, and an account named by a host key must be at that key's host. A shared account is made only by `POST …/shares` (`spec.sourceAccountId` on `POST /api/accounts` answers `400`); a PUT keeps its real account, owner and host. See [Sharing an account](/concepts/key-pooling#sharing-an-account). A host key needs `accountId` on create and on update: create the provider account at the host first (`POST /api/accounts`); a key without one answers `400 account_required`. `spec.groupedByRelay` is read-only and cleared by setting `orgId`; see [Accounts grouped by the upgrade](/concepts/key-pooling#accounts-grouped-by-the-upgrade).

`POST /api/accounts` creates provider accounts only (`spec.hostId` is required). Team, project, personal, member and service accounts are made by Relay; a PUT may change their name, display name and `payloadLogging`, and keeps their owner, holder and kind. Every account carries a read-only `spec.kind`, and `spec.holder` and `spec.closed` where they apply. `spec.holder.name`, and a key's `spec.principal.name`, is the user's username or the service account's display name, filled on reads of a row you can see whether or not you may list users; it is ignored on writes. The list filters by `kind`, `owner_id`, `holder_id` and `closed`. See [Accounts and lanes](/concepts/accounts).

Deleting an account that host keys, relay keys or a policy binding still name, or a host that still has accounts or pools, answers `409`, and so does deleting a team or project that still owns a provider account. Deleting a team, project, personal, service or open member account on its own answers `409` with the code `account_managed`: it goes with the row it stands for. Deleting a team or project that still has rows under it or owned by it answers `409` and lists them as `blockers`.

### Service accounts in one request

```
POST /api/pseudo-agents              a service account, its account, what it may use and its first key, in one transaction
POST /api/pseudo-agents?dryRun=true  the same checks, nothing written; answers 200 with what would be made
```

The route is served only when `RELAY_PSEUDO_KINDS` lists `agents` or is `all`; otherwise the path answers `404` and is absent from the OpenAPI document. `GET /config.json` lists the served kinds in `pseudoKinds`, so a client can fall back to the separate calls below.

```json
{
  "metadata": { "displayName": "CI bot", "labels": { "sa-type": "agent" }, "owner": { "kind": "project", "id": "<project-id>" } },
  "spec": {
    "access": { "accountIds": ["<team-account-id>", "<your-personal-account-id>"], "models": ["openai/gpt-5.5"] },
    "key": { "displayName": "CI bot key", "expiresAt": null }
  }
}
```

`metadata` is the service account's. `metadata.owner` is required, with no default: the project the service account belongs to (the kinds a service account may be owned by). `name` is derived from `displayName` when left out. `spec` takes exactly one of `policyId`, an existing policy to bind the service account's account to, and `access`:

| `access` | What is made after the service account and its account |
| --- | --- |
| `everyCredential: true`, no `models` | Nothing: the account's default reach is the access. |
| `everyCredential: true` with `models` | A policy of those models linking no pool, and its binding to the account. |
| `poolIds`, `accountIds` (one of them required unless `everyCredential`) | For each provider account in `accountIds` the owner does not reach and holds no share of (your personal account, an account of another team), a share with the owner; then one pool per host listing that host's accounts or shares in the order given, a policy of the pools and `models`, and its binding. A share the owner already holds may be listed as it is. `poolIds` names existing pools a policy of the owner may link. |

The policy links the `poolIds` first, in the order given, then the pools made, in the order each host first appears in `accountIds`. A host that takes no key (`spec.noAuth`) is reached through its pool alone: an account there in `accountIds` answers `400`; name that host's pool in `poolIds`. The pools and the policy made are owned by the service account's owner and carry the label `agent-id=<service account id>`. The binding holds the account alone, as `PUT /api/accounts/{ref}/policy` makes it. `spec.key` makes a key of the service account in its account; left out, none is made.

```json
{
  "created": [
    { "kind": "service-account", "id": "…", "name": "ci-bot" },
    { "kind": "account", "id": "…", "name": "sa-ci-bot" },
    { "kind": "account", "id": "…", "name": "alice-openai-for-web" },
    { "kind": "pool", "id": "…", "name": "ci-bot-at-openai" },
    { "kind": "policy", "id": "…", "name": "ci-bot" },
    { "kind": "policy-binding", "id": "…", "name": "ci-bot-sa-ci-bot" },
    { "kind": "key", "id": "…", "name": "ci-bot-key" }
  ],
  "serviceAccount": { "id": "…", "name": "ci-bot" },
  "account": { "id": "…", "name": "sa-ci-bot" },
  "policy": { "id": "…", "name": "ci-bot" },
  "pools": [{ "id": "…", "name": "ci-bot-at-openai" }],
  "shares": [{ "id": "…", "name": "alice-openai-for-web" }],
  "key": { "id": "…", "name": "ci-bot-key", "plaintext": "sk-wr-…" },
  "warnings": []
}
```

`created` lists the rows in write order. `warnings` lists the plan warnings the rows would raise that are not there now, on the rows the request makes (as the row carrying the warning or the row it names), in the shape of the `issues` of a `422` below; for example `model_ref_blocked` on the policy for a model a policy above it excludes. Warnings refuse nothing; the list is `[]` when there are none. A dry run answers `200` with the same body, ids and warnings included (ids are minted before the write) and `plaintext` left out. Each row passes what its own create call passes, with the same answers: the grant for its kind and owner, the row's rules and cross-row checks, and name minting with a `-2` suffix while a name is taken. Each row made is audited as its own create. A repeated request makes a second set.

Nothing is written on any refusal. A refusal of one row carries `pointer`, the JSON pointer of the part of the body it came from:

```json
{ "error": { "type": "invalid_request_error", "message": "authz: forbidden: only an admin of team \"Platform\" shares account \"platform-openai\" of team \"Platform\"; ask one to share it" }, "pointer": "/spec/access/accountIds/1" }
```

Once every row passes, the rows are checked against the plans as a whole, in memory. Errors they would raise that the plans do not have now refuse the request with `422` `plan_issue`; `issues` lists each one with the pointer of the row it is on, or without one for a row that exists already:

```json
{
  "error": { "type": "invalid_request_error", "code": "plan_issue", "message": "the rows pass one by one but together would raise errors in the plans (1, listed in issues); nothing was written" },
  "issues": [{ "code": "pools_serve_nothing", "message": "none of its pools (ci-bot-at-openai) has a usable key at an enabled host; requests under this policy cannot be served", "kind": "policy", "id": "…", "name": "ci-bot", "field": "spec.poolIds", "pointer": "/spec/access" }]
}
```

| Answer | When |
| --- | --- |
| `400` | The body names both or neither of `policyId` and `access`, lists an account or pool twice, lists an account at a host that takes no key, names a pool the owner may not link, or a row breaks a rule of its own create call. |
| `403`, `404` | A row's own grant, or an account or policy you may not see, as its own call answers. |
| `409` `conflict` | Another change touched the same rows at the same time, or took a name the rows need; retry. Also `share_exists`, `already_reachable`, `duplicate_binding` and `managed_by_source` from a row's own call. |
| `422` `plan_issue` | The rows would raise plan errors together; see above. |
| `503` | The plans are not loaded yet, or the check took longer than `RELAY_PLAN_CHECK_TIMEOUT_MS`, waiting for another one included. |

### Access and limits in one request

```
POST /api/pseudo-access               what a team, project or service account may use, stated whole
POST /api/pseudo-limits               a budget or rate limit on a team, project or service account
POST /api/pseudo-access?dryRun=true   the same checks, nothing written; without spec.access, the case and the current policy only
POST /api/pseudo-limits?dryRun=true   the same; without spec.budget and spec.rateLimit, the case and the current policy only
```

The routes are served only when `RELAY_PSEUDO_KINDS` lists `access` or `limits`, or is `all`. Both change the policy over the target's account: a team's or project's own account, or a service account's account (made first when Relay has not made it yet). `spec.target` is `{"kind": "team|project|service-account", "id": "<id>"}`; a slug answers `400`. What happens to the policy is answered in `case`:

| `case` | When | What is written |
| --- | --- | --- |
| `none` | The account is in no binding. | A policy owned by the target's scope, bound to the account alone. |
| `own` | The account is bound alone to a policy of the target's scope that you may update. | That policy, changed in place. |
| `copy` | The policy is bound to other accounts too, is a preset, or is owned elsewhere. | A copy owned by the target's scope, with its models, links, description and labels, changed; the account taken out of its binding and bound to the copy alone, as `PUT /api/accounts/{ref}/policy` does. The original and the other accounts stay as they were. |

A binding or policy holding the account that you may not see or change answers `403` `policy_set_above`, naming the scope that holds it (by name only when you may see that scope) and nothing of the binding or policy. A copy that would carry a pool, rate limit or budget the target's scope may not link answers `400` `links_not_carried` with how many of each kind, unless the request drops them.

```json
{ "spec": { "target": { "kind": "project", "id": "<project-id>" },
            "access": { "accountIds": ["<team-account-id>"], "poolIds": [], "models": ["openai"] } } }
```

`access` takes `everyCredential`, `poolIds`, `accountIds` and `models` with the rules of `POST /api/pseudo-agents`, and states the whole access: the policy's pools become `poolIds`, then one pool per host of `accountIds`; its models become `models`; its rate limits and budgets stay. Pools it makes are owned by the target's scope and labelled `access-for=<account id>`. On a later request, the labelled pool of a host is updated in place while only the policy changed in place links it, and a labelled pool the policy no longer links that nothing else links is deleted. Other pools are only linked or unlinked. A pool link you may not see is kept where it is in the policy's order, in place and in a copy, as an update of the policy keeps the links it holds; the answer counts those in `hiddenPoolsKept` and names none. `everyCredential: true` links no pools of its own; in case `none` without `models` nothing is written and the answer carries `unchanged: true`.

```json
{
  "case": "own",
  "policy": { "id": "…", "name": "two-app" },
  "pools": [{ "id": "…", "name": "two-app-at-openai" }],
  "shares": [],
  "created": [{ "kind": "pool", "id": "…", "name": "two-app-at-openai" }],
  "updated": [{ "kind": "policy", "id": "…", "name": "two-app" }],
  "deleted": [{ "kind": "pool", "id": "…", "name": "two-app-at-anthropic" }],
  "warnings": []
}
```

Lists with nothing in them are left out of the answer, except `warnings`, which both kinds answer as `POST /api/pseudo-agents` does, `[]` included and on the dry run without a change too. Binding the account to a new policy or a copy is the write `PUT /api/accounts/{ref}/policy` makes: the binding made is listed in `created`, and the one the account left in `updated`, or in `deleted` when it held no other account.

`POST /api/pseudo-limits` takes `metadata` (`name`, `displayName`, `description`, `labels`) and exactly one of `spec.budget` and `spec.rateLimit`, each the spec `POST /api/budgets` or `POST /api/rate-limits` takes. The row is owned by the target's scope and linked from the policy beside what it links already. The answer carries `case`, `policy`, `budget` or `rateLimit`, the three row lists, and for a budget `unpricedModels`: the models the target uses now that have no pricing and would answer `unpriced_under_budget` once the budget applies. It is a warning; the request goes through.

`spec.link` sets the fields of the policy's new `budgets` or `rateLimits` entry. `shared` is the entry's `shared`: `true` or omitted counts the limit once for everyone under the target, `false` once for each account under it, each lane with a counter of its own. `models`, with a rate limit only, is the entry's `models`: the limit applies to those models, in the policy model grammar, checked as `PUT /api/policies/by-id/{id}` checks a rate-limit entry's models and stored in canonical form; empty or omitted applies it to every model. A budget entry has no model scope, so `models` with a budget answers `400`, as does a model the policy update would refuse, both with `pointer` `/spec/link/models`. Without `spec.link` the entry is linked as before: shared, over every model. `budget` or `rateLimit` in the answer carries the entry as stored:

```json
{ "rateLimit": { "id": "…", "name": "ci-rpm", "link": { "shared": false, "models": ["openai/gpt-5"] } } }
```

The dry run without a change answers the case and what you may see of the current policy, so a form opens filled; it is absent in case `none`:

```json
{ "case": "copy", "current": { "policy": { "id": "…", "name": "gold" }, "models": [], "linksNoPools": false, "hiddenPools": 1,
  "pools": [{ "id": "…", "name": "gold-openai", "host": { "id": "…", "name": "openai" }, "accounts": [{ "id": "…", "name": "team-openai" }], "hiddenAccounts": 0, "labelled": false }] } }
```

Each row passes what its own create, update or delete call passes, with the same answers and pointers, and is audited as that call; then the result is checked against the plans as for `POST /api/pseudo-agents`, and against what every other account reaches: a change that would alter another account's models or hosts answers `422` `other_accounts_changed`, and one that would leave the target's account refusing every request answers `422` `plan_issue`. A concurrent change to a row the request read answers `409` `conflict`. Nothing is written on any refusal.

### Provider keys in one request

```
POST /api/pseudo-host-keys              a provider key, its account, the account's tier and its shares, in one transaction
POST /api/pseudo-host-keys?dryRun=true  the same checks and the same one read of the host; nothing written, the value not stored
```

The route is served only when `RELAY_PSEUDO_KINDS` lists `host-keys` or is `all`, as for `pseudo-agents` above.

```json
{
  "metadata": { "displayName": "Work key", "owner": { "kind": "user", "id": "<user-id>" } },
  "spec": {
    "hostId": "<host-id>",
    "value": "<the provider key>",
    "account": { "displayName": "Work" },
    "tierPolicyId": "<one of the host's tier presets>",
    "shareWith": [{ "kind": "team", "id": "<team-id>" }]
  }
}
```

`metadata` is the host key's, as `POST /api/host-keys` takes it; its owner owns the account too, and an omitted user id is yours. `spec` takes exactly one of `accountId`, an existing provider account of the owner at the host, and `account`, a new one. It takes exactly one of `value` and `valueFrom` (a host key's own `valueFrom`, such as `{"kind": "env", "env": "VAR"}`), or neither for a host that takes no key (`spec.noAuth`), which then gets no host key. `pricingStrategy` is the host key's. Every reference is an id; a slug answers `400` with its pointer.

Before anything is written, Relay asks the host which organization `value` belongs to, with the read `POST /api/host-keys/by-id/{id}/detect-account` makes, sent only to the host's own base URL. A `401` or `403` to the key refuses the request with `422` `provider_refused_key`. A host that names no organization, or does not answer, refuses nothing; `detection` says which. A detected organization becomes the new account's `orgId`; one that another account of the owner at the host holds refuses the request with `409` `organization_taken`, naming that account in `account`, and an `accountId` holding another organization answers `409` `organization_mismatch`. `valueFrom` is not checked.

Then, in one transaction: the account (when new), its binding to `tierPolicyId` (an existing account is moved to it as `PUT /api/accounts/{ref}/policy` moves it), the host key, and a share of the account with each `shareWith` receiver. A receiver that already holds a share of the account, or reaches it by ownership, gets none and is answered with `existing: true`. `value` is sealed under the owner's scope before the transaction opens, since the secret store writes on a connection of its own, and is removed when the transaction does not commit; if that removal fails, the answer is `500` and says what is left behind.

```json
{
  "created": [
    { "kind": "account", "id": "…", "name": "work" },
    { "kind": "policy-binding", "id": "…", "name": "tier-1-work" },
    { "kind": "host-key", "id": "…", "name": "work-key" },
    { "kind": "account", "id": "…", "name": "work-for-platform" }
  ],
  "account": { "id": "…", "name": "work" },
  "hostKey": { "id": "…", "name": "work-key" },
  "shares": [{ "receiver": { "kind": "team", "id": "…" }, "id": "…", "name": "work-for-platform" }],
  "detection": "detected",
  "detected": { "orgId": "org-…", "orgName": "…" },
  "warnings": []
}
```

`warnings` is as for `pseudo-agents`. Each row passes what its own call passes (`POST /api/accounts`, `PUT /api/accounts/{ref}/policy`, `POST /api/host-keys`, `POST /api/accounts/{ref}/shares`), is audited as it, and the rows are checked against the plans together, as for `pseudo-agents`. The value appears in no answer, log line or audit row.

| Answer | When |
| --- | --- |
| `400` | A reference is not an id; the body names both or neither of `accountId` and `account`, or both `value` and `valueFrom`; a value for a host that takes no key, or none for one that takes keys; `tierPolicyId` is not one of the host's tier presets; `accountId` is not a provider account of the owner at the host; or a row breaks a rule of its own call. |
| `403`, `404` | A row's own grant, or a host, account, policy or receiver you may not see. |
| `409` | `organization_taken`, `organization_mismatch`; `conflict` as above; `share_exists`, `reshare_refused`, `duplicate_binding` from a row's own call. |
| `422` | `provider_refused_key`, with `pointer` `/spec/value`; `plan_issue` as above. |
| `503` | As above. |

### Removing an agent in one request

```
POST /api/pseudo-agent-removals              a service account and what was made for it, deleted in one transaction
POST /api/pseudo-agent-removals?dryRun=true  the same checks, nothing deleted; answers what would be deleted and kept
```

The route is served only when `RELAY_PSEUDO_KINDS` lists `agent-removals` or is `all`, as for `pseudo-agents` above.

```json
{ "spec": { "serviceAccountId": "<service-account-id>", "keep": ["<pool-id>"], "expect": ["<id>", "…"] } }
```

Relay decides what goes, in an order each delete's own call accepts: the service account's keys; its account out of the policy binding holding it, as `PUT /api/accounts/{ref}/policy` with `"policyId": null` takes it out (the binding is deleted when it held only that account, else shrinks); each share the service account holds, revoked as `DELETE /api/accounts/by-id/{id}` revokes it; the service account, which takes its account with it; then each policy, then each pool, labelled `agent-id=<service account id>`, when the service account's scope owns it, you may see and delete it, `keep` does not name it, and no binding or policy left after the earlier deletes uses it, including ones you may not see.

A label is a claim anyone who can make a pool or policy can write, so a labelled row that does not go stays and is listed in `kept` with a `reason`:

| `reason` | When |
| --- | --- |
| `in_use` | A binding or policy the request does not delete uses it, whether you may see it or not. |
| `kept_by_request` | `keep` names it. |
| `not_visible` | The service account's scope owns it, but you may not see it; its `name` is left out. |
| `not_deletable` | It is owned outside the service account's scope, or its delete's grant or governance refuses you. |

A labelled row owned outside the scope that you may not see is neither touched nor listed. `keep` names labelled rows the answer lists; any other id answers `400` with `pointer` `/spec/keep/<i>`.

```json
{
  "deleted": [
    { "kind": "key", "id": "…", "name": "ci-key" },
    { "kind": "policy-binding", "id": "…", "name": "ci-bot-sa-ci-bot" },
    { "kind": "service-account", "id": "…", "name": "ci-bot" },
    { "kind": "account", "id": "…", "name": "sa-ci-bot" },
    { "kind": "policy", "id": "…", "name": "ci-bot" }
  ],
  "kept": [{ "kind": "pool", "id": "…", "name": "ci-bot-at-openai", "reason": "in_use" }],
  "updated": [],
  "warnings": []
}
```

`deleted` lists every row in delete order, with the bindings a revoke left empty after their share and the service account's account after it; `updated` lists a binding the account left that holds other accounts, and the bindings, keys and pools a revoke changed. Both answers are `200`. `expect`, when given, is the ids of a dry run's `deleted`: when the set to delete differs at submit, the request answers `409` `changed` with the current `deleted` and `kept`, and deletes nothing.

Each delete passes the grant, governance and reference check of its own delete call, with the same answer and `pointer` `/spec/serviceAccountId`; a refused delete refuses the request and nothing is deleted. A `409` `resource_in_use` carries the row's `blockers`, such as a role binding naming the service account. Then the result is checked against the plans as for `pseudo-agents`, so a delete that would leave an error on a row that stays answers `422` `plan_issue`, and against what every other account reaches, as for `pseudo-access`. Each row deleted or changed is audited as its own delete call records it. A deleted key stops authenticating once the pod's plans hear the delete, as after `DELETE /api/keys/by-id/{id}`.

| Answer | When |
| --- | --- |
| `400` | `serviceAccountId` or a `keep` entry is not an id, a `keep` entry is listed twice or names no listed labelled row. |
| `403`, `404` | A delete's own grant, or a service account you may not see. |
| `409` | `changed`; `resource_in_use` with `blockers`; `managed_by_source`; `conflict` as above. |
| `422` | `plan_issue` or `other_accounts_changed`, as above. |
| `503` | As above. |

### Accounts and limits

```
GET /api/me/accounts             the signed-in user's accounts, each with its policy and the user's keys in it
GET /api/accounts/{ref}/limits   the rungs a request in the account climbs, with usage against every limit
GET /api/keys/{ref}/limits       the same for the key's default lane
```

`GET /api/me/accounts` answers any signed-in user with their personal account, their member accounts (closed and token-only ones flagged) and the provider accounts they own personally; the admin token gets `[]`. Each row is `{account: {id, name, displayName, closed}, kind, scope: {kind, id, name}, policy?: {id, name}, keys: [{id, name, prefix}], tokenOnly}`. `policy` is omitted when no binding names the account, or when two do.

The limits reads answer the account's caller rungs, outermost first, as the published configuration holds them:

```json
{
  "lane": {"id": "…", "name": "alice-project-search", "kind": "member"},
  "rungs": [
    {"account": {"id": "…", "name": "team-ml", "kind": "team"}, "policy": {"id": "…", "name": "ml"},
     "rateLimits": [{"rateLimitId": "…", "name": "ml-limits", "models": [], "shared": true, "perLane": false,
       "rules": [{"meter": "requests", "strategy": "sliding-window", "amount": 600, "window": 60, "used": 188, "remaining": 412}]}],
     "budgets": [{"budgetId": "…", "name": "ml-monthly", "shared": true, "perLane": false, "amountUsd": "2000",
       "period": "month", "mode": "hard", "spentUsd": "759.5", "remainingUsd": "1240.5"}]},
    {"account": {"id": "…", "name": "project-search", "kind": "project"}, "rateLimits": [], "budgets": []},
    {"account": {"id": "…", "name": "alice-project-search", "kind": "member"}, "rateLimits": [], "budgets": []}
  ],
  "tightest": {"accountId": "…", "kind": "budget", "id": "…", "remaining": 1240.5, "label": "$1240.50 left: team ml-monthly"}
}
```

- `used` and `spentUsd` are read without counting anything. With `shared: true` they are what every lane under that rung's account spent together; with `shared: false`, this lane's own. Under the default hybrid limiter they are the answering pod's view, which may lag other pods by up to one sync interval.
- Read for a team's or project's own account, the answer holds the rungs above and including it. A link with `shared: false` has no single count there, so it is marked `perLane: true` and carries no `used`, `remaining`, `spentUsd` or `remainingUsd`.
- `tightest` is the hard limit with the least left as a share of its cap; alert budgets and `perLane` links are never it. It is omitted when no rung caps anything.
- A provider account answers with no rungs: its own policy caps its host keys upstream.

The account read is open to whoever may read the account and to the user who acts in it; the key read to whoever may read the key and to the user it authenticates as. Anyone else gets `404`. Both answer `503` before the configuration has loaded.

### Reach

```
GET /api/accounts/{ref}/reachable                       what a request in the account may use now
GET /api/catalog/reachable?owner=kind:id&pool=<id>&…&account=<id>   what a draft policy owned there, linking those pools, would reach
GET /api/policies/{ref}/reachable                       the same for a saved policy, with the accounts bound to it
```

All three run the fold and route fill a request runs on the loaded configuration, and answer `{account?, boundAccounts?, refused?, models, excluded, dropped}`. Each of `models` is `{provider, model: {id, name, displayName, labels}, hosts: [{id, name, displayName, snapshots}], via: [{pool?, account?, snapshots}], snapshots: [{name, aliases?, refused?: {code, reason, rung}}], upstream: [{account, sharedAs?, policy?, allowed, reason?, rung?}]}`, with hosts and `via` in failover order. Each host and `via` entry lists in `snapshots` the model's snapshot names whose requests it serves, and a model is in `models` when at least one of its snapshot names reaches a host. The model's `snapshots` list every snapshot name with the declared exact aliases that resolve to it, and `refused` is the refusal a request naming it gets when it reaches no host; each of `excluded` is a model bound at a reached host the lane may not use, `{code, reason, rung, provider, model, hosts, snapshots, upstream}`, where `rung` is `team`, `project`, `lane` or `account` (an upstream tier) and `reason` names the policy, as in `not allowed by team platform's policy platform-default`. `refused` is set instead when the whole ladder refuses, such as a disabled policy or personal accounts turned off. `dropped` lists each pool the policy links, and each account or key a pool lists, that brings the lane nothing: `{pool?, account?, credential?, code, reason}`, with `code` one of `ref_missing`, `link_out_of_scope`, `host_disabled`, `host_mismatch`, `pool_member_unusable`, `held_for_another_lane` (a share held for one service account, which serves only that account's lane), `narrowed_by_rung` or `not_found` (a pool id the caller may not read). A draft is read as the policy of `account` when given, an account inside `owner` (`400` otherwise), else of the owner's own account (a team's or project's account, a user's personal account), under the rungs above it; a system-owned draft read in no account sits alone above system-owned keys. A saved policy is read in each account bound to it, once per distinct ladder, and merged: a model is in `models` when any bound account reaches it, with `accounts` naming them, and in `excluded` only when none does, with one ladder's reason and the `accounts` it is refused for; bound nowhere, it is read in its owner's own account as a draft is. The draft read needs `policies.create` or `policies.update` in `owner` (`403` otherwise); the account read is open as the limits read is; the policy read to whoever may read the policy. Rows the caller may not read are left out.

### Plan issues

```
GET /api/plan-issues?kind=&id=&target=&about=   what Relay found wrong while folding the configuration
```

Each issue is `{code, message, kind, id, name, field, severity, refs: [{kind, id, name}]}`, sorted by kind, name and code. `field` is the spec path the issue is about (`spec.models[2]`, `spec.poolIds[0]`), empty when it is about the row as a whole. `severity` is `error` when the row cannot serve and `warning` when it serves but something is likely wrong. Codes include:

| Code | On | Means |
|---|---|---|
| `ref_missing` | any | a link to a row that does not exist |
| `subject_out_of_scope`, `link_out_of_scope` | policy binding | a binding naming an account outside its owner's scope, or a policy linking a pool its binding's scope may not use |
| `duplicate_binding` | policy binding | an account bound by more than one binding |
| `model_ref_invalid` | policy | a model entry that does not parse |
| `credential_unresolved` | host key | a key whose value cannot be read |
| `shared_account_missing` | account | a shared account whose real account is gone |
| `personal_account_off` | key, account | a relay key running in, a personal or provider account of, or a share of an account of a user whose personal accounts are turned off |
| `unpriced_under_budget` | policy | bindings the policy allows have no enabled pricing while a budget applies |
| `host_disabled` | pool, host key | its host is disabled, so requests are not sent to it |
| `host_disabled_in_use` | host | a disabled host that pools or enabled keys still point at |
| `pool_member_unusable` | pool | a listed key or account adds no usable key (disabled, unresolved, personal accounts off, broken share) |
| `pools_serve_nothing` | policy | none of the linked pools has a usable key at an enabled host |
| `pool_outside_models` | policy | a linked pool's host serves none of the policy's models |
| `model_ref_unreachable` | policy | a model entry served at no host the linked pools reach; an error when no entry is reachable |
| `model_ref_disabled` | policy | a model entry naming a disabled model |
| `model_ref_blocked` | policy | a model entry that a rung above the policy, or an upstream tier, keeps from the accounts bound to it; names the rung and policy (in refs), with a count when only some bound accounts are kept |
| `rate_limit_disabled` | policy | a linked rate limit is disabled and does not apply |
| `rate_limit_scope_outside_models` | policy | a rate-limit link scoped only to models the policy does not allow, so it never counts |
| `model_unservable` | model | an enabled policy grants the model, but no enabled binding at an enabled host serves any of its snapshots; one issue per granting policy, naming it in refs. A model no policy's model list grants gets none |

`kind` filters by the row's kind (`key`, `policy`, `policybinding`, `account`, `pool`, `credential`, `host`, `model`, `ratelimit`, …), and `id` together with `kind` narrows to one row. `target=kind:id` keeps the issues whose refs name that row, and `about=kind:id` the issues on that row or naming it. `about` repeats and matches any of its rows, so a policy page asks for `about=policy:<id>&about=pool:<id>&…` to get its own and its pools' issues in one call. Filters combine.

Issues on rows the caller may not read are left out, and a ref to such a row keeps its kind with an empty id and name. Under `RELAY_AUTHZ=rbac` the route takes a role whose rules include the kind `*`, such as the built-in `admin`.

## Operations

```
GET  /api/version        build version (public; license details only for authenticated callers)
GET  /api/healthz        readiness: process and backends (public)
GET  /api/livez          liveness: process only (public)
POST /api/reload         rebuild the in-memory catalog from Postgres
POST /api/catalog/sync   check for a newer catalog release now and seed it (admin)
POST /api/catalog/prune  judge the detached catalog rows; ?dryRun=false deletes the ones nothing holds (admin)
GET  /api/openapi.json   OpenAPI document
GET  /api/docs           API reference UI
```

`/api/reload` is a fallback; normal writes reach every pod on their own.

`/api/catalog/sync` runs the check a relay with `RELAY_CATALOG_VERSION=latest` makes every `RELAY_CATALOG_POLL_INTERVAL`, and answers when it is done: `{"previous": "v0.2.1", "current": "v0.2.2", "changed": true, "prune": {"pruned": 412, "keptDetached": 3}}`, where `prune` is what the prune the check ran did, after a seed or, with nothing to seed, on rows earlier releases detached. It is absent when no prune ran: the prune is off, no row is detached, or the usage store is not connected yet. It answers `409` on a relay with any other `RELAY_CATALOG_VERSION`, `503` while another pod is seeding the catalog, and `502` when the index or the release could not be read, verified or seeded; the seeded catalog stays as it was. See [Following the latest release](/concepts/catalog#following-the-latest-release).

`/api/catalog/prune` judges every row a catalog release stopped shipping and answers one entry per row: `kind`, `name`, `id`, `detachedAt`, `decision` (`prune` or `keep`) and, for a kept row, `reason` (`edited`, `overlay`, `named by policy <name>`, `referenced by <kind> <name>`, `traffic since <time>`, or `usage unknown: <why>`), with the `pruned` and `keptDetached` counts and the `idle` window used. It is a dry run unless `dryRun=false`, which deletes the rows decided `prune` and records each one in the audit log as a delete. `idle` overrides `RELAY_CATALOG_PRUNE_IDLE` for this call, as a Go duration or a day count (`30d`). A deleting call answers `503` while another pod is seeding the catalog. See [Pruning detached rows](/concepts/catalog#pruning-detached-rows).
