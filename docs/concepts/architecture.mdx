Relay is one binary with two HTTP listeners that share an in-memory view of the catalog. The **inference plane** serves your apps; the **control plane** serves the admin UI and the control API. Postgres is the source of truth and the control plane reads and writes it; the inference plane never queries Postgres while handling a request and routes from the snapshot instead.

## The two planes

<CardGroup cols={2}>
  <Card title="Inference plane" icon="bolt">
    Listens on `RELAY_PORT`. Serves the shape-prefixed routes (`/openai/v1/*`, `/anthropic/v1/*`), the canonical `/v1/*`, the client-profile prefixes, and `/healthz`. Authenticates relay keys and inference tokens. Dispatch is the same code for every vendor; the wire shape comes from the host binding.
  </Card>
  <Card title="Control plane" icon="sliders">
    Listens on `RELAY_CONTROL_PORT`. Serves the admin UI and the control API under `/api` (sign-in, CRUD for every kind, settings, usage, apply/export) plus `/metrics`. Authenticates with a session cookie or the admin bearer token.
  </Card>
</CardGroup>

The separate ports let you expose the inference plane while keeping the control plane on a private network. `RELAY_CONTROL_PORT=off` disables the control listener on a pod.

## The snapshot

Every pod holds an immutable in-memory snapshot of the catalog, credentials, policies and tenancy rows. Routing, authentication and policy resolution read only the snapshot.

1. A control-plane write lands in Postgres.
2. The write fires a `NOTIFY` on a Postgres channel.
3. Each pod's listener receives it, applies the change to a copy of the snapshot, and swaps the copy in. Notifications are debounced over one second.

A change made through the control API reaches every pod in about a second, with no restart and no manual reload. `POST /api/reload` rebuilds the snapshot from Postgres in full if you need it.

## A request, end to end

<Frame caption="The inference request lifecycle: auth, route, draw a key, forward, stream, settle.">
  <img className="block dark:hidden" src="/images/architecture/request-lifecycle.svg" alt="Inference request lifecycle" />
  <img className="hidden dark:block" src="/images/architecture/request-lifecycle-dark.svg" alt="Inference request lifecycle" />
</Frame>

<Steps>
  <Step title="Authenticate">
    A relay key is hashed and looked up in the snapshot; an inference token is verified against the signing key. A miss, a disabled or expired key, or a bad token is a `401`.
  </Step>
  <Step title="Resolve the policy">
    The governing policy comes from the key, the service account, or the project's policy bindings. See [Policies](/concepts/policies#which-policy-governs-a-request).
  </Step>
  <Step title="Route">
    The `model` resolves to a catalog model. Relay walks its enabled host bindings and picks the first one the policy grants whose host has a usable host key in the policy. The binding supplies the wire adapter (`openai`, `openai_responses`, `anthropic` or `gemini`) and the upstream model name.
  </Step>
  <Step title="Reserve and pick a key">
    The policy's rate limit is reserved in one script call to the state backend. A host key is then picked from the policy's keys for the chosen host, skipping keys whose circuit breaker is open, and the key's tier limit is reserved. See [Key pooling](/concepts/key-pooling) and [Rate limits](/concepts/rate-limits).
  </Step>
  <Step title="Forward and stream">
    Relay calls the upstream and streams the response back. When the inbound and upstream shapes match, bytes pass through unchanged; otherwise each request and stream event is translated through Relay's canonical protocol.
  </Step>
  <Step title="Settle">
    When the caller finishes reading the response, a background goroutine commits the observed token counts to the rate limits, records the key's success, and hands the request to the usage, payload and metrics observers. This work never delays the response.
  </Step>
</Steps>

<Info>
Failover happens only before the first response byte, and only across host keys of the chosen host. Relay does not switch to another host at request time, and once bytes flow an upstream error reaches the caller as-is. See [Key pooling](/concepts/key-pooling#failover-happens-before-the-first-byte).
</Info>

## Design choices on the request path

- **No Postgres queries.** Routing, authentication and policy resolution read the snapshot.
- **A small, fixed number of state-backend calls.** The inbound rate-limit reservation and a token's revocation check share one script call; key selection reads each candidate key's breaker record; the key's tier reservation is one more script call; commits after the response are batched.
- **Off-path emits.** Usage events, captured payloads and metrics go through bounded queues that drop on overflow and count the drops, so a slow sink cannot stall a request.
- **Byte-pass when shapes match.** Same-shape requests are copied, not parsed and re-serialized.
- **Horizontal scale.** Shared state lives in Postgres and the state backend, so pods are interchangeable; add pods to add capacity.

To see the time Relay itself adds to a request, watch the `relay_overhead_seconds` histogram, which excludes the upstream call. See [Metrics](/reference/metrics).

## Where state lives

| Store | Holds | Read on the request path? |
| --- | --- | --- |
| **Postgres** | Catalog, host keys, relay keys, policies, rate limits, tenancy, settings, audit log, batch jobs; usage events when that sink is selected | No. Only through the snapshot |
| **In-memory snapshot** | Read-optimized copy of the Postgres rows routing needs | Yes, for every routing and auth decision |
| **State backend** (`RELAY_STATE_BACKEND`: `memory` or `redis`, i.e. Valkey/Redis) | Rate-limit counters, circuit breakers, round-robin and LRU state, host reachability, token revocations, control-plane sessions | Yes. Use `redis` when you run more than one pod, or each pod keeps its own counters |
| **Usage sink** | Usage events: local JSONL file (default), ClickHouse, Postgres, or Valkey. See [Usage](/concepts/usage) | No. Written after the response |
| **Payload store** | Captured request and response bodies, when enabled: file, S3, or ClickHouse. See [Payload logging](/concepts/payload-logging) | No. Written after the response |
| **Batch payload directory** (`RELAY_BATCH_PAYLOAD_DIR`) | Batch item bodies, as local files. See [Batch](/batch) | Only by batch workers |
