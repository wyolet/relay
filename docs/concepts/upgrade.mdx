---
title: "Upgrading to teams, projects, and RBAC"
description: "Restart requirements, behaviour changes, and rollback when upgrading to the release that adds teams and projects"
---

The release that adds Teams, Projects, Roles, and relay-signed inference tokens changes the Postgres schema and how keys are stored. Plan a short downtime window: a fleet mixing the old and new binary is only partly functional (see [Rolling upgrades](#rolling-upgrades)).

## Before you upgrade

Run the latest 0.9.x patch release first. It boots against a schema newer than its own migrations — it logs a warning and skips migrating — instead of failing at startup. That is what lets an older pod restart while the upgrade is in progress, and what lets you start the previous image during a rollback. Earlier 0.9.x releases refuse to boot once the new migrations have run.

## What changed on disk

Migrations `000025`–`000030` add:

| Migration | Adds |
| --- | --- |
| `000025_teams_projects` | `teams`, `projects` tables — the tenancy scope every project-owned row hangs off. Host keys, policies, rate limits, hosts, host bindings, and models created with the admin token (a `user` owner with no id) become system-owned: nobody owns them, and the new code treats a user-owned row as personal. |
| `000026_subjects_keys` | `service_accounts`, `groups`, `group_members`; `relay_keys` gains `principal_sa_id` / `principal_user_id`, so a key is a credential of a principal (a service account or a user) instead of being its own identity. A key owned by a known user keeps that user as its principal; every other key is moved onto a generated service account in a system `legacy` project. |
| `000027_rbac_kinds` | `roles`, `role_bindings`, `policy_bindings` (plus their subject tables) — evaluated when `RELAY_AUTHZ=rbac`. |
| `000028_audit_events` | `audit_events` — the append-only admin audit log. |
| `000029_token_version` | `users.token_version` — bumped to invalidate every inference token a user holds. |
| `000030_batch_attribution` | Attribution columns on `batches` (project, team, principal, credential). |

## Upgrade procedure

1. Take a Postgres backup. The migrations add tables and columns and rewrite existing key and owner rows; rollback is a real down-migration, not a config flip.
2. Stop every pod running the old image — scale the deployment to 0, or use a `Recreate` deployment strategy. The bundled chart's Deployment uses the default rolling update, so scale it down first.
3. Deploy the new image. It runs the migrations on boot and starts serving.

### Rolling upgrades

If you roll pods one at a time, the first new pod migrates the schema while old pods are still serving. Until the last old pod is replaced, creating a key on an old pod fails: the old binary writes a key with no principal, which the new schema rejects. Stopping every old pod first avoids the window.

## What behaves differently afterwards

**Keys without a policy.** A key that had no policy before the upgrade lands in the `legacy` project with no policy bound, and keeps resolving as it did: through the policy-less flow, which the `allowMissingPolicy` field of the `inference` settings section governs under `RELAY_AUTHZ=single` and which `RELAY_AUTHZ=rbac` refuses. Once you add a policy binding to the `legacy` project, its keys follow the same rule as every other project: they resolve a policy through their service account or a binding, or are refused.

**Rate limits.** Rate-limit counters are keyed differently, so every bucket starts empty at the cutover. A bare `tokens` meter now counts input plus output tokens; before the upgrade it summed every token sub-meter, including cache reads, cache writes, and reasoning tokens. To cap those, add rules on the specific meter (`tokens.cache_read`, `tokens.reasoning`, …).

**Multi-user deployments.** `RELAY_MULTI_USER` is read as `RELAY_AUTHZ=rbac`. Under multi-user, any signed-in user could read the usage and request logs of their own keys; under rbac those reads need a RoleBinding that grants them — for example the built-in `developer` role (usage and logs) or `viewer` (usage) on the user's project. Bind those roles before switching users over, or non-admin users see no usage.

## Rolling back

If the new version needs to be backed out:

1. Stop every pod — scale the deployment to 0, or set `RELAY_MIGRATE_ON_BOOT=off` on it first. Every relay runs the pending up-migrations at boot, so a pod that restarts mid-rollback re-applies what you just undid.
2. Run `relay migrate down <target-version>` against the same database, with `RELAY_PG_DSN` set — for example `relay migrate down 24` to return to the schema before this release's migrations. This runs the bundled down-migrations in reverse order down to (not including) the target version; `relay migrate down 0` unwinds all of them. A target above the current schema version is refused rather than run as an upgrade. A key that resolved its policy through its service account or a policy binding gets that policy written onto the key, the only place the older binary reads it from.
3. Deploy the previous image — the 0.9.x patch release from [Before you upgrade](#before-you-upgrade) — and drop `RELAY_MIGRATE_ON_BOOT` again, so the next upgrade migrates on boot.

`migrate down` is for rollback, not a round trip. Upgrading again after a rollback runs the backfill afresh: keys that had no user are moved onto newly generated service accounts, and anything created against the newer schema — teams, projects, roles, bindings, service accounts — is gone.

If a migration fails part-way, the schema is left marked dirty and every later migrate refuses it. Repair the schema by hand (or restore the backup), then record the version it is now at with `relay migrate force <version>`; this clears the flag without running any migration.

<Warning>
`relay migrate down` is destructive — it drops the tables and columns its down-migrations remove, including any teams, projects, roles, bindings, and service accounts created since the upgrade. Take the backup in step 1 before you need this, not after.
</Warning>
