Everything under the control API can also be declared as YAML and applied
from a git repository. `POST /api/apply` runs the same loader
(`app/apply`) that boots the server from `RELAY_CATALOG_DIR` — a seed and
an apply of the same manifest tree converge on the same rows.

## Apply

```bash
relay apply -f manifests/ --dry-run
relay apply -f manifests/
```

A file or a directory of `.yaml` documents is parsed, diffed against the
stored rows, and — unless `--dry-run` — written. Every entry in the plan
gets one of seven actions:

| Action | Meaning |
| --- | --- |
| `create` | No row with this name exists yet. |
| `update` | The row exists and at least one field differs. `changedFields` lists the JSON paths. |
| `unchanged` | The row matches the manifest exactly. Nothing is written. |
| `skip-dirty` | The row was hand-edited through the control API (`meta.Dirty`) and the run is not forcing. Reported as drift; left alone. |
| `delete` | Pruning removed a row absent from the bundle. Only appears with `--prune`. |
| `conflict` | Another writer changed the row between the plan and the write. Nothing is written for it; re-running picks up the change. |
| `forbidden` | The caller may not see the row the document names. Nothing is written for it, and the run reports it by the name the bundle used. |

`--force` overwrites a dirty row with the manifest's version and clears the
dirty flag — apply owns the row again from that point on.

## Running it from CI

Run the dry run first so a pipeline can gate on drift before writing
anything:

```bash
relay apply -f manifests/ --dry-run || exit_code=$?
if [ "$exit_code" = "1" ]; then
  echo "drift detected — see plan above"
  exit 1
fi
relay apply -f manifests/
```

Exit codes:

| Code | Meaning |
| --- | --- |
| `0` | Clean — every entry was `create`, `update`, `unchanged`, or `delete`. |
| `1` | Drift — at least one `skip-dirty` entry and the run did not pass `--force`, at least one `conflict` entry, or at least one `forbidden` entry. |
| `2` | The server rejected the request (4xx/5xx). |

`$RELAY_URL` (default `http://localhost:8081`) names the server;
`$RELAY_ADMIN_TOKEN` or `--token` authenticates. Both can be overridden
per invocation with `--url`.

A `conflict` entry means the row is not applied, so the run exits `1` even
under `--force`: `--force` overrides an operator's edit, not a write that
landed mid-apply. Re-run to converge on the row as it now stands.

## Prune

```bash
relay apply -f manifests/ --prune --selector env=prod,team=platform
```

`--prune` deletes rows that are absent from the bundle, but only rows that
carry **every** label in `--selector` — an unfiltered prune would delete
every user row the manifest happens to omit, so the selector is required.

Pruning draws the same membership line as export (below): teams, groups,
roles, and role-bindings are always prunable (minus built-in roles);
every other kind is prunable only when it's user-, team-, or
project-owned. System-, provider-, and host-owned rows — the catalog's
own data — are never candidates, no matter what labels they carry: a
manifest that omits a catalog-managed provider or host is not asking for
its removal.

## Authorization and partial failure

Every row in the plan is authorized before anything is written. A denied
write fails the whole apply with `403` (or `401` if the caller isn't
authenticated) and nothing is written — authorization is all-or-nothing,
checked up front.

A row the caller may not *see* is different: it is not a write they were
refused, it is a document about a row outside their scope. Those entries come
back as `forbidden`, named as the bundle named them, and the rest of the
bundle still applies. `relay apply` exits `1` on them, so a pipeline applying
a bundle wider than its own scope learns which documents were ignored instead
of reading a clean run.

Writes then run sequentially, one kind at a time, each kind in its own
store transaction. There is no cross-kind transaction: if a write fails
part-way through, the apply returns `500` with the list of entries that
already landed. Re-applying the same bundle converges — the rows that
landed diff as `unchanged`, and the run picks up from where it stopped.

## Export

```bash
relay export -o manifests/relay.yaml
relay export --scope project:<id> --kinds policies,keys
```

`GET /api/export` renders the tenant-owned rows as a manifest bundle in
the same shape `apply` accepts — round-trip the deployment's state without
hand-authoring YAML. Kinds emit in dependency order, each sorted by name for
a stable diff:

```
teams, projects, groups, roles, rate-limits, policies,
host-keys, service-accounts, keys, role-bindings,
policy-bindings, overlays
```

Teams, groups, roles, and role-bindings are exported by **kind**,
regardless of who owns the row — a scope or a grant isn't its author's
property, so provenance can't decide membership for these four (built-in
roles are excluded by name). Every other kind is exported by **owner**:
only rows owned by a user, a team, or a project. Catalog template rows
(system-, provider-, and host-owned — providers, hosts, models, pricing)
are never exported; they come from the catalog, not from a git repo.
Overlays layered on top of those catalog rows *are* exported, since the
overlay itself is user-owned.

A role-binding at global scope (`{kind: system}`) has no team or project
to scope it into, so it only survives an **unscoped** export — `--scope
team:<id>` or `--scope project:<id>` drops it along with every other
row outside that subtree.

Secrets never leave: a `HostKey`'s `value` is always omitted from the
export, regardless of `valueFrom.kind`. A `Key` exports only `keyHash`,
`prefix`, and `expiresAt` — never `previousKeyHash` or `graceUntil` (a
`Key` document also carries `revokedAt`, `enabled`, and the passthrough/
payload-logging flags, none of which are secret).

`--scope team:<id>` or `--scope project:<id>` restricts the export to one
subtree (overlays are skipped in a scoped export — they're keyed by their
target catalog row, not by tenant, so scoping them would mean guessing).
`--kinds` takes a comma-separated list of API plurals. `--format` is
`yaml` (default) or `json`.

## The `$schema` directive

Every document `export` renders is preceded by an editor directive:

```yaml
# yaml-language-server: $schema=http://localhost:8081/api/schemas/v1alpha2/Policy.schema.json
apiVersion: relay.wyolet.dev/v1alpha2
kind: Policy
```

The base is `RELAY_PUBLIC_URL` when the deployment sets one, otherwise the
path is relative (same-origin). `GET /api/schemas/{version}` lists the
kinds available at a schema version; `GET /api/schemas/{version}/{kind}`
serves one. Both are public — an editor resolving the directive has no
session, and a schema describes shape, never data.

## Minting a token

A **token** is a short-lived, project-scoped credential for the inference
API, minted for the session holder — the admin token identifies no user
and cannot mint one. Session auth only:

```bash
curl -X POST http://localhost:8081/api/auth/token \
  -H "Cookie: relay_session=<session from POST /api/auth/login>" \
  -H "Content-Type: application/json" \
  -d '{"project": "my-project", "ttl": "1h"}'
```

```json
{
  "token": "eyJhbGciOi...",
  "jti": "...",
  "expiresAt": "2027-01-01T01:00:00Z",
  "project": "my-project",
  "teamId": "..."
}
```

Or via the CLI, which logs in and mints in one step:

```bash
export RELAY_PASSWORD=...   # never pass a password on argv
relay token mint --project my-project --ttl 1h --user alice
```

`relay token` reads the password from `$RELAY_PASSWORD`, or prompts on an
interactive terminal — there is no `--password` flag, since argv is
world-readable through the process table and lands in shell history. It
prints the token to stdout on success.

## Other commands

```bash
relay keygen [--prefix]
```

`keygen` mints a key locally, so the plaintext never has to pass through
the server and only the hash goes in a manifest.
