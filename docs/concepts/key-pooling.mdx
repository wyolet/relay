A provider API key has its own failures, and the provider counts its limits per organization, not per key. Relay groups host keys into **pools** that a policy draws from, groups them by provider **account** so limits count where the provider counts them, and takes a failing key out of rotation with a per-key circuit breaker.

## Pools

A **pool** is an ordered set of host keys at one host, with the algorithm that picks among them:

| Field (API) | Field (manifest) | Meaning |
| --- | --- | --- |
| `hostId` | `host` (name) | The host every key in the pool authenticates to. |
| `accountIds` | `accounts` (names) | Provider [accounts](#accounts) the pool draws on whole: each brings every host key it holds, including keys added later, and a [shared account](#sharing-an-account) brings its real account's keys. An account at another host is refused on save. May be empty. |
| `credentialIds` | `credentials` (names) | The host keys, in order. A key at another host is refused on save. May be empty. |
| `selection` | `selection` | `prioritized` (default), `round-robin` or `least-recently-used`. |

A caller [policy](/concepts/policies) links pools in `pools`, in the order they are tried. Many policies may link one pool and draw on it first come, first served: nothing in a pool is reserved for one of them, and to keep one caller from using all of it, cap each caller with its own [rate limits](/concepts/rate-limits) or [budgets](/concepts/budgets). To give a policy a single host key, make a pool of that one key.

Host keys, pools, accounts and budgets may be owned by the system, a team, a project or a user. Your callers never see which key served them.

### Picking a key

| Selection | Behavior |
| --- | --- |
| `prioritized` | The first healthy key in pool order: the keys of `accountIds` first, account by account and each account's keys in the order they were created, then `credentialIds`. A key listed directly and through its account keeps its first place. Later keys take traffic only when earlier ones are unhealthy or over a limit. |
| `round-robin` | Rotates across healthy keys using a counter in the state backend, one per pool, shared by every policy that links the pool. |
| `least-recently-used` | Picks the healthy key whose last use is oldest. |

Breaker state is shared across pods through the state backend (Dragonfly when `RELAY_STATE_BACKEND=redis`). Every change to a key's breaker is one atomic script, so pods recording failures on the same key add to one count.

After picking a key, Relay reserves the key's upstream limits: the rate limits and budgets of the policy bound to its account. A key over one of them is skipped without touching its breaker, and the next key is tried. When the refusing limit is an account-wide request or token window (no model scope), every key of that account is skipped on this pod until the limit's retry time. See [Rate limits](/concepts/rate-limits#upstream-rungs).

### Keyless hosts

A host marked `noAuth` (a self-hosted Ollama, for example) needs no host key: Relay uses a built-in anonymous credential that sends no auth header and is never taken out by a breaker. Because no key gates it, a keyless host is reached only through a pool at that host linked by a caller policy; the pool may list no keys. Model wildcards and the ownership reach never cover it.

## Accounts

A **provider account** is one provider organization at one host. A host key names its account in `accountId` (`account` in manifests), which must be at the key's host. Accounts of other kinds stand for teams, projects, users and service accounts on the caller side; see [Accounts and lanes](/concepts/accounts).

| Field (API) | Field (manifest) | Meaning |
| --- | --- | --- |
| `hostId` | `host` (name) | The host the organization is held at. |
| `orgId` | `orgId` | The provider's organization id. Optional and informational. |
| `default` | `default` | Marks the owner's default account at the host. See [Default accounts](#default-accounts). |
| `sourceAccountId` (read-only) | `sourceAccount` (name) | On a [shared account](#sharing-an-account): the real account whose keys it reaches. |
| `holder` (read-only) | `serviceAccount` (name) | On a share with a service account: that service account, the only lane that draws on it. |

An account is the organization, not a person: one login can belong to several organizations with separate limits, and each is its own account. Keys of one account share its capacity. Adding a second key to an account gives failover on key-level failures and lets you rotate without downtime (add the new key, then revoke the old one); it does not add throughput.

That is why tier limits belong on the account. Bind a [tier preset](/concepts/policies#tier-presets), or a tier policy of your own, to the account, and its rate limits count once across every key of the account and every caller that reaches them.

Two cooldowns skip a whole account. Both live in each pod and are learned from that pod's own requests:

- **An account-wide limit refuses.** When the account's own request or token window is spent, the account is skipped for every model until the window has room.
- **The provider answers `429`.** A `429` from a key of an account you created cools the account for the requested model only, since providers limit each model separately within an organization. The cooldown lasts for the response's `Retry-After`, 5 seconds when it has none, and at most 60 seconds; after it, one request learns whether the limit still holds. The key's breaker is not written. A key in its owner's default account, or with no account, has no `429` cooldown on the account: the `429` goes to the key's breaker as in the table below, and the request fails over to the next key.

When every key of the route is over a limit or cooling, the request fails with `429 rate_limit_exceeded` and a `Retry-After` for the first one that frees up.

Deleting an account that host keys, relay keys or a policy binding still name is refused with `409`. Read an account's keys with `GET /api/accounts/{ref}/keys` and a pool's with `GET /api/pools/{ref}/keys`.

A user may also run requests directly in a provider account they own personally, as a [lane](/concepts/accounts#lanes): such a request reaches only that account's host keys, under the account's own policy.

### Sharing an account

To let a user, team, project or service account use a provider account without giving them its keys, share it:

```bash
curl -X POST -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" -H 'Content-Type: application/json' \
  -d '{"receiver": {"kind": "team", "id": "<team id>"}}' \
  http://localhost:8081/api/accounts/anthropic/shares
```

The receiver gets a provider account of its own (`anthropic-for-platform`) whose `spec.sourceAccountId` names the real account and `spec.sharedBy` its owner. It holds no host keys and never shows a secret: it reaches every key of the real account, including keys added later and rotated values, and `GET /api/accounts/{ref}/keys` lists them read-only. A host key cannot be added to it (`409 account_shared`).

- **Who shares.** The real account's owner: its user for a personal account, an admin of its team or project, or an admin for a system account. A shared account is not shared on (`409 reshare_refused`), and one account is shared with one receiver once (`409 share_exists`).
- **Who reaches it.** The receiver's lanes reach it as they reach the receiver's own keys: a user's personal lane, the member lanes of a team or project, and, for a service account, only that service account's lane (its share is owned by its project and held by it). A pool of the receiving scope may list it in `accountIds`.
- **Limits.** Requests through it count on the real account's tier, one ceiling for the owner and every share. A policy bound to the shared account only narrows: its rate limits and budgets count on the share, in the same store call as the tier.
- **Usage.** Rows keep `account_id` on the real account and add `via_account_id`. `GET /api/accounts/{ref}/shares?since=30d` lists the real account's shares with each receiver and the requests and cost it drew.
- **Removing it.** Delete the shared account like any account, as the real account's owner or as an admin of the receiving scope; the answer lists the pools that lose it. Deleting the real account is refused while shares exist; `POST /api/accounts/by-id/{id}/detach` deletes them first. A share whose real account is gone serves nothing and shows the plan issue `shared_account_missing`.

In a manifest, a shared account names its real account by name and repeats its host:

```yaml
apiVersion: relay.wyolet.dev/v1alpha3
kind: Account
metadata: {name: anthropic-for-indexer, owner: {kind: project, name: ml-search}}
spec: {host: anthropic, sourceAccount: anthropic, serviceAccount: search-indexer}
```

### Default accounts

A host key saved without `accountId` joins its owner's default account at its host, so keys of one owner at one host share their account rung unless you split them. Relay creates the default account with the first such key, owned like the key and named after the host (`openai`, then `openai-2`, … when the name is taken). A key created with the admin token is system-owned and joins the system's default account.

Each owner has at most one default account per host; marking a second one `default` answers `409`. To group keys by real provider organizations instead, create the accounts and name one on each key.

A default account groups keys by owner, not by provider organization, so Relay does not assume its keys share capacity: a provider `429` on one of them goes to that key's breaker and the request fails over to the next key, so independent keys pooled at one host keep failing over for each other. Limits bound to a default account still count across all of its keys. To have a `429` cool every key of one provider organization for the model, put those keys into an account you create.

A default account no host key names never blocks a delete: deleting its host, its team or its project takes it along. One that keys still name blocks like any other account.

## Circuit breakers

Each key has its own breaker, keyed by a hash of the key's value. The upstream response decides what happens:

| Upstream result | Breaker | Cooldown |
| --- | --- | --- |
| `401` | Opens | 30 s, then 1 min, 5 min, 15 min, and 1 h for every further failure |
| `403` | Opens | 1 s, doubling per repeated failure up to 60 s |
| `5xx`, or a network error after the connection was made | Opens after 5 such errors within 30 s with no success between them | 1 s, doubling per repeated failure up to 60 s |
| `429` from a key in an account you created | Unchanged | The account cools for the model, see [Accounts](#accounts) |
| `429` with `Retry-After` of 5 s or less, from a key in a default account or with no account | Stays closed | None; the request moves to the next key |
| `429` with `Retry-After` over 5 s, from a key in a default account or with no account | Opens | The `Retry-After` duration |
| Connection could not be established (refused, DNS, TLS) | Unchanged | None; this is a host problem, see below |
| The caller disconnected or cancelled during the call | Unchanged | None; the request stops without trying another key |

A single `5xx` does not take a key out: providers return a few percent of them on healthy keys, and the request already moves to the next key. `RELAY_KEY_BREAKER_THRESHOLD` and `RELAY_KEY_BREAKER_WINDOW_S` set the count and the window. Failures of requests that were already in flight when the key opened do not move it further up the ladder.

An open key is skipped during selection. When its cooldown ends, one request probes it while the others keep skipping it; if the probe's outcome has not come back within 10 seconds (a long stream, say), the next request probes too. A successful probe closes the breaker one backoff step down, and each further success takes another step off; a failed probe moves it one step up. The step counter is shared by all failure classes. No failure takes a key out for good, since the request that caused a `401` or `403` may have been the caller's doing.

<Info>
Because breakers are keyed by value hash, rotating a key to a new value gives it a fresh, closed breaker. The old record expires on its own.
</Info>

When the host cannot be reached at all, the key is not blamed: Relay re-dials the same host up to three times with a short backoff, then moves to the next pool, or returns `502 upstream_unreachable` when none is left. Every key on that host shares the same base URL, so switching keys would not help.

## Failover

A route is the caller's pools, in order, that are at a host serving the model. A request tries at most three host keys in total. If the upstream answers with a retryable failure (`401`, `403`, `429`, `5xx`, or a network error) before any response bytes reach the caller, Relay records the failure and moves to the next healthy key in the pool, and to the next pool once the pool has none left or its host is unreachable. That is how a policy that links pools on two hosts fails over from one to the other. Only pools whose binding speaks the same wire shape as the first one are tried, since the request body is built once.

Once bytes start flowing back, the request is committed and there is no mid-stream failover. When the attempts run out, the caller gets the last upstream response with its status and body; when no healthy key is left to try, the caller gets a `502` with `no healthy keys in pool`.

## Recovery after a `401`

A `401` can mean the value Relay holds is stale, for example after a stored key was rotated on another pod. Relay re-reads the key's value from its source (the encrypted value in Postgres, or the environment variable) before giving up:

- **Other healthy keys remain:** the request fails over at once, and the re-read runs in the background so the key rejoins the pool if its value changed.
- **It was the last candidate:** the request waits for one re-read and retries the same key if the value changed.
- **The value is unchanged:** the key is treated as revoked, the caller gets the upstream error, and the key is probed again after each cooldown.

## Detect a key's account

Keys of one provider organization share that organization's rate limits, so they belong in one account. To find out which organization a key belongs to, ask its host:

```bash
curl -X POST -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  http://localhost:8081/api/host-keys/by-id/<id>/detect-account
```

Relay makes one models-list request to the key's host with that key and reads the organization id from the response header: `openai-organization` on OpenAI, `anthropic-organization-id` on Anthropic. Hosts that send no such header (Gemini, most OpenAI-compatible hosts) answer `422`; a key the host refuses answers `502` with the host's status.

```json
{ "orgId": "org-abc123", "currentAccountId": "<account id>", "matchingAccountId": "<account id>" }
```

`matchingAccountId` is the account of the key's owner at the same host whose `orgId` is the detected one; it is absent when there is none. The call never moves the key. To move it, update the key with `spec.accountId` set to that account, or create an account with the detected `orgId` first.

When the key's current account has no `orgId` and no other account of the owner at the host claims the organization, Relay fills it in, but only after asking every other key of that account (up to 8) and getting the same organization from each. The answer then names the current account as the match.

Relay also reads the same header on live responses and remembers, per pod, the organization each key last named. When two keys of one account name different organizations, it logs a warning naming both keys and counts [`relay_account_org_mismatch_total`](/reference/metrics). It never moves a key on its own.

## Inspecting and recovering keys

Read a key's breaker state:

```bash
curl -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  http://localhost:8081/api/host-keys/by-id/<id>/health
```

The response gives `state` (`closed`, `open`, `half_open`, or `unknown` when the key's value cannot be resolved), `reason` (`upstream_auth_failed`, `upstream_forbidden`, `upstream_rate_limited`, `upstream_server_error`, `upstream_network_error`), `open_until` and `cooldown_remaining_seconds`. The `relay_provider_keys_down_total` metric counts breaker openings by reason.

If every key in the pool is open, requests fail with `502` and the message `no healthy keys in pool`. That almost always points at a real upstream problem: a revoked credential, an exhausted quota, an outage. To recover:

1. Fix the cause, for example by giving the key a new value or adding another key to the pool. A stored key is rotated with `POST /api/host-keys/by-id/<id>/rotate` and body `{"value": "<new value>"}`; an env-ref key takes the new value from its environment variable after a restart. Either way the new value gets a closed breaker.
2. Otherwise wait out the cooldown: at most 60 s for `403`, `5xx` and network failures, at most 1 h for `401`.
3. To clear all breaker state immediately: with `RELAY_STATE_BACKEND=memory`, restart the pods; with Dragonfly, delete the `secret_health:*` keys.

See [Troubleshooting](/troubleshooting) for related errors.
