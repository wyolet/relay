---
title: "Proxy Mode"
description: "Forward requests with the caller's own upstream key, without the key pool"
---

In normal mode Relay picks a host key from a pool for each request. In **proxy mode** the caller sends its **own upstream credential**, and Relay forwards the request body unchanged to the host with that credential attached. Relay still authenticates the relay key, applies the caller's model grants, rate limits and budgets, and records usage, cost and (if enabled) payloads.

Use it when the credential belongs to the caller, for example a developer's own provider subscription, but you still want one endpoint, rate limits and usage records in front of the traffic. [Claude Code](/claude-code) uses it this way.

## Normal mode vs proxy mode

| | Normal mode | Proxy mode |
| --- | --- | --- |
| Upstream credential | A host key from the caller's pools | The caller's `Authorization` header, forwarded as-is |
| Host selection | The caller's pools, in order, at hosts serving the model | The `X-WR-Upstream-Host` header, or the first host binding the caller's grants allow when the header is absent |
| Request body | Model name rewritten; translated across shapes when needed | Forwarded byte for byte, no translation |
| Key pooling and failover | Yes | No. One attempt |
| Policy ladder | Every rung | The caller rungs and the host rung, for authenticated requests. No account rung, since no host key serves |
| Usage, cost, payload capture | Yes | Yes |

## Enabling it

Proxy mode is off by default. Turn it on through the control API:

```bash
curl -X PUT http://localhost:8081/api/settings/proxy-mode \
  -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"enabled": true, "allowUnauthenticated": false}'
```

| Setting | Default | Effect |
| --- | --- | --- |
| `enabled` | `false` | Global switch. While `false`, every proxy request returns `403 proxy_disabled`. |
| `allowUnauthenticated` | `false` | Allows proxy requests that carry no relay key. |

The change reaches every pod within about a second.

### Allowing a relay key to proxy

An authenticated proxy request also needs a relay key with `spec.passthroughAllowed: true`; any other credential gets `403 passthrough_forbidden`. Inference tokens never carry the flag, so they cannot be used for proxy mode. Set the flag when you create the key:

```bash
curl -X POST http://localhost:8081/api/keys \
  -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "metadata": {"displayName": "alice laptop"},
    "spec": {
      "principal": {"kind": "user", "id": "<user-id>"},
      "passthroughAllowed": true
    }
  }'
```

For an existing key, read it with `GET /api/keys/{ref}`, set `spec.passthroughAllowed` to `true`, and send the object back with `PUT /api/keys/by-id/{id}`. In a manifest the field is `spec.passthroughAllowed` on the `Key` document.

## Making a proxy request

Send `X-WR-Proxy-Mode: Proxy`, put your relay key in `X-WR-API-Key`, put your upstream credential in `Authorization`, and name the host in `X-WR-Upstream-Host`:

```bash
curl http://localhost:8080/openai/v1/chat/completions \
  -H "X-WR-Proxy-Mode: Proxy" \
  -H "X-WR-API-Key: <your-relay-key>" \
  -H "X-WR-Upstream-Host: openai" \
  -H "Authorization: Bearer sk-your-own-openai-key" \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"hello"}]}'
```

Relay removes its own headers (`X-WR-*`) and hop-by-hop headers, sets `Authorization` to the value you sent, and posts the body to the host's endpoint for that shape. In proxy mode the relay key is read only from `X-WR-API-Key`, because `Authorization` carries the upstream credential. Send the body in the shape the target host expects, since nothing is translated.

### Authenticated requests

With a relay key:

- **Host.** If `X-WR-Upstream-Host` is set, Relay forwards to that host. If it is absent, Relay reads `model` from the body and picks the first of the model's host bindings that the caller's rungs and the host's rung allow, without requiring a host key.
- **Grants.** A pinned request reaches only a model the caller's rungs allow on the pinned host, as normal routing does, and its usage is priced from that binding. The caller's own credential does not widen the grant. A model that is not in the catalog or does not route there is refused with the same errors as normal mode (`model_not_found`, `model_not_allowed`), and an `@host` in the model that names a different host than `X-WR-Upstream-Host` gets `400 upstream_host_conflict`. A keyless (`noAuth`) host such as a self-hosted Ollama is reachable only when one of the caller's pools is at that host. An unpriced binding is refused with `unpriced_under_budget` while a budget applies.
- **Limits.** The caller rungs' rate limits and budgets, and the host rung's, are reserved and committed as in normal mode. The `inference-api-proxy` rate limit is applied on top as a per-credential ceiling. It ships disabled with no rules; add rules and enable it to cap every relay key's proxy traffic.
- **Attribution.** The request is recorded against the relay key, its principal, project and innermost caller policy.

### Anonymous requests

Without a relay key, a proxy request is allowed only when `allowUnauthenticated` is on. `X-WR-Upstream-Host` is then required, and the request is rate-limited per client IP by the `inference-api-proxy-anonymous` rate limit, which ships enabled at 60 requests and 5,000 tokens per minute and 10 concurrent requests per IP. Keyless hosts cannot be reached anonymously. See [client IP](/reference/headers#client-ip-and-trusted-proxies) for how Relay finds the caller's address behind a load balancer.

Both system rate limits are created on boot when missing and never overwritten once they exist. Change them with `PUT /api/rate-limits/by-id/{id}`; set `enabled: false` to remove a limit. A deleted one is recreated as shipped on the next boot. See [Rate limits](/concepts/rate-limits#system-rate-limits).

## Discovering upstream hosts

List the host slugs you can pass in `X-WR-Upstream-Host`:

```bash
curl http://localhost:8080/v1/proxy/hosts \
  -H "X-WR-API-Key: <your-relay-key>"
```

Keyless hosts appear only when one of the caller's pools is at that host.

## Errors

| Status | Code | Meaning |
| --- | --- | --- |
| `400` | `bad_request` | `X-WR-Proxy-Mode` has a value other than `Proxy` or `No-Proxy`, or `Authorization` is missing. |
| `400` | `unknown_upstream_host` | `X-WR-Upstream-Host` names no host, or a keyless host none of the caller's pools is at. |
| `400` | `missing_upstream_host` | Anonymous request without `X-WR-Upstream-Host`. |
| `400` | `upstream_host_conflict` | The model's `@host` names a different host than `X-WR-Upstream-Host`. |
| `403`, `404` | `model_not_allowed`, `model_not_found` | A model a rung does not allow on that host, or one that is not in the catalog. |
| `401` | `unauthenticated` | Anonymous request while `allowUnauthenticated` is off, or an unknown relay key. |
| `403` | `proxy_disabled` | Proxy mode is off. |
| `403` | `passthrough_forbidden` | The relay key lacks `passthroughAllowed`, or the credential is an inference token. |
| `403` | `policy_disabled`, `subject_disabled`, `duplicate_binding`, `unpriced_under_budget` | A [policy refusal](/reference/inference-api#policy-refusals) on a caller rung or the host rung. |
| `429` | `rate_limit_exceeded`, `budget_exceeded` | Over a rate limit or budget on the caller or host rung, or a proxy rate limit. `Retry-After` gives the wait in seconds. |

An upstream error is returned as the upstream sent it.
