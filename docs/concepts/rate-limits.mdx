A **rate limit** is a named list of rules. Each rule caps one meter over one window, and each rule keeps its own counter: a request is admitted only when every rule of every rate limit that applies to it has room. A policy links rate limits, and the rung the policy is bound on decides who shares the counters. Rate limits are enforced by Relay before the request leaves for the upstream, with counters in the state backend.

## Rules

A rule has four fields, all required:

| Field | Meaning |
| --- | --- |
| `meter` | What is counted. See [Meters](#meters). |
| `amount` | The cap, greater than zero. |
| `window` | The period. The control API takes an integer number of seconds (`60`); manifests take a duration string (`1m`, `5h`). |
| `strategy` | How the window is enforced. See [Strategies](#strategies). |

A rate limit with `enabled: false` applies no rules. An enabled rate limit needs at least one rule.

A rule's counter is identified by its `meter`, `strategy` and `window`, so two rules of one rate limit cannot share all three. Changing a rule's `amount` or moving it in the list keeps its counter; changing its `meter`, `strategy` or `window` starts a new one from zero. Renaming a policy or a rate limit keeps its counters.

<Warning>
In a manifest, write `window` as a duration string. A bare integer there is read as nanoseconds, not seconds.
</Warning>

A rate limit is owned by the system, a team, a project, a user, or (for the catalog's tier limits) a provider or a host. A team's rate limits can be linked by the team's policies and its projects' policies.

### Meters

| Meter | Counts |
| --- | --- |
| `requests` | Requests, counted when the request is admitted. |
| `concurrency` | Requests in flight. The slot is held until the response ends, including the full length of a stream. |
| `tokens` | Input plus output tokens. |
| `tokens.input` | Input tokens. |
| `tokens.output` | Output tokens. |
| `tokens.cache_read` | Prompt-cache read tokens. |
| `tokens.cache_creation` | Prompt-cache write tokens. |
| `tokens.reasoning` | Reasoning tokens. |
| `tokens.server_tool_use_input` | Input tokens of server-side tool use. |
| `tokens.server_tool_use_output` | Output tokens of server-side tool use. |

Token counts come from the provider's response. Relay does not tokenize requests itself. Spend in dollars is capped by [budgets](/concepts/budgets), not by a meter.

### Strategies

The strategy applies to the `requests` meter:

| Strategy | Behavior |
| --- | --- |
| `token-bucket` | Capacity refills continuously at `amount` per `window`; bursts up to `amount`. |
| `sliding-window` | Weighted count across the current and previous window, so the cap holds at any point, not only at window edges. |
| `fixed-window` | The count resets at each window boundary. |
| `leaky-bucket` | Drains at a constant `amount` per `window`; requests that would overflow are rejected. |
| `session-window` | The window starts with the first request and runs for `window`; the next request after it ends starts a new one. Use it for session quotas such as "N requests per 5 hours from first use". |

Two meters ignore the strategy:

- **Token meters** are always enforced as a sliding window, because tokens are only known after the response. A request is admitted while the window's counted tokens are at or under `amount`, so the request that crosses the cap still completes; the next one is refused until the window moves on.
- **`concurrency`** is a gauge: the request is refused when `amount` requests are already in flight.

## Where rate limits apply

A [policy](/concepts/policies) lists rate limits in `rateLimits`. Each entry names one rate limit and, optionally, the models it covers:

```yaml
rateLimits:
  - ref: ml-requests             # every request under the policy
  - ref: ml-gpt-5-5-tokens       # only requests for these models; upstream rungs only
    models: [openai/gpt-5-5]
```

`models` takes the same references as a policy's [model grant](/concepts/policies#granting-models). One rate limit may be linked more than once with different `models`; linking it twice over the same models is refused on save. A disabled rate limit, or one the policy can no longer find, applies nothing.

An entry with `models` counts per model, which only the upstream rungs do, so a policy with one can be bound only to a host, an account or a host key. Binding it to a team, project, user or service account is refused with `400`, and so is adding `models` to an entry of a policy already bound to one.

Every rate limit on every rung of the ladder applies to a request. Who shares a counter depends on the side of the ladder the policy is bound on.

### Caller rungs

On the team, project and principal rungs, a counter belongs to one rule, one policy and one bound subject:

- A policy bound to a team gives the whole team one counter per rule, shared by its projects, service accounts and members' tokens.
- A policy bound to a project, or to a principal, counts for that project or principal alone.
- One policy bound to two subjects gives each its own counters. Binding a subject to another policy starts fresh ones.
- A user bound by a project-owned binding is counted per project, so the same policy bound by two projects never shares a counter.
- Every entry covers the whole policy: a caller policy's entries carry no `models`.

To cap one relay key on its own, give it a service account of its own and bind a policy to that service account.

The caller's counters are reserved once per request, before the first upstream attempt, so failing over between host keys or pools does not charge them again. A caller counter that has no room ends the request with `429`.

### Upstream rungs

On the host, account and credential rungs, a counter belongs to one rule and the rung's subject, and is shared by every caller that reaches it, across teams. It models a limit the provider enforces, so:

- A rate limit on an account's tier policy counts once across every host key of the account.
- An entry with `models` keeps a separate counter for each model it matches, as providers limit each model separately. A rule that two entries reach for one model counts once.
- The policy is not part of the counter. Binding the account to another tier policy that links the same rate limit keeps the count.

Upstream counters are reserved per attempt, after a host key is picked. A key over an upstream limit is skipped without touching its breaker and the next key is tried; a skipped key does not count toward the three keys a request tries upstream. An account-wide request or token window that refuses also cools the whole account on this pod until it has room. See [Accounts](/concepts/key-pooling#accounts). If every key is over its limits, the request fails with `429 rate_limit_exceeded`, and `Retry-After` says when the first key has room.

The catalog's [tier presets](/concepts/policies#tier-presets) carry provider-published limits. Bind one to an account, or bind a tier policy of your own to match what the provider gives your organization.

### System rate limits

Relay ships a few rate limits of its own, owned by the system:

| Name | Applies to | Counted per | Shipped as |
| --- | --- | --- | --- |
| `inference-api-proxy` | Authenticated [proxy mode](/concepts/proxy-mode) requests, as a ceiling on top of the caller's and the host's limits | Credential | Disabled, no rules |
| `inference-api-proxy-anonymous` | Anonymous proxy mode requests | Client IP | Enabled: 60 requests and 5,000 tokens per minute, 10 concurrent |
| `otlp-export` | Exports to the [OTLP receiver](/concepts/otlp-receiver) | Credential | Enabled: 1,200 requests per minute |

Each boot creates any of these that is missing and leaves an existing row unchanged, so edits made through `PUT /api/rate-limits/by-id/{id}` survive restarts, upgrades and catalog re-seeds. To switch one off, set `enabled: false`; a deleted one comes back as shipped on the next boot. To change what they start as on a new database, put a YAML file defining them (same names, `owner.kind: system`) under `<RELAY_CONFIG_DIR>/ratelimits/`.

## Reserve and commit

Each request goes through two steps:

1. **Reserve**, before the upstream call. The counters are checked in atomic scripts, one per counter group (the caller's counters usually form one group, a host key's account and key counters another, the host's a third): `requests` and `concurrency` are counted, and token meters are checked against what has already been counted. If any rule is over, nothing stays counted: the groups already reserved are released before the refusal returns.
2. **Commit**, after the response ends. The token counts from the provider's response are added to the token meters and the concurrency slot is released. This runs in the background once the caller has read the response.

If a request fails before any attempt reaches the upstream, its reservation is cancelled: the concurrency slot is released and, for `token-bucket`, `leaky-bucket` and `session-window` rules, the request is refunded. Once an attempt may have reached the upstream, the request charge stands. A store that cannot be reached refuses the request: limits fail closed.

With `RELAY_STATE_BACKEND=memory`, counters live in each pod, so every pod enforces the full amount on its own. Use `redis` (Dragonfly) to share counters across pods.

## What a limited caller sees

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 12
X-Should-Retry: true
X-WR-Origin: relay
Content-Type: application/json

{"error": {"type": "rate_limit_error", "code": "rate_limit_exceeded", "message": "the rate limit of the team policy <policy-id> is exhausted; try again in 12s"}}
```

The message names the rung and the policy whose limit refused, never the rule. A spent [budget](/concepts/budgets) answers the same way with the code `budget_exceeded`. When every host key is over an upstream limit, the message is `every credential for this model is over its upstream rate limit`.

`Retry-After` is the wait in whole seconds until the refused rule has room, at least `1`. Relay does not send `X-RateLimit-*` headers for its own limits. When the upstream itself answers `429` and no other key can take the request, the upstream's response is forwarded, including its rate-limit headers.

A `503` with code `overloaded` (`529` `overloaded_error` on Anthropic-shaped routes) and `Retry-After: 1` is not a rate limit: it means the pod is at its in-flight cap (`RELAY_MAX_INFLIGHT`, see [Configuration](/configuration)).

## Example

A rate limit with three rules, as a manifest:

```yaml
apiVersion: relay.wyolet.dev/v1alpha3
kind: RateLimit
metadata:
  name: team-chat-rl
  owner: {kind: project, name: chat}
spec:
  rules:
    - {meter: requests, amount: 600, window: 1m, strategy: sliding-window}
    - {meter: tokens, amount: 2000000, window: 1m, strategy: sliding-window}
    - {meter: concurrency, amount: 20, window: 1m, strategy: sliding-window}
```

The same through the control API, with the window in seconds:

```bash
curl -X POST http://localhost:8081/api/rate-limits \
  -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "metadata": {"displayName": "Team chat"},
    "spec": {
      "rules": [
        {"meter": "requests", "amount": 600, "window": 60, "strategy": "sliding-window"},
        {"meter": "tokens", "amount": 2000000, "window": 60, "strategy": "sliding-window"},
        {"meter": "concurrency", "amount": 20, "window": 60, "strategy": "sliding-window"}
      ]
    }
  }'
```

Link it from a policy's `rateLimits` (`{rateLimitId}` through the API, `{ref: team-chat-rl}` in a manifest). `GET /api/policies/{ref}/rate-limits` shows the rate limits a policy links. [Policy examples](/policy-examples) has a complete team policy, and a tier policy with model-scoped entries bound to an account.
