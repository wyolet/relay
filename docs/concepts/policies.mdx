A **policy** links a subject to what it may use: the models it may call, the pools and host keys it draws from, and the rate limits and budgets every request must fit. A policy holds none of these itself; it names them. A **policy binding** attaches a policy to subjects such as a team, a project, a service account or a provider account.

## The ladder

Every request passes six rungs, three on the upstream side and three on the caller side:

```
Host → Account → Credential → Team → Project → Principal
```

| Rung | Subject | Typical use |
| --- | --- | --- |
| Host | A [host](/concepts/catalog) | Rules for everything sent to that host. Only a system-owned binding can bind a host. |
| Account | A provider [account](/concepts/key-pooling#accounts) | The provider's tier: what the provider allows that organization. |
| Credential | One host key | Narrowing a single upstream key. |
| Team | The caller's team | A team-wide model list, budget or rate limit. |
| Project | The caller's project | The same, for one project. |
| Principal | A user or a service account | The same, for one identity. |

Three rules hold on every rung:

- A subject is bound to at most one policy. A second binding naming the same subject is refused when it is saved; there is no priority between bindings. A user is the one exception, see [Bindings on users](#bindings-on-users).
- A request must pass every rung, and a rung can only narrow what the others allow. A rung whose subject has no policy does not constrain anything.
- Relay keys and inference tokens never carry a policy. A key acts as its principal, so rotating or replacing a key leaves the principal's allowance as it was.

Which caller rungs a request has depends on its credential:

| Credential | Team and project rungs | Principal rung |
| --- | --- | --- |
| Service account key | The service account's project and that project's team | The service account |
| A user's own relay key | None | The user, through system-owned bindings only |
| Inference token | The project the token was minted for, and its team | The user, through the binding that governs inside that project |

The upstream rungs are the host the request goes to, the account of the host key that serves it, and that host key. Every host key has an account: one saved without one joins its owner's [default account](/concepts/key-pooling#default-accounts) at its host.

## How the rungs combine

Relay folds the ladder ahead of time, when a policy, binding or linked row changes, so a request reads the result instead of walking the rungs.

- **Models.** A model is allowed only if every rung whose policy lists `models` allows it, upstream rungs included. A policy with no `models` does not narrow models. Wildcard grants skip deprecated and sunset models unless the policy sets `includeDeprecated`. When no caller rung lists models, deprecated models are refused unless a caller policy sets `includeDeprecated`.
- **Pools and host keys.** Only caller rungs link pools and host keys. The innermost caller rung whose policy links any decides which ones the request reaches and in what order; each outer rung that also links some narrows that list to the host keys it reaches too. A rung whose policy links none leaves reach to the others. See [Reach without a caller policy](#reach-without-a-caller-policy) for the case where no rung links any.
- **Rate limits and budgets.** Every rate limit and budget on every rung applies, and the request must fit all of them. See [Rate limits](/concepts/rate-limits) and [Budgets](/concepts/budgets).
- **Disabled rows.** A disabled policy on a caller rung refuses the request with `policy_disabled`; Relay never falls through to a broader rule. A disabled team, project or service account refuses with `subject_disabled`. On an upstream rung, a disabled policy takes that host key out of every route, so it serves nothing rather than serving unmetered.

A refusal names the rung, the subject and the policy that decided it. The codes are listed in [Policy refusals](/reference/inference-api#policy-refusals).

## Reach without a caller policy

When no caller rung links pools or host keys, the principal reaches the host keys its own scopes own, each on its own:

1. the user's own host keys (for a user),
2. the project's (when the request is inside a project: a service account's key, or an inference token),
3. the team's,
4. system-owned host keys.

They are tried in that order, and within one scope in the order they were created. A keyless (`noAuth`) host is never reached this way: it takes a pool at that host, linked by a caller policy, because no key gates it.

Upstream rungs still apply to these requests: the account's tier, the host's rules and any policy bound to the host key.

To give a principal anything beyond this, or a different order, link pools or host keys in a caller policy.

## What a policy holds

| Field (API) | Field (manifest) | Meaning |
| --- | --- | --- |
| `models` | `models` | Model references the rung allows. Empty does not narrow. See [Granting models](#granting-models). |
| `poolIds` | `pools` (names) | Pools to draw host keys from, in failover order. Caller rungs only. See [Pools](/concepts/key-pooling#pools). |
| `credentialIds` | `credentials` (names) | Host keys linked directly; each acts as a pool of one. Caller rungs only. |
| `rateLimits` | `rateLimits` | A list of `{rateLimitId, models}` (`{ref, models}` in manifests). An entry without `models` covers every request; with `models` only requests for a matching model, and only on upstream rungs. See [Rate limits](/concepts/rate-limits#where-rate-limits-apply). |
| `budgetIds` | `budgets` (names) | [Budgets](/concepts/budgets) every request must fit. |
| `includeDeprecated` | `includeDeprecated` | Lets wildcard grants include deprecated and sunset models. Default `false`. |
| `payloadLoggingEnabled` | `payloadLoggingEnabled` | Captures request and response bodies when [payload logging](/concepts/payload-logging) is on. The innermost caller policy decides, overriding the relay key's own flag in both directions. |
| `enabled` | `enabled` | Default `true`. |

A policy is owned by the system, a team, a project, a user or a host. Host-owned policies are the catalog's [tier presets](#tier-presets) and cannot link pools or host keys.

A policy links only rows its scope may use. A system-owned row can be linked from any policy; a team's row from the team's policies and its projects' policies; a project's row from that project's policies. Host keys, rate limits, pools, accounts, budgets and policies can all be owned by a team. A linked row that is missing or out of scope is refused with `400`, and one the caller may not see with `404`.

A policy whose `rateLimits` has an entry with `models` can be bound only to a host, an account or a host key. Binding it to a team, project, user or service account is refused with `400`, and so is adding `models` to an entry of a policy already bound to one: a caller rung's limits cover the whole policy.

## Granting models

`models` is an allow-list of references. A reference has up to three parts, and a missing part matches everything:

| Reference | Example | Grants |
| --- | --- | --- |
| `provider` or `provider/*` | `anthropic` | Every model from the provider, on every host |
| `provider@host` or `provider/*@host` | `anthropic@anthropic` | Every model from the provider, on that host only |
| `provider/model` | `openai/gpt-4o-mini` | That model on every host |
| `provider/model@host` | `openai/gpt-4o-mini@openai` | That model on that host only |
| `@host` | `@ollama-self` | Every model on that host |

Rules:

- Names are normalized, so `openai/gpt-5.5` and `openai/gpt-5-5` are the same reference.
- `provider/*` is the only pattern, the same grant as `provider`, and is stored as `provider`. Any other `*`, such as `openai/gpt-*` or `@*`, is refused with `400`; leave the part out to match everything.
- References with a missing part expand against the live catalog, so a model added later is covered without editing the policy.
- Those wildcard references skip deprecated and sunset models unless `includeDeprecated` is set. A `provider/model` reference grants the model whatever its status.
- There is no deny syntax. To exclude a model, list what you do want.
- `group:` references are accepted and match no model yet.

A grant alone does not make a model callable: the request also needs a pool or host key, reachable from the caller side, at a host that serves the model. See [Naming a model in a request](/concepts/catalog#naming-a-model-in-a-request).

To check what a reference expands to before saving it:

```bash
curl -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  "http://localhost:8081/api/catalog/resolve?ref=anthropic@anthropic&ref=@ollama-self"
```

## Policy bindings

| Field (API) | Field (manifest) | Meaning |
| --- | --- | --- |
| `metadata.owner` | `metadata.owner` | `{kind: system}` or `{kind: team, ...}`. A project-owned binding sets `projectId` instead. |
| `projectId` | `project` (name) | The owning project, for a project-owned binding. |
| `policyId` | `policy` (name) | The policy it attaches. |
| `subjects` | `subjects` | One or more `{kind, id}` (`{kind, name}` in manifests). Kinds: `host`, `account`, `credential` (a host key), `team`, `project`, `user`, `serviceaccount`. |
| `enabled` | `enabled` | Default `true`. A disabled binding binds nothing. |

The owner decides which subjects a binding may name:

| Owner | May bind |
| --- | --- |
| System | Any subject. Only a system-owned binding binds a host. |
| Team | The team, its projects, their service accounts, accounts and host keys owned by the team or one of its projects, and users who are members of the team. |
| Project | The project, its service accounts, accounts and host keys it owns, and users who are members of the project. |

A user is a member of a team or project when they may mint inference tokens there. A binding may use a policy owned by its own scope, an enclosing scope (a project binding may use its team's policies), the system, or a host. A subject outside the owner's scope, or a policy it may not use, is refused with `400`. If a subject later leaves the owner's scope, for example a project moved to another team, the binding stops applying to it.

A group is not a rung, so a group subject is refused with `400`; bind the users, their team or their project instead. A binding stored with a group subject by an earlier version binds nothing through it and must drop the group before it can be saved again. Relay keys are never subjects.

### Bindings on users

A user may be bound once per owner scope, because a team- or project-owned binding on a user governs only that user's requests inside that scope: the inference tokens minted for that project, or for a project of that team. A system-owned binding on a user governs everywhere, including the user's own relay keys. Two scopes that would both govern one request conflict and the second is refused: a system-owned binding and any other, or a team's binding and one owned by a project of that team.

Counters follow the scope, so a policy bound to the same user by two projects counts each project's requests on its own.

A user-owned policy cannot be bound: bindings are owned by the system, a team or a project, and none of them may use a personal policy.

### One binding per subject

Saving a binding that names a subject another binding already holds answers `409` with the code `duplicate_binding` and names the other binding when you may see it. Remove the subject from one binding first. If two bindings do reach one subject, the rung refuses every request with `duplicate_binding` until one is removed.

## Tier presets

The catalog ships host-owned policies that describe a provider's account tiers, such as `openai-build` or `anthropic-scale`, with the provider's published rate limits scoped to the models they apply to. Bind one to an [account](/concepts/key-pooling#accounts) and its limits count across every host key of that account.

List a host's presets:

```bash
curl -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  http://localhost:8081/api/hosts/openai/policies
```

A negotiated tier is a policy you write yourself, usually starting from a preset's rate limits, and bind to the account instead. See [Binding a tier to an account](/policy-examples#binding-a-tier-to-an-account).

## Deleting what a policy links

Deleting a rate limit, budget, pool or host key that policies link is allowed, and the policies lose the link:

- **Rate limit or budget.** The policy acts as if it never had that cap.
- **Pool or host key.** The policy keeps the deleted id and reaches nothing through it; it narrows to what it still links and never falls back to the ownership reach. A policy left with nothing reachable refuses with `no_keys`. A deleted host key also drops out of every pool. Saving that policy again requires removing the stale id, since every link is checked on save.

The delete answers `200` with the links it took, grouped by the kind and field that held them, or `204` when it took none:

```json
{"detached": [{"kind": "policy", "field": "spec.budgetIds", "detachable": false, "count": 2, "hidden": 0,
  "items": [{"id": "…", "name": "ml"}, {"id": "…", "name": "search"}]}]}
```

`GET /api/{plural}/by-id/{id}/references` lists the same before you delete. Some deletes are refused with `409 resource_in_use` instead: a policy still used by a binding, an account still named by host keys, and a host that still has accounts or pools. A default account no host key names never blocks a delete; it goes with its host, team or project.
