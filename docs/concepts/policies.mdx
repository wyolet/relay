A **policy** is a reusable rule set: the models requests under it may call, the pools of host keys they draw from, and the rate limits and budgets they must fit. A policy holds none of these itself; it names them. A **policy binding** applies one policy to one or more [accounts](/concepts/accounts). Many bindings may use one policy, so one rule set can govern many teams, projects or members.

## The ladder

Every request runs in one account, its [lane](/concepts/accounts#lanes), and climbs the accounts above it. On the caller side, outermost first:

| Lane | Rungs |
| --- | --- |
| Member or service account in project P of team T | T's account → P's account → the lane |
| Member account in team T | T's account → the lane |
| Personal account | The lane |
| Provider account used as a lane | None: its own policy applies as the upstream rung of its keys, which are all it reaches |

On the upstream side, each host key's [provider account](/concepts/key-pooling#accounts) is a rung: its policy, usually a [tier preset](#tier-presets), applies to every request a key of that account serves, whoever the caller is. Every host key names its account; one that names none is refused.

Refusals, usage and metrics name the rungs `team`, `project`, `lane` and, upstream, `account`.

Three rules hold on every rung:

- An account is bound to at most one policy. A second binding naming the same account is refused when it is saved; there is no priority between bindings. To add a cap on top of an account's policy, put it on a rung above (the project's or team's account), or give the work an account of its own, such as a service account.
- A request must pass every rung, and a rung can only narrow what the others allow. A rung whose account has no policy constrains nothing.
- Relay keys and inference tokens never carry a policy. A key runs in an account, so rotating or replacing a key leaves the account's allowance as it was.

## How the rungs combine

Relay folds the ladder ahead of time, when a policy, binding or linked row changes, so a request reads the result instead of walking the rungs.

- **Models.** A model is allowed only if every rung whose policy lists `models` allows it, upstream rungs included. A policy with `models: []` does not narrow models.
- **Pools.** Only caller rungs link pools. The innermost caller rung whose policy links any decides which ones the request reaches and in what order; each outer rung that also links some narrows that list to the host keys it reaches too. A rung whose policy links none leaves reach to the others. When no rung links any, see [Reach without a linking rung](#reach-without-a-linking-rung).
- **Rate limits and budgets.** Every rate limit and budget on every rung applies, and the request must fit all of them. See [Shared and per-lane counting](#shared-and-per-lane-counting), [Rate limits](/concepts/rate-limits) and [Budgets](/concepts/budgets).
- **Disabled and closed rows.** A disabled policy on a caller rung refuses the request with `policy_disabled`; Relay never falls through to a broader rule. A disabled team or project refuses with `subject_disabled`, and a closed member account with `account_closed`. A disabled user or service account makes its keys answer `401`. On an upstream rung, a disabled policy takes that account's host keys out of every route, so they serve nothing rather than serving unmetered.

A refusal names the rung, the account and the policy that decided it. The codes are listed in [Policy refusals](/reference/inference-api#policy-refusals).

## Reach without a linking rung

When no caller rung links pools, the lane reaches the host keys its own scopes own, each on its own:

| Lane | Host keys reached, in this order |
| --- | --- |
| Member or service account in a project | The project's, the team's, then the system's |
| Member account in a team | The team's, then the system's |
| Personal account | The user's own, then the system's |
| Provider account | That account's host keys |

Within one scope they are tried in the order they were created. A keyless (`noAuth`) host is never reached this way: it takes a pool at that host, linked by a caller policy, because no key gates it.

Upstream rungs still apply to these requests: each key's account and its tier.

To give a lane anything beyond this, or a different order, link pools in a caller policy.

## What a policy holds

| Field (API) | Field (manifest) | Meaning |
| --- | --- | --- |
| `models` | `models` | Model references the rung allows. Always returned; `[]` allows every model the reached pools serve. See [Granting models](#granting-models). |
| `poolIds` | `pools` (names) | Pools to draw host keys from, in failover order. Caller rungs only. See [Pools](/concepts/key-pooling#pools). |
| `rateLimits` | `rateLimits` | A list of `{rateLimitId, models, shared}` (`{ref, models, shared}` in manifests). An entry without `models` covers every request; with `models`, only requests for a matching model. See [Rate limits](/concepts/rate-limits#where-rate-limits-apply). |
| `budgets` | `budgets` | A list of `{budgetId, shared}` (`{ref, shared}` in manifests). [Budgets](/concepts/budgets) every request must fit. |
| `enabled` | `enabled` | Default `true`. |

`shared` defaults to `true` when left out, and is always returned. The API refuses the fields of earlier versions (`includeDeprecated`, `credentialIds`, `budgetIds`, `payloadLoggingEnabled`) with `422`. A manifest with `includeDeprecated`, `credentials` or `payloadLoggingEnabled` is refused with an error naming the replacement, and each `budgets` entry is a `{ref}` object, not a bare name. Payload logging is set on [accounts](/concepts/accounts#payload-logging).

A policy is owned by the system, a team, a project, a user or a host. Host-owned policies are the catalog's [tier presets](#tier-presets) and cannot link pools.

A policy links only rows its scope may use. A system-owned row can be linked from any policy; a team's row from the team's policies and its projects' policies; a project's row from that project's policies. Rate limits, pools, budgets and policies can all be owned by a team. A linked row that is missing or out of scope is refused with `400`, and one the caller may not see with `404`.

## Shared and per-lane counting

Each rate-limit and budget link says how it counts under the account the policy is bound to:

- `shared: true` (the default): one count for the bound account. A rate limit linked this way by the policy on a team's account is one counter for every lane in the team.
- `shared: false`: one count per lane under the bound account. The same link gives every member and service account in the team its own counter of the same cap.

```yaml
rateLimits:
  - ref: ml-rpm                 # one 600/min counter for the whole team
  - ref: per-person-rpm         # 60/min for each lane in the team
    shared: false
budgets:
  - ref: ml-monthly             # one $2,000 a month for the team
  - ref: per-person-daily       # $20 a day for each lane
    shared: false
```

On a provider account, `shared: true` counts once for the whole organization, as the provider does, and `shared: false` once per caller lane that reaches the account's keys. One rate limit may be linked shared by one policy and per lane by another.

## Granting models

`models` is an allow-list of references:

| Reference | Example | Grants |
| --- | --- | --- |
| `provider` or `provider/*` | `anthropic` | Every model from the provider |
| `provider/model` | `openai/gpt-4o-mini` | That model |

Rules:

- Names are normalized, so `openai/gpt-5.5` and `openai/gpt-5-5` are the same reference.
- `provider/*` is stored as `provider`. Any other `*`, such as `openai/gpt-*`, is refused with `400`.
- A reference naming a host (`anthropic@anthropic`, `@ollama-self`) is refused with `400`: the pools a policy reaches decide the hosts.
- A `provider` reference expands against the live catalog, so a model added later is covered without editing the policy. It covers deprecated and sunset models too.
- There is no deny syntax. To exclude a model, list what you do want.
- `group:` references are accepted and match no model yet.

A grant alone does not make a model callable: the request also needs a pool, reachable from the caller side, at a host that serves the model. A request may still pin a host with `model@host`; it is refused with `host_not_reachable` when none of the pools it reaches is at that host. See [Naming a model in a request](/concepts/catalog#naming-a-model-in-a-request).

To check what a reference expands to before saving it:

```bash
curl -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  "http://localhost:8081/api/catalog/resolve?ref=anthropic&ref=openai/gpt-4o-mini"
```

## Policy bindings

| Field (API) | Field (manifest) | Meaning |
| --- | --- | --- |
| `metadata.owner` | `metadata.owner` | `{kind: system}`, or a team, project or user. Left out of an API create, the caller's own user, or the system for the admin token. |
| `policyId` | `policy` (name) | The policy it applies. |
| `accountIds` | `accounts` (names) | One or more accounts. |
| `enabled` | `enabled` | Default `true`. A disabled binding binds nothing. |

Only accounts are bound. To govern a team, bind its account (`team-<team>`); a project, `project-<project>`; a service account, `sa-<name>`; one person inside a team or project, their member account there; a provider organization, its provider account. See [Kinds of account](/concepts/accounts#kinds-of-account).

The owner decides which accounts a binding may name:

| Owner | May bind |
| --- | --- |
| System | Any account. |
| Team | The team's account and every account owned by the team or one of its projects: project, member, service and provider accounts. |
| Project | The project's account and the accounts it owns: its members', its service accounts' and its provider accounts. |
| User | The accounts the user owns: the personal account and the user's own provider accounts. |

A binding may use a policy owned by its own scope, an enclosing scope (a project binding may use its team's policies), the system, or a host. A policy owned by a user is bound by that user to their own accounts, or by a team or project binding where its owner may create policy bindings. The policy's pools, and the host keys in them, must be usable from the binding's scope. An account outside the owner's scope, or a policy or pool it may not use, is refused with `400`. If an account later leaves the owner's scope, for example a project moved to another team, the binding stops applying to it, and so does a team or project binding of a user's policy once that user may no longer create policy bindings there.

### One binding per account

Saving a binding that names an account another binding already holds answers `409` with the code `duplicate_binding` and names the other binding when you may see it. Remove the account from one binding first. If two bindings do reach one account, the rung refuses every request with `duplicate_binding` until one is removed.

## Tier presets

The catalog ships host-owned policies that describe a provider's account tiers, such as `openai-build` or `anthropic-scale`, with the provider's published rate limits scoped to the models they apply to. Bind one to a [provider account](/concepts/key-pooling#accounts) and its limits count across every host key of that account.

List a host's presets:

```bash
curl -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  http://localhost:8081/api/hosts/openai/policies
```

A negotiated tier is a policy you write yourself, usually starting from a preset's rate limits, and bind to the account instead. See [Binding a tier to an account](/policy-examples#binding-a-tier-to-an-account).

## Deleting what a policy links

Deleting a rate limit, budget or pool that policies link is allowed, and the policies lose the link:

- **Rate limit or budget.** The policy acts as if it never had that cap.
- **Pool.** The policy keeps the deleted id and reaches nothing through it; it narrows to what it still links and never falls back to the ownership reach. A policy left with nothing reachable refuses with `no_keys`. Saving that policy again requires removing the stale id, since every link is checked on save. A deleted host key drops out of every pool.

The delete answers `200` with the links it took, grouped by the kind and field that held them, or `204` when it took none:

```json
{"detached": [{"kind": "policy", "field": "spec.budgets[].budgetId", "detachable": false, "count": 2, "hidden": 0,
  "items": [{"id": "…", "name": "ml"}, {"id": "…", "name": "search"}]}]}
```

`GET /api/{plural}/by-id/{id}/references` lists the same before you delete. Some deletes are refused with `409 resource_in_use` instead: a policy still used by a binding, an account still named by host keys, relay keys or a binding, and a host that still has accounts or pools.

## Finding problems

`GET /api/plan-issues` lists what Relay found wrong while folding the configuration: a binding naming an account outside its owner's scope, a policy linking a pool that no longer exists, an account bound twice, a host key whose value cannot be resolved. See [Control API](/reference/control-api#plan-issues).
