title: "Usage & Logging"
description: "Track every request, and optionally capture full payloads"
---

Relay records every request that passes through it, and can optionally capture
the full request/response bodies. Both are read back through the control plane,
so you get usage analytics and request-level debugging without bolting on a
separate tool.

## Usage tracking

Every request is logged — there's no opt-in. Each record carries the relay
key, policy, model, status, token counts, and timing. Capture happens off the
hot path in a detached observer, so it never adds latency to a response.

Read it back through the control plane:

| Endpoint | Returns |
| --- | --- |
| `GET /logs` | The request log, newest first (paginated with `limit` + `cursor`). |
| `GET /logs/{request_id}` | A single request, with captured bodies attached if payload logging was on. |
| `GET /usage/events` | Raw usage events, filterable. |
| `GET /usage/summary` | Aggregated totals (tokens, counts) over a window. |
| `GET /usage/timeseries` | Bucketed usage over time. |

All three endpoints share the same filter parameters: `since` (default
`1h`) or an absolute `from`/`to` window; `status_min`/`status_max` or the
`status_class` shorthand (`2xx`/`4xx`/`5xx`); `model_id`, `host_id`,
`policy_id`, `project_id`, `team_id`, `principal_id`, `host_key_id`
(repeatable, match-any); `model`, `host`, `policy`, `provider`,
`requested_model` (slug/string match-any); `source` (`pipeline` / `proxy`
/ `ws` / `batch` / `otlp`); `finish_reason`, `error_kind`; `streamed` and `error`
(`true`/`false`); `attempts_min`, `duration_ms_min`/`max`,
`ttft_ms_min`/`max`; `tag` (`key:value`, repeatable); `q` (free-text
substring); and `request_id` / `relay_key_hash` for a single event.

Every event also carries who made the request: `project_id` / `team_id` /
`principal_id` (with the `project`, `team`, `principal` slugs as of the
request) and the credential that authenticated it (`credential_kind`,
`credential_id`). `summary` and `timeseries` take a `group_by` on top of
the filters — `source` (default) | `model` | `host` | `policy` |
`provider` | `project` | `team` | `principal` (event-time slugs), or
`model_id` | `host_id` | `policy_id` | `project_id` | `team_id` |
`principal_id` | `credential_id` | `relay_key_hash` | `host_key_id` |
`finish_reason` | `error_kind`, or `tags.<key>` to group by one caller
tag's value — so per-project or per-service-account spend is one query:

```bash
curl -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  "http://localhost:8081/api/usage/summary?group_by=project&since=7d"
```

```bash
curl -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  "http://localhost:8081/api/usage/summary?model_id=<id>&since=24h"
```

### Where usage is stored

The sink is selectable and hot-swappable via the control plane — no restart:

```bash
curl -X PUT http://localhost:8081/api/settings/usage-logging \
  -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"backend": "clickhouse", "retentionDays": 0, "file": {}, "clickhouse": {}}'
```

| Backend | Use |
| --- | --- |
| `file` (default) | JSONL on disk — fine for a single node and a try-out. |
| `clickhouse` | Analytical store for high-volume, queryable history. |
| `postgres` | Reuse your existing database. |
| `valkey` | Redis-compatible, for short-lived recent history. |

### Retention

`retentionDays` in the `usage-logging` section sets how long usage events are kept by the `clickhouse` and `postgres` backends. `0` (the default) keeps them forever. On ClickHouse the value becomes the table's TTL and is applied to the existing table whenever the section changes; shortening it deletes older events in the background, and they cannot be recovered. Postgres deletes expired rows once a day. Only an admin may change this section.

## Reported usage (OpenTelemetry)

Model calls that never pass through Relay can still be recorded. An application instrumented with OpenTelemetry exports its traces or logs to Relay over OTLP/HTTP, and each span or event that describes a model call becomes a usage event next to the proxied ones, attributed to the relay key that sent it and priced from the catalog. Reported usage is what the client declares: it is recorded, never enforced.

### Enable the receiver

The receiver is off by default and returns `404` until the `otlp-receiver` setting is enabled. It applies without a restart.

```bash
curl -X PUT http://localhost:8081/api/settings/otlp-receiver \
  -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"enabled": true}'
```

The write replaces the whole section: a field left out takes its default, so this body also turns [content capture](#message-content) off.

### Configure the exporter

The endpoints are on the inference port: `/otlp/v1/traces` and `/otlp/v1/logs`. The exporter authenticates like an inference client, with a relay key or token in the `Authorization` header. Any valid credential may report: one with no policy, and one whose policy does not grant the reported model, since reporting routes nothing. A credential that inference rejects as invalid (unknown, disabled, expired) cannot, and neither can one whose governing policy is disabled: the operator switched that access off, and the export is answered `403`. Calls are attributed to that key's project, team and principal, so give each reporting service a key of its own.

```bash
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
export OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://localhost:8080/otlp/v1/traces
export OTEL_EXPORTER_OTLP_LOGS_ENDPOINT=http://localhost:8080/otlp/v1/logs
export OTEL_EXPORTER_OTLP_HEADERS="Authorization=Bearer $RELAY_KEY"
export OTEL_EXPORTER_OTLP_COMPRESSION=gzip
```

- The protocol must be OTLP over HTTP: `http/protobuf` or `http/json`. Relay does not serve gRPC, and an SDK whose default is `grpc` fails to connect until the protocol is set.
- `gzip` compression is accepted and optional. Chunked request bodies are accepted.
- `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:8080/otlp` works in place of the two signal variables: the SDK appends `/v1/traces` and `/v1/logs`. It also appends `/v1/metrics` when a metrics exporter is configured, which Relay answers with `404`; set `OTEL_METRICS_EXPORTER=none` or use the signal variables.

In Python, with `opentelemetry-sdk`, `opentelemetry-exporter-otlp-proto-http` and a GenAI instrumentation such as `opentelemetry-instrumentation-openai-v2` or `opentelemetry-instrumentation-google-genai`, the exporters read those variables:

```python
from opentelemetry import trace
from opentelemetry.exporter.otlp.proto.http.trace_exporter import OTLPSpanExporter
from opentelemetry.instrumentation.openai_v2 import OpenAIInstrumentor
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor

provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter()))
trace.set_tracer_provider(provider)
OpenAIInstrumentor().instrument()
```

Traces are enough for usage. Export logs as well only when the instrumentation reports model calls as events (`OTEL_INSTRUMENTATION_GENAI_EMIT_EVENT=true` in the Python instrumentations) and you want [message content](#message-content) from them. The JSON exporters (`opentelemetry-exporter-otlp-json-http` in Python, `@opentelemetry/exporter-trace-otlp-http` and `@opentelemetry/exporter-logs-otlp-http` in Node.js) work the same way.

### What is recorded

Relay reads the [OpenTelemetry GenAI semantic conventions](https://github.com/open-telemetry/semantic-conventions-genai), including the attribute names earlier releases used. Exporting whole traces and all logs is fine: everything that is not a model call is ignored and counted in `relay_otlp_spans_total{outcome="ignored"}` or `relay_otlp_log_records_total{outcome="ignored"}`.

| Record | Recorded | Ignored |
| --- | --- | --- |
| Span | `gen_ai.operation.name` is `chat`, `generate_content`, `text_completion` or `embeddings`. A span without an operation name counts when it names a model and carries token usage. | Agent, workflow, tool, retrieval and all other spans. An agent span repeats the token usage of the model calls beneath it, so recording it would count them twice. |
| Log record | The event `gen_ai.client.inference.operation.details` for one of the operations above, with its fields as log record attributes. | Every other log record, including the per-message events of earlier conventions (`gen_ai.user.message`, `gen_ai.choice`, …). |

| Event field | Read from |
| --- | --- |
| `requested_model`, `model` | `gen_ai.request.model`, `gen_ai.response.model`; the response model is tried first against the catalog |
| `provider`, `pricing` | `gen_ai.provider.name` (earlier: `gen_ai.system`) and the catalog; see [Pricing](#pricing-and-provider-names) |
| `tokens` | `gen_ai.usage.input_tokens`, `output_tokens`, `cache_read.input_tokens`, `cache_creation.input_tokens` (or `cache_write.input_tokens`), `reasoning.output_tokens`, `audio.input_tokens`, `audio.output_tokens` (earlier: `prompt_tokens`, `completion_tokens`) |
| `status` | `http.response.status_code`; an `error.type` that is an HTTP error status (`"429"`) is used when that is missing. A failed call with no status is stored with status `0`: it is listed in the logs and left out of summaries, like a request Relay rejected before reaching a provider. |
| `error_kind` | Relay's own classification of a failed call, in the values proxied requests use; see [Error kinds](#error-kinds). The `error.type` the client sent is kept in `extras.reported_error_type`. |
| `finish_reason` | first value of `gen_ai.response.finish_reasons` |
| `streamed`, time to first token | `gen_ai.request.stream`, `gen_ai.response.time_to_first_chunk` |
| `ts`, `duration_ms` | the span's start and end. An event has no duration: `duration_ms` is `0` and `ts` is the record's time, or the time the SDK observed it. A start time in the past is kept as reported, within the store's [retention](#retention): see [Old calls](#old-calls). A call with no start time is dated when Relay receives it. |
| `extras` | `trace_id`, `span_id`, `response_id` (`gen_ai.response.id`), `session_id` (`gen_ai.conversation.id`), `service` (the resource's `service.name`), `operation`, `reported_provider` |

A row is as complete as the instrumentation makes it. Three examples from current releases: `opentelemetry-instrumentation-openai-v2` 2.4b0 and `@opentelemetry/instrumentation-openai` 0.20.0 report neither cached nor reasoning tokens and do not mark a streamed call, so such a call is stored with all input at the uncached rate and `streamed: false`; `opentelemetry-instrumentation-google-genai` 1.2b0 reports all of them. Report one call and read it back with `GET /api/usage/events?source=otlp` before relying on the numbers.

### Old calls

Retention counts from a call's start time, so a store with a retention window would delete a call older than the window as soon as it arrived. Relay does not accept such data:

- A call that started before the usage retention window (`retentionDays` of `usage-logging`, less an hour) is rejected and named in the partial-success message, for example `model-call spans rejected: 2 older than the usage retention of 30 days`. With `retentionDays: 0`, and with the `file` and `valkey` backends, which do not delete by age, a call of any age is accepted.
- A call inside the usage window but older than the payload retention (`retentionDays` of `payload-logging` on the `clickhouse` backend, 30 by default) is recorded without its content, and the response says so.
- Both follow the settings as they change, without a restart.

To import history, set the usage retention to cover the imported dates first, and the payload retention too if the content matters.

### Error kinds

Instrumentations put different things in `error.type`: an exception class name, a provider error code, an HTTP status. Relay does not store that as the kind, because filtering or grouping by `error_kind` would then not line up between reported and proxied events. A failed call gets one of five kinds:

| `error_kind` | When |
| --- | --- |
| `upstream_error` | The provider's HTTP status is known and is 400 or above. The status is in `status`. |
| `timeout` | No status, and `error.type` names a timeout or an exceeded deadline. |
| `client_canceled` | No status, and `error.type` names a cancellation. |
| `upstream_unreachable` | No status, and `error.type` names a failed connection. |
| `error` | Anything else, including `_OTHER` and class names such as `RateLimitError` that arrive without a status. |

A call that succeeded has no `error_kind`. To see what clients actually sent, read `extras.reported_error_type`.

### How a reported event differs from a proxied one

- `source` is `otlp`. Summaries and time series include reported events by default; filter with `source=otlp`, or name the other sources to leave them out.
- `request_id` is `otlp-<trace id>-<span id>`.
- It is attributed to the credential that sent the export, not to anything the telemetry claims.
- `policy`, `host` and `host_key` are empty: Relay routed nothing. No policy, budget or inference rate limit is applied or consumed.
- Token counts use the same split as proxied events. `gen_ai.usage.input_tokens` includes cached tokens under the conventions, so Relay stores the uncached part as `input` and the rest as `cache_read` and `cache_creation`. `audio_input` and `audio_output` stay counted inside `input` and `output`. `reasoning` likewise stays counted inside `output`. When the model's rate sheet prices reasoning as its own meter, the cost charges those tokens on that meter only, not on output as well; the stored counts are the same either way.
- Timing has no relay overhead or attempt count; it is the client's own measurement.

### Duplicates

Exporters resend a batch when they get no answer, and a client may report one call as a span and as an event. A call is identified by its trace id and span id, and the first report of it within 24 hours is recorded; later ones are skipped, still answered with success, and counted as `outcome="duplicate"`. The span and the event of one call share those ids, so they are one usage event. Whichever arrives first sets the row, which leaves `duration_ms` at `0` when the event wins.

An event emitted outside any span is identified by `gen_ai.response.id` instead (its `request_id` is `otlp-<digest of the response id>-response`). Calls are told apart per project, or per principal for a credential outside any project: one service reporting through two keys of a project is recorded once, and two projects reporting the same ids are recorded separately.

### Pricing and provider names

Cost is computed when the reported model resolves to a catalog model, at the time the event is recorded. The model name is looked up qualified by the reported provider, then on its own; names and aliases match as they do for inference. A model the catalog does not know is stored unpriced, which is not a cost of zero: `unpriced` in a summary counts such events.

Telemetry names providers its own way, and often names the service that served the call. Relay maps the names that differ from the catalog's: `gcp.gemini` and `gemini` to provider `google`, `azure.ai.openai` to `openai`, `x_ai` to `xai`, `mistral_ai` to `mistral`, `moonshot_ai` to `moonshot`. Because Relay did not route the call, it picks the rate sheet in this order: the host the mapped name stands for, the provider's own host, then the first host that has pricing for the model. `aws.bedrock` and `gcp.vertex_ai` have no catalog host, so their calls are priced at the model provider's own rates. The chosen rate sheet is in the event's `pricing` field.

### Limits and responses

| Response | When | Exporter |
| --- | --- | --- |
| `200` | The export was accepted. An empty body means every model call in it was recorded or was a duplicate. | done |
| `200` with `partialSuccess` | Some model calls were refused and the rest recorded: `rejectedSpans` / `rejectedLogRecords` counts those with no trace id and span id (for an event: nor a response id), starting more than 5 minutes in the future, or [older than the usage retention](#old-calls); `errorMessage` says which and how many. | logs it, does not resend |
| `400` | The body does not decode, or the export reports more than 10,000 model calls. | drops the batch |
| `200` with `partialSuccess.errorMessage` only | Everything was recorded, with a warning: the export carried [message content](#message-content) that Relay does not store. No record is counted as rejected. | logs it if it reads partial success |
| `401` | Missing or invalid relay key. | drops the batch |
| `403` `policy_disabled` | The policy that governs the credential is disabled. The body is the one inference returns for that credential. | drops the batch |
| `404` | The receiver is disabled, or the path is not served (`/otlp/v1/metrics`). | drops the batch |
| `413` | The body is over 16 MiB after decompression (`RELAY_MAX_REQUEST_BYTES` when set). | drops the batch |
| `415` | The `Content-Type` is neither `application/x-protobuf` nor `application/json`, or the `Content-Encoding` is not `gzip`. | drops the batch |
| `429` + `Retry-After` | The credential is over the export rate limit: 1,200 export requests per minute, traces and logs together. A rate limit named `otlp-export` replaces the built-in value (`config/ratelimits/system.yaml` holds one, loaded with `relay seed --from config --apply`); disable it to apply none. | retries |
| `503` + `Retry-After` | The usage queue lacks room. Reported calls use the queue only while it is under half full, so they never crowd out the records of proxied traffic. | retries |

Exporters retry `429` and `503` with backoff, and a resend is safe: whatever the first attempt recorded is skipped as a duplicate. An exporter that exhausts its retries drops the batch, and that usage is lost.

### Message content

Content is stored only when the client sends it and Relay is set to keep it. Sending it is a request; the operator decides. Both operator switches below must be on, and then the policy that governs the reporting credential decides: content is stored when that policy has `payloadLoggingEnabled: true` and dropped when it does not, whatever the key's own flag says. A credential that no policy governs has what it sends stored. A client behind a policy that does not capture is uploading content Relay drops, so turn capture off in its instrumentation; `relay_otlp_content_total{outcome="policy"}` counts those calls.

Relay tells the client. When an export carries content that is not stored because of the policy, because an operator switch is off, or because the call is [older than the payload retention](#old-calls), the `200` response is a partial success with nothing rejected and a message such as `message content of 2 model calls was not stored: the policy of this credential does not allow storing message content. It is safe to stop sending content; usage was recorded.` Whether the application sees it depends on its exporter: the Node.js exporters log partial success through the diagnostics logger (`diag.setLogger(...)` at warn level), and the Python exporters (1.45.0) do not read it. Content skipped as a duplicate or dropped by a busy queue produces no message.

On the client, turn on content capture in the instrumentation. For the Python instrumentations:

```bash
export OTEL_SEMCONV_STABILITY_OPT_IN=gen_ai_latest_experimental
export OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=span_only   # or event_only, span_and_event
```

On Relay, enable [payload logging](#payload-logging) and set `captureContent` on the receiver:

```bash
curl -X PUT http://localhost:8081/api/settings/otlp-receiver \
  -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"enabled": true, "captureContent": true}'
```

Relay reads `gen_ai.system_instructions`, `gen_ai.input.messages`, `gen_ai.tool.definitions` and `gen_ai.output.messages`, as structured values or as the JSON text instrumentations put on spans. They become the payload of the call's log record, returned by `GET /api/logs/{request_id}` like a proxied request's bodies: `request_body` is one JSON object holding the input-side attributes under their names, `response_body` one holding `gen_ai.output.messages`.

```json
{
  "gen_ai.input.messages": [{"role": "user", "parts": [{"type": "text", "content": "Say hello."}]}],
  "gen_ai.system_instructions": [{"type": "text", "content": "You are a terse assistant."}]
}
```

- Each body is cut at the payload `maxBytes` and flagged `request_truncated` / `response_truncated`; a cut body is no longer valid JSON.
- With the deduplicated ClickHouse store (`clickhouse.dedup: true`, under [Payload logging](#payload-logging)), each message, tool definition and instruction part of the request body is stored once. A message is the same bytes whether it came on a span or an event and whichever export carried it, so the second turn of a conversation adds only its new messages. A body cut at `maxBytes` is stored whole, so use `maxBytes: 0` with it. The response body is not deduplicated.
- Content is stored once per call, also when it arrives after the usage event (`event_only` with spans exported first). `span_and_event` sends every message to Relay twice and stores it once, so prefer one of the other two.
- The governing policy is found as for inference: the key's policy, else its service account's, else the project's policy bindings. Unlike a proxied request, where the policy or the key can opt in, the key's `payloadLoggingEnabled` has no effect on reported content.
- When the payload queue is over half full, content is dropped and the usage event is kept; `relay_otlp_content_total{outcome="dropped"}` counts it.
- The content forms of earlier conventions (`gen_ai.prompt` / `gen_ai.completion` attributes, one event per message) are not stored. `@opentelemetry/instrumentation-openai` 0.20.0 emits the per-message events, so its content is not captured.

Capturing content roughly doubles what the application uploads for each call: the messages it sends to the provider are sent again to Relay, along with the response. Budget the egress and the store before turning it on for a busy service.

### Not supported

- The metrics signal. GenAI metrics are pre-aggregated histograms with no per-request rows, and a client sending both would be counted twice.
- OTLP over gRPC.
- Agent, tool and retrieval spans as usage events.
- Enforcement. A reported call has already happened; policies, budgets and rate limits of inference do not see it.

## Payload logging

Payload logging captures the **full request and response bodies** and attaches
them to the matching log record (joined by request id). It's how you inspect
exactly what a client sent and what the provider returned — invaluable for
debugging integrations.

It's **off by default** and gated at three levels. All must line up for a body
to be captured:

<Steps>
  <Step title="Global master switch">
    `PUT /api/settings/payload-logging` with `enabled: true`. While this is off,
    nothing is ever captured, regardless of the per-request flags below.
  </Step>
  <Step title="Per-request opt-in">
    Then capture is enabled for a request when **either** its **policy** or its
    **relay key** opts in — `payloadLoggingEnabled: true` on either one.
  </Step>
</Steps>

So you can turn capture on broadly (set it on a policy) or narrowly (set it on
a single relay key you're debugging), while the global switch stays the master
kill switch.

```bash
# 1. Turn the observer on globally, pick a backend.
curl -X PUT http://localhost:8081/api/settings/payload-logging \
  -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "enabled": true, "backend": "file", "maxBytes": 1048576, "retentionDays": 30,
    "file": {"path": "relay-payloads.jsonl"},
    "s3": {"endpoint": "", "bucket": "", "useSSL": false, "accessKey": {"kind": ""}, "secretKey": {"kind": ""}},
    "clickhouse": {}
  }'

# 2. Opt a single key into capture.
curl -X PUT http://localhost:8081/api/keys/by-id/<id> \
  -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"spec": {"payloadLoggingEnabled": true}}'
```

The write replaces the whole section; `retentionDays` and every backend block are required, also the ones not in use. To change one field, read the section with `GET /api/settings/payload-logging` and send its `value` back with the change.

### Reading captured payloads

The bodies come back on the log detail endpoint:

```bash
curl -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  http://localhost:8081/api/logs/<request_id>
```

The response includes `request_body` and `response_body`, plus
`request_truncated` / `response_truncated` flags when a body exceeded
`maxBytes`.

| Backend | Use |
| --- | --- |
| `file` (default) | JSONL on disk. |
| `s3` | Object storage — content-addressed blobs; credentials resolved from env or the encrypted store, never plaintext. |
| `clickhouse` | Alongside ClickHouse usage events. |

`retentionDays` sets how long the `clickhouse` backend keeps bodies: `30` by default, `0` to keep them forever. It is applied to the existing table whenever the section changes, the same way as usage retention. For `s3`, expire objects with a bucket lifecycle rule; the `file` backend is never pruned.

Agent clients resend the whole conversation on every turn, so most of each request body repeats earlier ones. `clickhouse.dedup: true` (off by default) stores each distinct message, tool list, and large field such as a system prompt once, and each request as the rest of its body plus references to them. Bodies read back byte for byte; a body that is not a JSON object, including a truncated one, is stored whole. Rows written before switching either way stay readable. Pair it with `maxBytes: 0`, so the largest requests are not truncated and stored whole.

The `s3` credentials (`s3.accessKey`, `s3.secretKey`) are secret references limited to this section: an env reference must name a variable starting with `RELAY_PAYLOAD_S3_` (for example `{"kind": "env", "env": "RELAY_PAYLOAD_S3_ACCESS_KEY"}`), and a stored reference must use an id starting with `payload-logging:`. Leave both empty to use the S3 client's ambient credentials (an IAM role, for example). `s3.useSSL` must be `true` unless `RELAY_COOKIE_SECURE=false`. Only an admin may change the `payload-logging` section. A stored section that breaks these rules is read as the default (capture off, `file` backend) and logged at startup; rename the variables and write the section again.

<Warning>
Payloads contain prompts and completions — potentially sensitive data. Keep it
off by default, scope it to the keys or policies you're actively debugging, and
set a `maxBytes` cap.
</Warning>
