---
title: "Upgrading to 0.20"
description: "Moving a 0.11 deployment to the policy ladder: what the migrations drop, the checks to run first, and the steps in order"
---

0.20 replaces how policies reach host keys and limits. A policy now links pools, host keys, rate limits and budgets, policy bindings attach it to any rung of the [policy ladder](/concepts/policies#the-ladder), and relay keys, service accounts and host keys no longer hold a policy. The upgrade is a manual migration: you rewrite your policies and bindings in the new shape, and nothing is converted for you.

<Warning>
**The migration drops the old policy links.** Migration 36 deletes every policy's host keys, model ids and rate limit, every relay key's and service account's policy, and every host key's tier policy. They are not converted and not restored by a down-migration. Export your configuration and back up Postgres before you upgrade.
</Warning>

This is a [stop-and-start upgrade](/concepts/upgrade#stop-and-start-upgrades): a 0.11 pod cannot serve against the new schema. Schema version goes from 34 to 36.

## What changes

| 0.11 | 0.20 |
| --- | --- |
| Policy `hostKeyIds` (`hostKeys` in manifests) | `poolIds` / `credentialIds` (`pools` / `credentials`). See [Pools](/concepts/key-pooling#pools). |
| Policy `keySelection` | A pool's `selection`. |
| Policy `rateLimitId` (`rateLimit`) | `rateLimits: [{rateLimitId}]` (`[{ref}]`). |
| Policy `rlBindings` | `rateLimits` entries with `models`, in a policy bound to a host, an account or a host key. A policy bound to a team, project, user or service account cannot scope a rate limit to models: its limits cover every model. |
| Policy `modelIds` | `models` (model references). |
| Relay key `policyId`, service account `policyId` | A policy binding on the key's principal. |
| Host key `policyId` (its tier policy) | Host key `accountId` (`account`), and a policy binding of the tier on that [account](/concepts/key-pooling#accounts). A key without an account joins its owner's [default account](/concepts/key-pooling#default-accounts). |
| Policy binding `priority`, several bindings per subject | One binding per subject. `priority` is gone: the control API refuses it with `422` and manifests ignore it. |
| Group subjects in policy bindings, `system:authenticated` as a project default | Group subjects are refused with `422` on save, and stored ones bind nothing. Bind the users, the team or the project instead. |
| Host `policies` and `defaultPolicy` | Gone. A host's tier presets are the policies it owns (`GET /api/hosts/{host}/policies`), and one applies once it is bound to an account. The control API refuses the fields with `422`, manifests ignore them, and the hosts list filters `policy_id`, `default_policy` and `has_default_policy` answer `400`. |
| Team and project `spec.budget`, which nothing enforced | A [budget](/concepts/budgets) linked by the policy bound to the team or project. A manifest that still carries `budget` is refused with a pointer to `Budget`. |
| `RELAY_REDIS_POSTFLIGHT_BATCH_SIZE`, `RELAY_REDIS_POSTFLIGHT_BATCH_DELAY_MS`, `RELAY_REDIS_POSTFLIGHT_QUEUE_SIZE`, the chart's `relay.redisPostFlightBatchSize`, `relay.redisPostFlightBatchDelayMs`, `relay.redisPostFlightQueueSize`, and the metrics `relay_settle_queue_full_total`, `relay_settle_retries_total` | Gone: each request settles its counters on store calls of its own. Leftover values are ignored. |
| `allowMissingPolicy` in the `inference` settings section | Gone. A principal with no caller policy reaches the host keys its own scopes own, and system-owned ones. |
| `relay.wyolet.dev/v1alpha2` for `Policy`, `HostKey`, `Key`, `PolicyBinding` | `relay.wyolet.dev/v1alpha3`. The old shape is refused with a pointer to the new one; other kinds still accept v1alpha2. |
| `POST`/`DELETE /api/policies/by-id/{id}/keys/{keyId}` | Removed. Bind a policy to the key's principal. |
| `/api/schemas/v1alpha2/...` | `/api/schemas/v1alpha3/...`. |

New kinds: `Account`, `Pool` and `Budget`, with their CRUD routes (`/api/accounts`, `/api/pools`, `/api/budgets`) and RBAC kinds (`accounts`, `pools`, `budgets`, granted by the built-in roles). Teams may now own host keys and rate limits as well.

Behaviour that changes at request time:

- **Reach without a policy widens.** In 0.11 a project-scoped credential that resolved no policy was refused with `no_policy`. In 0.20 it reaches the host keys owned by its project, its team and the system. Host keys created with the admin token are system-owned, so every principal without a caller policy that links pools can use them. To keep a team or project on specific keys, bind it a policy that links the pools it should use; see [Reach without a caller policy](/concepts/policies#reach-without-a-caller-policy).
- **Project bindings on users govern only that project's tokens.** A binding owned by a project, naming a user, applies to the inference tokens that user mints for the project. The user's own relay keys see only a system-owned binding or the user's own, and no longer take a project's attribution or limits from a project-owned policy.
- **Every host key has an account.** Migration 36 puts each host key without one into its owner's default account at its host, and a key saved later without one joins it too. A `429` from the provider on a key in a default account still goes to that key's breaker and the request fails over to the next key, as in 0.11. Only accounts you create cool on a `429`: put keys that share one provider organization into such an account to have a `429` on one skip the others for the requested model. See [Accounts](/concepts/key-pooling#accounts).
- **Usage `policy_id`** records the innermost caller policy: the principal's, else the project's, else the team's.
- **Proxy mode** refuses a model that is not in the catalog, also for a key that had no policy, instead of forwarding it unpriced.
- **Batch items** run under the ladder as it is when each item runs, not as it was at submission.
- **Error codes.** `no_policy`, `policy_not_found` and `policyless_disabled` are gone; `subject_disabled`, `duplicate_binding`, `unpriced_under_budget` and `budget_exceeded` are new. `model_not_allowed` names the rung and the policy that refused. A disabled, revoked, expired or rotated-out relay key answers `401 invalid api key`. See [Policy refusals](/reference/inference-api#policy-refusals).

## What the migrations do

**Migration 35** adds the `accounts`, `pools`, `pool_credentials` and `budgets` tables and the junctions linking a policy to pools, host keys, rate limits and budgets. Policy bindings gain team and system owners and the host, account, credential, team and project subject kinds. Every existing binding stays owned by its project.

It then enforces one binding per subject: a subject other than a user may appear in one binding, and a user in one binding per owning project. If the database holds a subject bound twice, the migration stops and nothing of it is applied:

```
migration 000035: a subject may be bound by one policy binding (a user by one per owner scope); remove the subject from all but one binding, then upgrade again: serviceaccount <id> in <binding>, <binding>
```

**Migration 36** drops the `policy_models` and `policy_host_keys` tables, the `policies.rate_limit_id` column and the `policy_bindings.priority` column, and removes `modelIds`, `hostKeyIds`, `rateLimitId`, `rlBindings` and `keySelection` from every policy, `policyId` from every relay key, service account and host key, `policies` and `defaultPolicy` from every host, and `budget` from every team and project. Policies keep their name, owner, `models`, `includeDeprecated`, `payloadLoggingEnabled` and `enabled`. Policy bindings, rate limits, host keys, relay keys, teams, projects and service accounts are kept.

<Note>
Migration 36 refuses to run if any still-bound policy would lose its only access restriction. A policy with rows in `policy_models` and an empty `models` field, or rows in `policy_host_keys` and no pools or credentials, becomes unrestricted once those rows are gone. If any such policy is bound to a non-group subject—disabled bindings count—the migration stops and lists each policy and its bindings. Adding `models` or pools before upgrading is not possible; the pools table exists only in 0.20. Unbind those policies (or delete their bindings) on the 0.11 database first, upgrade, then add `models`, pools or credentials following [Re-creating the dropped links](#re-creating-the-dropped-links). See step 5 of [Before you upgrade](#before-you-upgrade) for the check query.
</Note>

Before it drops them, it logs each link it removes by the names of both ends, on boot and in `relay migrate up`: one log entry per link, with the message `migrate: postgres notice` and the line below in its `notice` field. A target whose row no longer exists is named by its id:

```
000036: dropping link: key "ci-runner" -> policy "ci"
000036: dropping link: host key "anthropic-main" -> tier policy "anthropic-start"
000036: dropping link: service account "legacy-api" -> policy "ci"
000036: dropping link: policy "ci" -> host key "anthropic-main"
000036: dropping link: policy "ci" -> model "claude-haiku-4-5"
000036: dropping link: policy "ci" -> rate limit "ci-rpm"
000036: dropping link: policy "anthropic-start" -> rate limit "anthropic-start-rl" for models anthropic/claude-opus-5-5, anthropic/claude-sonnet-5-5
000036: binding no longer applies: policy binding "project-default" (policy "users") -> group "system:authenticated"
000036: binding narrows to project tokens: policy binding "project-alice" (policy "users") -> user "alice" governs only tokens in project "dev", not personal keys
```

It then gives every host key without an account its owner's default account at the key's host, creating one account per owner and host, named after the host (suffixed `-2`, `-3`, … when the name is taken). A key created with the admin token is system-owned and joins the system's default account. Keys whose host no longer exists are left without one.

The catalog's tier policies lose their rate limits with this migration. They get them back, as `rateLimits` entries scoped to models, when a catalog release with the v1alpha3 schema is seeded.

**Migration 37** adds `policy_bindings.user_id`, the owner of a user's own binding; deleting the user deletes it.

**Migration 38** moves every binding subject that names a host key to the key's account, since a limit set on a key counts on its account (see [Bindings on host keys](/concepts/policies#bindings-on-host-keys)). A 0.11 database has none. If an account would end up in two bindings, the migration stops and names the account and the bindings; remove all but one and upgrade again.

## Before you upgrade

1. **Export the current configuration** with the 0.11 CLI, as the reference for the rewrite:

   ```bash
   relay export --include-system -o before-0.20.yaml
   ```

2. **Export the links migration 36 drops and the bindings it changes**, by name. The query only reads; run it against the 0.11 database and keep the result for [Re-creating the dropped links](#re-creating-the-dropped-links):

   ```sql
   SELECT 'key -> policy' AS link, k.name AS source, COALESCE(p.name, k.spec->>'policyId') AS target, NULL AS models
   FROM relay_keys k LEFT JOIN policies p ON p.id = k.spec->>'policyId'
   WHERE COALESCE(k.spec->>'policyId', '') <> ''
   UNION ALL
   SELECT 'host key -> tier policy', s.name, COALESCE(p.name, s.spec->>'policyId'), NULL
   FROM secrets s LEFT JOIN policies p ON p.id = s.spec->>'policyId'
   WHERE COALESCE(s.spec->>'policyId', '') <> ''
   UNION ALL
   SELECT 'service account -> policy', sa.name, COALESCE(p.name, sa.spec->>'policyId'), NULL
   FROM service_accounts sa LEFT JOIN policies p ON p.id = sa.spec->>'policyId'
   WHERE COALESCE(sa.spec->>'policyId', '') <> ''
   UNION ALL
   SELECT 'binding -> group (no longer applies)', b.name, s.subject_name, p.name
   FROM policy_binding_subjects s
   JOIN policy_bindings b ON b.id = s.binding_id
   JOIN policies p ON p.id = b.policy_id
   WHERE s.kind = 'group'
   UNION ALL
   SELECT 'binding -> user (project tokens only)', b.name, COALESCE(u.username, s.subject_id), pr.name
   FROM policy_binding_subjects s
   JOIN policy_bindings b ON b.id = s.binding_id
   JOIN policies p ON p.id = b.policy_id
   JOIN projects pr ON pr.id = b.project_id
   LEFT JOIN users u ON u.id = s.subject_id
   WHERE s.kind = 'user'
   UNION ALL
   SELECT 'policy -> host key', p.name, s.name, NULL
   FROM policy_host_keys l JOIN policies p ON p.id = l.policy_id JOIN secrets s ON s.id = l.host_key_id
   UNION ALL
   SELECT 'policy -> model', p.name, m.name, NULL
   FROM policy_models l JOIN policies p ON p.id = l.policy_id JOIN models m ON m.id = l.model_id
   UNION ALL
   SELECT 'policy -> rate limit', p.name, rl.name, NULL
   FROM policies p JOIN rate_limits rl ON rl.id = p.rate_limit_id
   UNION ALL
   SELECT 'policy -> rate limit for models', p.name, COALESCE(rl.name, b->>'rateLimitId'), b->>'models'
   FROM policies p
   CROSS JOIN LATERAL jsonb_array_elements(CASE WHEN jsonb_typeof(p.spec->'rlBindings') = 'array' THEN p.spec->'rlBindings' ELSE '[]' END) AS b
   LEFT JOIN rate_limits rl ON rl.id = b->>'rateLimitId'
   ORDER BY 1, 2, 3;
   ```

   With the query saved as `dropped-links.sql`:

   ```bash
   psql "$RELAY_PG_DSN" --csv -f dropped-links.sql > dropped-links.csv
   ```

   Host keys are the rows of the `secrets` table. For `binding -> group` and `binding -> user` rows the `models` column holds the policy name and project name; these bindings are not dropped but change: group subjects bind nothing after the upgrade, user subjects govern only that project's tokens. The migration logs the same dropped links as it drops them.

3. **Back up Postgres.** Rolling back needs it; see [Rolling back](#rolling-back).

4. **Find subjects bound twice**, which would stop migration 35. Run this against the 0.11 database; it lists what the migration would refuse:

   ```sql
   SELECT s.kind, s.subject_id, string_agg(b.name, ', ' ORDER BY b.name) AS bindings
   FROM policy_binding_subjects s
   JOIN policy_bindings b ON b.id = s.binding_id
   WHERE s.subject_id IS NOT NULL
   GROUP BY s.kind, s.subject_id, CASE WHEN s.kind = 'user' THEN b.project_id END
   HAVING count(*) > 1;
   ```

   For each row, decide which binding keeps the subject and remove it from the others, on 0.11, before upgrading.

5. **Check for policies that migration 36 would refuse.** A policy with rows in `policy_models` and an empty `models` field, or rows in `policy_host_keys` and no pools or credentials, would become unrestricted once those tables are dropped; if it is bound to a non-group subject—disabled bindings count—the migration stops. Run this against the 0.11 database to find them:

   ```sql
   SELECT p.name AS policy, l.lost AS would_lose, l.bindings
   FROM policies p
   CROSS JOIN LATERAL (
       SELECT concat_ws(' and ',
                  CASE WHEN EXISTS (SELECT 1 FROM policy_models pm WHERE pm.policy_id = p.id)
                        AND (CASE WHEN jsonb_typeof(p.models) = 'array' THEN jsonb_array_length(p.models) ELSE 0 END) = 0
                       THEN 'model ids' END,
                  CASE WHEN EXISTS (SELECT 1 FROM policy_host_keys phk WHERE phk.policy_id = p.id)
                        AND NOT EXISTS (SELECT 1 FROM policy_pools pp WHERE pp.policy_id = p.id)
                        AND NOT EXISTS (SELECT 1 FROM policy_credentials pc WHERE pc.policy_id = p.id)
                       THEN 'host keys' END) AS lost,
              (SELECT string_agg(DISTINCT b.name, ', ' ORDER BY b.name)
               FROM policy_bindings b JOIN policy_binding_subjects s ON s.binding_id = b.id
               WHERE b.policy_id = p.id AND s.subject_id IS NOT NULL) AS bindings
   ) l
   WHERE l.lost <> '' AND l.bindings IS NOT NULL;
   ```

   For each row, the migration stops and reports: `migration 000036: bound policies would lose their only model or host-key restriction and widen; …: policy <name> loses its <what> (bound by <bindings>)`. Adding `models` or pools before upgrading is not possible—the pools table exists only in 0.20. On the 0.11 database, delete those bindings or remove those policies from them, then upgrade. After upgrading, add `models`, pools or credentials following [Re-creating the dropped links](#re-creating-the-dropped-links).

6. **Write the new manifests** in `relay.wyolet.dev/v1alpha3`, from the exports; [Re-creating the dropped links](#re-creating-the-dropped-links) maps each dropped link to its replacement:

   - An `Account` for each provider organization, and `account` on each of its host keys. A key you leave without one stays in the default account migration 36 gave it.
   - A `PolicyBinding` of a tier preset (or your own tier policy) on each account, replacing the host keys' `policyId`. List a host's presets with `GET /api/hosts/{host}/policies`.
   - A `Pool` for each set of host keys a policy listed, with the old `keySelection` as its `selection`.
   - Each policy with `pools` (or `credentials`), `rateLimits` and, where you want spend caps, `budgets`. Only a policy bound to a host, an account or a host key may scope a rate limit to `models`.
   - A `Budget` linked by the team's or project's policy in place of a team or project `budget`.
   - Policy bindings on the subjects the keys and service accounts pointed at, and on the users, team or project in place of group and `system:authenticated` subjects. Remove group subjects from the bindings you keep: a binding that still has one is refused when it is saved again.
   - No `priority` on bindings, and no `policies` or `defaultPolicy` on hosts.

   [Policy examples](/policy-examples) shows each of these.

7. **Pick the catalog release.** Set `RELAY_CATALOG_VERSION` to the relay-catalog release with the v1alpha3 schema that is published for 0.20. A release in the older schema is refused by 0.20.

## Upgrade steps

1. Keep callers off the inference port until step 5. Between the migration and your new bindings, principals reach what their scopes own, which may be more than before.
2. Stop every 0.11 pod: scale the deployment to 0, as in [Stop-and-start upgrades](/concepts/upgrade#stop-and-start-upgrades).
3. Deploy 0.20 with the new `RELAY_CATALOG_VERSION`. Migrations 35 and 36 run, and the catalog release is seeded. Keep the log of the pod that ran the migrations, or of `relay migrate up` if you migrate in a step of its own: it holds the `000036: dropping link` lines. If migration 35 stops on a subject bound twice, it applies nothing but leaves version 35 marked dirty: run `relay migrate force 34` (see [Recovering from a dirty schema version](/concepts/upgrade#recovering-from-a-dirty-schema-version)), start the 0.11 image again, fix the bindings, and repeat.
4. Apply the manifests with the 0.20 CLI, dry run first:

   ```bash
   relay apply -f manifests/ --dry-run
   relay apply -f manifests/
   ```

5. Check representative credentials, then let callers back in:

   ```bash
   curl http://localhost:8080/v1/models -H "Authorization: Bearer <relay key>"
   curl -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" http://localhost:8081/api/policies/<policy>/models
   ```

   Watch `relay_inference_auth_rejected_total` and the `403` and `503` codes in the [usage events](/concepts/usage#failed-requests) for refusals you did not expect.

6. Re-run token revocations, see [The state store](#the-state-store).

## Re-creating the dropped links

Each row of the export, and each `000036: dropping link` line, has a replacement in 0.20:

| Dropped link | In 0.20 |
| --- | --- |
| key → policy | A policy binding of the policy on the key's principal. |
| host key → tier policy | A policy binding of the tier on the key's account. |
| policy → host key | `credentials`, or a pool in `pools`, on the policy. |
| policy → model | `models` on the policy, as model references (`provider/model`). |
| policy → rate limit | `rateLimits: [{ref}]` on the policy. |
| policy → rate limit for models | `rateLimits: [{ref, models}]` on the policy, which may then be bound only to a host, an account or a host key. |

The catalog's tier policies, owned by their host, get their rate limits back when the v1alpha3 catalog release is seeded, so their `policy → rate limit` rows need nothing from you, unless you edited those policies.

### A host key's tier

Migration 36 put each host key in its owner's default account at its host, named after the host. List the accounts with `GET /api/accounts` and an account's keys with `GET /api/accounts/{ref}/keys`. Bind the tier to the account with a binding owned by the system:

```yaml
apiVersion: relay.wyolet.dev/v1alpha3
kind: PolicyBinding
metadata:
  name: anthropic-tier
  owner: {kind: system}
spec:
  policy: anthropic-start
  subjects:
    - {kind: account, name: anthropic}
```

An account has one policy. Host keys of one owner at one host share a default account, so if they had different tiers, they belong to different provider organizations: create an account for each, name it on its keys, and bind each tier to its own account:

```yaml
apiVersion: relay.wyolet.dev/v1alpha3
kind: Account
metadata:
  name: openai-build-org
  owner: {kind: system}
spec:
  host: openai
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: HostKey
metadata:
  name: openai-build-key
  owner: {kind: system}
spec:
  hostId: openai
  account: openai-build-org
  valueFrom: {kind: env, env: OPENAI_BUILD_KEY}
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: PolicyBinding
metadata:
  name: openai-build-org-tier
  owner: {kind: system}
spec:
  policy: openai-build
  subjects:
    - {kind: account, name: openai-build-org}
```

Accounts you create cool on a provider `429`, unlike default accounts; see [Accounts](/concepts/key-pooling#accounts).

### A relay key's policy

A policy now reaches a relay key through the key's principal, the service account or user the key belongs to. Every key of a principal has the principal's policy, and a subject has one binding, so keys of one principal that pointed at different policies need either one policy for all of them or a principal each, such as a service account per use.

For a service account's key, bind the policy with a binding owned by the service account's project. The policy may be owned by that project, its team or the system. Keys created without a user before service accounts existed belong to generated service accounts in the `legacy` project, named `legacy-<key name>-` and the last 8 characters of the key's id:

```yaml
apiVersion: relay.wyolet.dev/v1alpha3
kind: Policy
metadata:
  name: ci
  owner: {kind: project, name: legacy}
spec:
  models: [anthropic/claude-haiku-4-5]
  credentials: [anthropic-main]
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: PolicyBinding
metadata:
  name: ci-runner
spec:
  project: legacy
  policy: ci
  subjects:
    - {kind: serviceaccount, name: legacy-ci-runner-0d9f1a2b}
```

For a user's own key, bind a system-owned policy with a binding owned by the system:

```yaml
apiVersion: relay.wyolet.dev/v1alpha3
kind: RateLimit
metadata:
  name: alice-rpm
  owner: {kind: system}
spec:
  rules:
    - {meter: requests, amount: 60, window: 1m, strategy: sliding-window}
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: Policy
metadata:
  name: alice
  owner: {kind: system}
spec:
  models: [anthropic/*]
  rateLimits:
    - ref: alice-rpm
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: PolicyBinding
metadata:
  name: alice
  owner: {kind: system}
spec:
  policy: alice
  subjects:
    - {kind: user, name: alice}
```

A policy a user owns, such as one made for their own automation key, stays theirs: the user binds it to themselves with a binding they own, and it governs their relay keys; their inference tokens follow the binding of the project or team they act in. It cannot sit beside a system-owned binding of the same user, so use one or the other:

```yaml
apiVersion: relay.wyolet.dev/v1alpha3
kind: PolicyBinding
metadata:
  name: alice-own
  owner: {kind: user, name: alice}
spec:
  policy: alice-bot
  subjects:
    - {kind: user, name: alice}
```

Two limits of this version apply here:

- A binding owned by a project may name the user, but it governs only the inference tokens the user mints for that project, not the user's relay keys. It may use the user's own policy only while that user may create policy bindings in the project.
- A policy bound to a user, a service account, a team or a project cannot scope a rate limit to models: its rate limits count every model together, and saving one with `models` is refused. Per-model limits belong in a policy bound to a host, an account or a host key.

## The state store

The Helm chart and the Compose stack bundle Dragonfly as the state store in place of Valkey. Upgrading with the chart's defaults replaces the bundled Valkey with an empty Dragonfly, and the [chart README](https://github.com/wyolet/relay/blob/main/chart/README.md) has the values that keep Valkey. An external store run as Dragonfly needs `--cluster_mode=emulated --lock_on_hashtags`.

An empty store at the cutover means:

- Control-plane sessions end: users sign in again.
- Rate-limit windows and key breaker state start fresh.
- Revoked inference tokens are accepted again until they expire.

Token revocation moves to one list in the store, the `{revoked}:tokens` key, which 0.11 did not have: tokens revoked one by one under 0.11 are accepted again after the upgrade, whether or not the store changes. Revoke them again with `DELETE /api/auth/token/{jti}`, or revoke all of a user's tokens with `POST /api/users/by-id/{id}/revoke-tokens`, which survives any store change because the user's token version is kept in Postgres. See [Revoking a token](/concepts/auth#revoking-a-token).

When a 0.20 deployment later moves to another store, copy the revocation list across before switching. The key expires with the last token on it, so it is absent when no revoked token is still valid, and there is nothing to copy:

```bash
old="redis-cli -h <old store> -a <password>"
new="redis-cli -h <new store> -a <password>"
$new SET '{revoked}:tokens' "$($old --raw GET '{revoked}:tokens')" EX "$($old TTL '{revoked}:tokens')"
```

## Rolling back

`relay migrate down 34` recreates the dropped tables and column empty and deletes what 0.20 added: accounts, pools, budgets, their links, team-, user- and system-owned bindings, and binding subjects of the new kinds. It does not bring back the policy links migration 36 removed, so a 0.11 pod on that schema runs with no policy links at all.

To return to 0.11, stop every pod, restore the Postgres backup taken before the upgrade, and deploy the 0.11 image. See [Rolling back](/concepts/upgrade#rolling-back) for the general procedure.
