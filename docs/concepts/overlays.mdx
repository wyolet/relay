---
title: "Catalog Overlays"
description: "Customize catalog models without losing your changes on the next catalog update"
---

Catalog upgrades refresh catalog rows, and a direct API edit marks a row dirty so upgrades skip it from then on, including fields you never touched. An **overlay** avoids both: it is a sparse patch you own, stored next to the pristine catalog row and merged over it when Relay builds its in-memory snapshot. Routing sees the merged result; catalog upgrades keep updating every field you did not override.

Overlays apply to **models**. Use one to pin a context window, add an alias, or add tags to a catalog model.

## How it works

| Term | What it is |
| --- | --- |
| **Template** | The catalog row as seeded. Catalog upgrades replace it. |
| **Overlay** | Your patch: only the spec fields you set. |
| **Effective** | The template with the overlay merged over it. Exists only in memory, and is what routing uses. |

The merge follows JSON merge patch rules:

- A scalar or array in the patch replaces the template's value.
- A nested object merges field by field.
- `null` removes the field.
- `aliases` and `tags` are the exception: the patch's entries are added to the template's, so a catalog upgrade can still add aliases or tags. To remove one the template ships, edit the model directly.
- `enabled` cannot be set through an overlay; enable or disable the model with a direct edit.

<Info>
Because the effective row lives only in memory, reading the model through the CRUD endpoints or the database shows the **template**. The overlay endpoint returns the template, your patch and the effective spec in one response.
</Info>

## Managing an overlay

The overlay is a sub-resource of the model on the control API:

```bash
# Template, your patch, and the effective spec
curl -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  http://localhost:8081/api/models/by-id/<id>/overlay

# Set or replace your patch: spec fields at the top level
curl -X PUT http://localhost:8081/api/models/by-id/<id>/overlay \
  -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"patch": {"aliases": ["my-model"], "contextWindowTotal": 200000}}'

# Remove the overlay; the template applies unchanged
curl -X DELETE http://localhost:8081/api/models/by-id/<id>/overlay \
  -H "Authorization: Bearer $RELAY_ADMIN_TOKEN"
```

`patch` holds spec fields directly, not a `spec` wrapper; metadata cannot be patched.

<Note>
`PUT` **replaces** the whole patch; it does not merge with the previous one. Send every field you want overridden. A `PUT` whose result would not be a valid model is rejected with `400`.
</Note>

Setting an overlay counts as an edit of the model, so it follows the same rules: the `governance:model` setting and, under RBAC, the caller's permissions.

## When the template changes underneath

If a catalog upgrade changes the template so that your patch no longer produces a valid model, Relay serves the template unchanged and the overlay response reports `quarantined: true` with a `quarantineReason`. Fix the patch with a new `PUT`, or delete it.

Overlays are rows in Postgres, so backing up the database captures them. [`relay export`](/concepts/gitops#export) includes them in an unscoped export, and `relay apply` can write them back.
