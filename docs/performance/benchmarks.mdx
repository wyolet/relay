These results measure the Relay v0.11.7 code under load, on dedicated AWS boxes with a mock upstream. They are the baseline taken before a planned rework of the request engine; the same scenarios will be rerun after it and added as a new tab beside each table. These are measurements of one setup. Your capacity depends on your store, network, request mix and upstream latency; measure your own with [`relay_overhead_seconds`](/reference/metrics#measuring-relay-overhead).

For how to turn these numbers into a deployment, see [Sizing and tuning](/performance/sizing).

## What this measures

Each run puts one relay (or a group of relays behind HAProxy) on its own box, sends it an open-loop request schedule from a generator box, and steps the offered rate up until the relay refuses part of it. The upstream is a mock that answers with a fixed latency model, so every millisecond of variation above it is Relay, the network, or the state store.

This is not a service-level objective, and the numbers are not a promise for any other setup. The repository's in-process benchmarks (`make bench-gate`, in-memory state, no network) are a regression gate for allocations and are not published as performance figures.

| | v0.11.7 (before engine rework) |
| --- | --- |
| Relay code | Development builds with no Go changes against v0.11.7. The state-store and upstream idle-connection runs used v0.11.7 without its last commit, which makes the upstream idle cap default to the in-flight cap; each table states its settings. |
| Go | 1.27.3, default `GOEXPERIMENT` |
| Relay boxes | AWS c7a: `c7a.xlarge` (4 cores), `c7a.2xlarge` (8), `c7a.4xlarge` (16), `c7a.8xlarge` (32). One relay per box, the whole box. |
| Generator and mock | One box running 40 generator processes and the mock upstream on separate pinned cores: `c7a.16xlarge`, or `c7a.8xlarge` for the four-relay group and the default in-flight cap runs. |
| State store | Dragonfly v2.0.2 with `--cluster_mode=emulated --lock_on_hashtags`, 12 threads, on its own `c7a.8xlarge`, unless the scenario says otherwise. Postgres 16 and ClickHouse 24.8 on the same box. |
| Network | Private addresses in one availability zone, plain HTTP, no load balancer except in the four-relay group. |
| Request mix | Half Anthropic Messages, half OpenAI Chat Completions, non-streaming, routed to a host of the same shape, so bodies pass through without translation. Request bodies 2 KB at p50, 20 KB at p99. The relay keys belong to rate-limited policies, so every request reserves and settles a rate limit in the store. |
| Mock upstream | Time to first token 20 ms, 5,000 tokens per second, 150 output tokens at p50: about 50 ms per request. |
| Steps | Each offered rate is warmed up for 30 s and then held for 90 s. |
| Relay environment | `GOMAXPROCS` = box cores, `GOMEMLIMIT` = 90 % of the container memory limit, `GOGC=100`, `RELAY_STATE_BACKEND=redis`, `RELAY_MAX_INFLIGHT=20000` unless stated, `RELAY_PG_MAX_CONNS=20`, usage events to ClickHouse. |

## How to read the numbers

- **Overhead** is measured by the generator: the client-side total latency of a request minus the duration the mock upstream reports for it. It includes two network hops inside one availability zone, so it is a little higher than [`relay_overhead_seconds`](/reference/metrics#measuring-relay-overhead), which Relay measures inside the process. Each step reports the worse of the two request types.
- **Errors** are every non-2xx response, as a share of all responses, the worse of the two request types. A request refused as overloaded (`503`, or `529` on Anthropic-shaped routes) counts as an error.
- **Latency knee** is the highest step at which p99 overhead stays at or under 15 ms with at most 0.1 % errors, with every lower step passing too.
- **Error capacity** is the highest served rate at a step with at most 0.1 % errors. Its p99 is always given with it, because it is usually well past the knee.
- **Relay cores** and **working set** cover the last two minutes of each step. Working set is the largest value in that window.
- A step where the generators fell behind their schedule measures the generator, not Relay. Those steps are marked as excluded and left out of every figure. Where the generators sent less than the step's rate without falling behind, the table shows what was sent.
- Usage record delivery was not checked in these runs.

### Later run: 16 and 32 cores on the v0.11.8 code

A separate run after v0.11.7, on 16 and 32 cores only, with a development build carrying the Go code of v0.11.8 before its dependency updates. It includes allocation and garbage-collection work on the request path. It compares `GOGC=100` with `GOGC=400`, alternating the two on the same boxes; each row is the mean of two runs, except the 32-core steps from 48,000 up, which ran once. Same setup as the v0.11.7 table otherwise: generators on a `c7a.16xlarge`, Dragonfly with hash tags on a `c7a.8xlarge`, `RELAY_MAX_INFLIGHT=20000`. There are no v0.11.8 figures for 4 cores, 8 cores or the four-relay group.

## Past capacity

Past error capacity, a single relay refuses the excess as overloaded (`503`, or `529` on Anthropic-shaped routes, with `Retry-After: 1`) and keeps serving close to its highest rate: the 8-core box served 25,563 rps at 32,000 offered against a peak of 26,141, and the 16-core box 41,451 at 56,000 against 41,860. Two exceptions:

- The four-relay group fell from 77,921 rps to 60,618 at the next step, with 9.7 % errors, as the wait on the shared store reached its highest (admission p99 123 ms).
- On 32 cores the generators fell behind above 64,000 offered, so behaviour past that point was not measured.

## Rerun it

The harness itself is not published. The setup and reading rules above describe the method in full: a fixed request mix against a mock with a known latency model, open-loop steps with warm-up and hold, overhead as client latency minus mock duration, and the knee and capacity rules applied per step.
