Relay is a self-hosted gateway that puts one endpoint in front of your LLM providers. Your app sends OpenAI-shaped (Chat Completions, Responses, Embeddings) or Anthropic-shaped (Messages) requests, or Relay's own canonical shape at `/v1/generate`, with a relay key. Relay checks what that key may use, picks an upstream credential from a pool, enforces rate limits, forwards the call, and records usage and cost.

## Why it exists

A provider API key has one rate limit and fails on its own. Running real traffic means writing the same code in every app: spread load over several keys, retry on `429`, skip a revoked key, keep per-model limits, attribute spend to a team. Relay moves that into one service you run next to your apps.

## The mental model

The catalog describes what can be called. Credentials and policies describe who may call it and with what.

<AccordionGroup>
  <Accordion title="Hosts" icon="server">
    An upstream endpoint Relay sends requests to: a provider's API (`openai`, `anthropic`, `google`) or your own server, such as a self-hosted Ollama. A host has a base URL. See [Catalog](/concepts/catalog).
  </Accordion>
  <Accordion title="Models" icon="cube">
    A catalog entry, owned by the provider that makes it. The `model` field of a request resolves against the catalog by name, optionally pinned to a host as `model@host`.
  </Accordion>
  <Accordion title="Host bindings" icon="link">
    The join of one model and one host. A binding carries the wire shape Relay speaks to that host for that model (`openai`, `openai_responses`, `anthropic` or `gemini`), the upstream model name, and the pricing. A model is reachable only through an enabled binding, and one model can have bindings on several hosts.
  </Accordion>
  <Accordion title="Host keys" icon="key">
    Your provider credentials, stored by Relay as an environment-variable reference or as a value encrypted under the master key. Each host key belongs to one host. See [Authentication](/concepts/auth#host-keys).
  </Accordion>
  <Accordion title="Relay keys and inference tokens" icon="ticket">
    The credentials your apps send. A relay key (`sk-wr-…`) is long-lived and belongs to a service account or a user. An inference token is short-lived, minted for a signed-in user, and scoped to one project. Neither exposes a host key. See [Authentication](/concepts/auth).
  </Accordion>
  <Accordion title="Policies and policy bindings" icon="scale-balanced">
    A policy grants models, lists the host keys requests may spend, and names a rate limit. A relay key can point at a policy directly; otherwise a service account's policy or a project's policy bindings decide. See [Policies](/concepts/policies).
  </Accordion>
  <Accordion title="Rate limits" icon="timer">
    Named rule sets (requests, tokens, concurrency per window). A policy's rate limit caps everyone it governs; a host key's tier limit caps that one upstream credential. See [Rate limits](/concepts/rate-limits).
  </Accordion>
  <Accordion title="Teams, projects, service accounts, users" icon="users">
    The tenancy layer. Teams contain projects; projects contain service accounts; users join through groups and role bindings. Keys, policies and usage are attributed to this hierarchy, and RBAC scopes on it. See [Authentication](/concepts/auth#authorization).
  </Accordion>
</AccordionGroup>

## A request, end to end

<Steps>
  <Step title="Authenticate">
    The app sends a request with a relay key or an inference token. Relay resolves it to a principal: a service account or a user, plus its project and team.
  </Step>
  <Step title="Resolve the policy">
    Relay finds the governing policy: the key's own, else the service account's, else the first matching policy binding in the project.
  </Step>
  <Step title="Route">
    The `model` is resolved against the catalog. Relay walks the model's enabled bindings, keeps those the policy grants, and picks the first whose host has a usable host key in the policy.
  </Step>
  <Step title="Reserve and pick a key">
    The policy's rate limit is reserved. A healthy host key is picked from the policy's keys for that host, and its tier limit is reserved. If the key fails before any response bytes are sent, Relay tries the next key.
  </Step>
  <Step title="Forward and settle">
    The request goes upstream, translated if the binding speaks a different shape, and the response streams back in the shape you sent. When the response ends, Relay commits the token counts to the rate limits and records the usage event.
  </Step>
</Steps>
