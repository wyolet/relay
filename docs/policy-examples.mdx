Each example is a `relay.wyolet.dev/v1alpha3` manifest bundle. Apply it with [`relay apply`](/concepts/gitops), dry run first:

```bash
relay apply -f policies/ --dry-run
relay apply -f policies/
```

The examples build on each other: the second and third use the team, project and account the first one declares. The tier presets they bind (`openai-build`, `openai-grow`) ship in catalog releases with the v1alpha3 schema. How the pieces combine is on [Policies](/concepts/policies).

## A team policy with a pool, a budget and a scoped rate limit

An admin provisions the upstream side: one OpenAI organization as an account, its two keys, and a pool of them. The team gets a policy that draws on the pool, a monthly budget, a request limit for everything, and a token limit for one model.

```yaml
apiVersion: relay.wyolet.dev/v1alpha3
kind: Team
metadata:
  name: ml
spec: {}
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: Project
metadata:
  name: search
spec:
  team: ml
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: Account
metadata:
  name: acme-openai
  owner: {kind: system}
spec:
  host: openai
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: HostKey
metadata:
  name: acme-openai-a
  owner: {kind: system}
spec:
  hostId: openai
  account: acme-openai
  valueFrom: {kind: env, env: OPENAI_KEY_A}
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: HostKey
metadata:
  name: acme-openai-b
  owner: {kind: system}
spec:
  hostId: openai
  account: acme-openai
  valueFrom: {kind: env, env: OPENAI_KEY_B}
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: Pool
metadata:
  name: openai-main
  owner: {kind: system}
spec:
  host: openai
  credentials: [acme-openai-a, acme-openai-b]
  selection: prioritized
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: Budget
metadata:
  name: ml-monthly
  owner: {kind: team, name: ml}
spec:
  amountUsd: "2000"
  period: month
  mode: hard
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: RateLimit
metadata:
  name: ml-requests
  owner: {kind: system}
spec:
  rules:
    - {meter: requests, amount: 600, window: 1m, strategy: sliding-window}
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: RateLimit
metadata:
  name: ml-gpt-5-5-tokens
  owner: {kind: system}
spec:
  rules:
    - {meter: tokens, amount: 2000000, window: 1m, strategy: sliding-window}
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: Policy
metadata:
  name: ml
  owner: {kind: team, name: ml}
spec:
  models: [openai]
  pools: [openai-main]
  rateLimits:
    - ref: ml-requests
    - ref: ml-gpt-5-5-tokens
      models: [openai/gpt-5-5]
  budgets: [ml-monthly]
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: PolicyBinding
metadata:
  name: ml
  owner: {kind: team, name: ml}
spec:
  policy: ml
  subjects:
    - {kind: team, name: ml}
```

What this gives every request on the team's rung, which is every service-account key and inference token of every project in `ml`:

- Only OpenAI models, and only through `openai-main`. The policy links a pool, so it decides reach: the team's members no longer fall back to the host keys their scopes own.
- 600 requests a minute and $2,000 a month, each one counter shared by the whole team.
- 2,000,000 tokens a minute for `gpt-5-5`, one counter across the team; other models are not limited by it.
- Unpriced OpenAI models are refused while the budget applies.

The host keys, the account, the pool and the rate limits are system-owned because host keys and rate limits cannot be owned by a team, and a team's pool may hold only system-owned keys. The budget, the policy and the binding belong to the team, so a `team-admin` can change them.

## Binding a tier to an account

The account's keys share the organization's limits only once a tier policy is bound to the account. Bind the catalog preset that matches your OpenAI usage tier:

```yaml
apiVersion: relay.wyolet.dev/v1alpha3
kind: PolicyBinding
metadata:
  name: acme-openai-tier
  owner: {kind: system}
spec:
  policy: openai-grow
  subjects:
    - {kind: account, name: acme-openai}
```

A project that brings its own OpenAI organization owns its account and binds the tier itself, with a binding owned by the project:

```yaml
apiVersion: relay.wyolet.dev/v1alpha3
kind: Account
metadata:
  name: search-openai
  owner: {kind: project, name: search}
spec:
  host: openai
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: PolicyBinding
metadata:
  name: search-openai-tier
spec:
  project: search
  policy: openai-build
  subjects:
    - {kind: account, name: search-openai}
```

A tier negotiated with the provider is a policy of your own. Scope each rate limit to the models it covers, as the presets do, so each model counts on its own:

```yaml
apiVersion: relay.wyolet.dev/v1alpha3
kind: Account
metadata:
  name: acme-openai-enterprise
  owner: {kind: system}
spec:
  host: openai
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: RateLimit
metadata:
  name: acme-openai-gpt-5-5
  owner: {kind: system}
spec:
  rules:
    - {meter: requests, amount: 20000, window: 1m, strategy: sliding-window}
    - {meter: tokens, amount: 40000000, window: 1m, strategy: sliding-window}
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: Policy
metadata:
  name: acme-openai-enterprise-tier
  owner: {kind: system}
spec:
  rateLimits:
    - ref: acme-openai-gpt-5-5
      models: [openai/gpt-5-5]
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: PolicyBinding
metadata:
  name: acme-openai-enterprise-tier
  owner: {kind: system}
spec:
  policy: acme-openai-enterprise-tier
  subjects:
    - {kind: account, name: acme-openai-enterprise}
```

An account has one policy. To move it to another tier, change the binding's `policy`; counters of a rate limit both tiers link carry over, since upstream counters do not depend on the policy.

## Per-project budgets

The `search` project gets a weekly cap and an alert below it, and its evaluation service account a daily cap and a single model:

```yaml
apiVersion: relay.wyolet.dev/v1alpha3
kind: Budget
metadata:
  name: search-weekly
  owner: {kind: project, name: search}
spec:
  amountUsd: "250"
  period: week
  mode: hard
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: Budget
metadata:
  name: search-weekly-alert
  owner: {kind: project, name: search}
spec:
  amountUsd: "150"
  period: week
  mode: alert
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: Policy
metadata:
  name: search
  owner: {kind: project, name: search}
spec:
  budgets: [search-weekly, search-weekly-alert]
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: PolicyBinding
metadata:
  name: search
spec:
  project: search
  policy: search
  subjects:
    - {kind: project, name: search}
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: ServiceAccount
metadata:
  name: eval-runner
spec:
  project: search
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: Budget
metadata:
  name: eval-runner-daily
  owner: {kind: project, name: search}
spec:
  amountUsd: "20"
  period: day
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: Policy
metadata:
  name: eval-runner
  owner: {kind: project, name: search}
spec:
  models: [openai/gpt-4o-mini]
  budgets: [eval-runner-daily]
---
apiVersion: relay.wyolet.dev/v1alpha3
kind: PolicyBinding
metadata:
  name: eval-runner
spec:
  project: search
  policy: eval-runner
  subjects:
    - {kind: serviceaccount, name: eval-runner}
```

A request with an `eval-runner` key passes three caller rungs. It must fit the team's $2,000 a month, the project's $250 a week and the service account's $20 a day, and it may call only `gpt-4o-mini`, since the team allows all of OpenAI and the service account narrows that to one model. Neither project policy links a pool, so reach still comes from the team's `openai-main`. The alert budget refuses nothing; the charge that reaches $150 counts once in `relay_limits_budget_crossings_total`.

To cap one person inside the project, bind a policy to the user with a binding owned by the project. It governs only the inference tokens that user mints for `search`; the user's own relay keys and their tokens for other projects are not affected.

## Checking the result

List what a credential can reach; a model a rung refuses does not appear:

```bash
curl http://localhost:8080/v1/models -H "Authorization: Bearer <eval-runner key>"
```

Read what one policy allows and the limits it applies per model, without the rest of the ladder:

```bash
curl -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" http://localhost:8081/api/policies/ml/models
curl -H "Authorization: Bearer $RELAY_ADMIN_TOKEN" http://localhost:8081/api/policies/ml/rate-limits
```

A refused request names the rung and the policy that refused it; the codes are in [Policy refusals](/reference/inference-api#policy-refusals).
